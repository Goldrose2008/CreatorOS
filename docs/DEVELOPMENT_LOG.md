# Журнал разработки

## План Localization Dashboard CreatorOS

### Архитектура и поэтапная реализация

#### **Этап LD-1 — фундамент Localization Dashboard**
- Создать отдельный developer-tool target `CreatorOSLocalization`, не входящий в runtime приложения.
- Выделить модель записи локализации и каталог: загрузка, доступ к entries, изменение значения, добавление/удаление записи и подготовка сохранения.
- Убедиться, что работа с TSV отделена от будущего Qt Widgets UI.
- На первом этапе не выполнять массовое изменение существующей локализации и не внедрять сложный UI.
- Результат: устойчивый программный слой, на который опираются scanner, editor и dashboard.

#### **Этап LD-2 — Source Scanner и Usage Index**
- Сканировать актуальный `src/` и находить статические обращения к localization ID.
- Для каждого ID считать количество использований и хранить файл/строку.
- Определять категории: used, unused, missing, duplicate и dynamic reference.
- Добавить повторяемый анализ без изменения исходного кода.
- Отдельно определить безопасный формат статических localization references, пригодный для rename.

#### **Этап LD-3 — первый Localization Dashboard UI**
- Создать Qt Widgets-интерфейс developer tool.
- Реализовать таблицу ID / переводы / usage / status.
- Добавить поиск, фильтрацию, просмотр всех найденных мест использования и Problems.
- Показывать результаты Source Scanner и Validator в одном интерфейсе.

#### **Этап LD-4 — полноценное редактирование каталога**
- Добавление, удаление и редактирование localization entries.
- Автоматическая генерация корректного `localization.tsv`.
- Сортировка и стабильное форматирование файла.
- Контроль уникальности ID и обязательных языковых колонок.
- Сохранение только после успешной валидации.

#### **Этап LD-5 — безопасный Rename ID**
- Переименование localization ID из Dashboard.
- Предварительный preview всех изменений в TSV и source-файлах.
- Замена только распознанных localization references, а не глобальный text replacement.
- Проверка, что исходные файлы не изменились после сканирования.
- Повторный scan и автоматическая проверка отсутствия старого ID.

#### **Этап LD-6 — Validator и защита качества**
- Проверка missing/unused IDs, дублирования переводов, пустых обязательных значений, placeholder consistency и некорректного формата TSV.
- Отдельное отображение динамических ссылок, которые нельзя гарантированно переименовать автоматически.
- Добавление понятных предупреждений и ошибок перед сохранением.

#### **Этап LD-7 — эксплуатация и release workflow**
- Добавить поддержку нескольких языков без изменения архитектуры каталога.
- Добавить экспорт/импорт и резервную копию перед массовыми изменениями.
- Подготовить release-проверки локализации.
- Документировать workflow для разработчика.
- После стабилизации оценить возможность запуска Dashboard из development environment одной командой.

### Контрольные критерии готовности Dashboard

Localization Dashboard считается базово готовым, когда он умеет:
- показать все entries из `localization.tsv`;
- показать для каждого ID количество и места использования;
- находить unused и missing IDs;
- находить дублирующиеся переводы;
- редактировать и сохранять TSV;
- безопасно переименовывать ID с preview изменений в source;
- после любой операции повторно валидировать проект.

### Актуализация принципа локализации
- По результатам обсуждения унификация должна быть шире первоначального правила: различие сущности само по себе не является основанием для отдельного text ID.
- Универсальные тексты формата Back, Error, Edit, Not Found, Delete, Name, Loading/Empty/Error и Progress выносятся в `common.*`; конкретное имя объекта при необходимости формируется UI.
- `docs/LOCALIZATION.md` актуализирован под эту модель.

## Правила разработки
* Все изменения в исходном коде выполняются пользователем по точечным инструкциям. GPT самостоятельно изменяет только документы из `/docs`.
* На каждом ответе GPT выдаёт инструкции для пользователя: в каком файле (прописывая полный путь до файла) и что нужно добавить/удалить/изменить. 
* Перед каждым новым архитектурным или кодовым этапом проверяются последний commit, фактическое дерево проекта, `TECHNICAL_SPEC.md`, `DEVELOPMENT_LOG.md`, `PROGRAM_STRUCTURE.md` и соответствующий текущий исходный код.
* После добавления каждого нового файла его фактический путь и назначение сразу отражаются в `PROGRAM_STRUCTURE.md`. После удаления файла соответствующая запись удаляется.
* После каждого крупного этапа выполняются проверка работоспособности и запись в DEVELOPMENT_LOG (журнал разработки) по схеме:
```
## <текущая дата>
### <тема>
  <описание>
### <тема>
  <описание>
...
```
Повторно одна и та же дата не проставляется.
* Временные реализации фиксируются в разделе «Временные решения». После замены или отмены временного решения запись актуализируется или удаляется.
* Технические и постоянные архитектурные правила хранятся в `TECHNICAL_SPEC.md`; журнал фиксирует фактически выполненную работу и контрольные точки.
* Название и версия приложения хранятся в единственном источнике `src/app/AppInfo.h`.
* Локализуемые тексты хранятся в едином `localization.tsv`; каталоги переводов строит `LocalizationService`.
* Основной стек: C++20 + Qt 6 Widgets + CMake + SQLite.
* Любая новая внешняя зависимость сначала проходит проверку лицензии и способа распространения, и только после этого добавляется в проект.

* UI-класс рассматривается как целостная программная единица: визуальная структура, локальное состояние и UI-поведение остаются вместе, если относятся к одной ответственности.
* В базовом UI-классе допускается заранее собрать общие механизмы отображения, которые потенциально нужны производным классам.
* База знает UI-механизмы; наследник знает конкретную сущность. База не содержит ветвлений по типам Project / Content / Task.
* Наследование является основным способом переиспользования общей целостной сущности при реальном `is-a` отношении, общем контракте и общем поведении.
* Composition применяется внутри целостной сущности для сложных независимых объектов с собственной ответственностью, состоянием или контрактом.
* Новый UI-класс не создаётся только потому, что участок интерфейса «надо вынести» или потому, что `.cpp` стал большим.
* Простые `QLabel`, `QPushButton`, layout и участки обычной разметки не получают отдельный архитектурный класс без самостоятельной причины.
* Отдельный компонент появляется только при самостоятельной ответственности, реальном повторном использовании, собственном контракте, сложном состоянии/жизненном цикле или отдельной технической границе.
* Application/domain содержат бизнес-правила, инварианты, вычисления, прикладные операции и жизненный цикл сущностей. Infrastructure/adapters содержат SQLite, файловые, сетевые и другие технические процессы.
* Общие прикладные алгоритмы не копируются между Project, Content и Task. После подтверждения повторения используется общий типобезопасный механизм.


## Временные решения:
- **Незавершённые маршруты AppShell:** `home`, `planning`, `library`, `analytics` и `settings` пока представлены временными placeholder-страницами внутри `AppShell`. По мере реализации соответствующей функциональности временные записи должны удаляться.
- **Иконки UI:** `src/ui/style/Icons.cpp` временно использует стандартные Qt-иконки там, где собственные ресурсы ещё не подключены. После появления собственных ресурсов реализация должна быть актуализирована.

### Архитектурная ревизия native UI
- Уточнён основной принцип архитектуры: UI-класс является целостной единицей и может содержать визуальную структуру, локальное состояние и логику взаимодействия пользователя в одном классе.
