# Журнал разработки

## Правила разработки
* Все изменения в исходном коде выполняются пользователем по точечным инструкциям. GPT самостоятельно изменяет только документы из `/docs`.
* На каждом ответе GPT выдаёт инструкции для пользователя: в каком файле (прописывая полный путь до файла) и что нужно добавить/удалить/изменить. 
* Перед каждым новым архитектурным или кодовым этапом проверяются последний commit, фактическое дерево проекта, `TECHNICAL_SPEC.md`, `DEVELOPMENT_LOG.md`, `PROGRAM_STRUCTURE.md` и соответствующий текущий исходный код.
* После добавления каждого нового файла его фактический путь и назначение сразу отражаются в `PROGRAM_STRUCTURE.md`. После удаления файла соответствующая запись удаляется.
* После каждого крупного этапа выполняются проверка работоспособности и запись в DEVELOPMENT_LOG (журнал разработки) по схеме:
```
## <текущая дата>
### <тема>
  <описание>
### <тема>
  <описание>
...
```
Повторно одна и та же дата не проставляется.
* Временные реализации фиксируются в разделе «Временные решения». После замены или отмены временного решения запись актуализируется или удаляется.
* Технические и постоянные архитектурные правила хранятся в `TECHNICAL_SPEC.md`; журнал фиксирует фактически выполненную работу и контрольные точки.
* Название и версия приложения хранятся в единственном источнике `src/app/AppInfo.h`.
* Локализуемые тексты хранятся в едином `localization.tsv`; каталоги переводов строит `LocalizationService`.
* Основной стек: C++20 + Qt 6 Widgets + CMake + SQLite. HTML/CSS/JavaScript и QWebEngine/WebChannel используются только в специализированных или переходных web-сценариях.

* UI-класс рассматривается как целостная программная единица: визуальная структура, локальное состояние и UI-поведение остаются вместе, если относятся к одной ответственности.
* В базовом UI-классе допускается заранее собрать общие механизмы отображения, которые потенциально нужны производным классам.
* База знает UI-механизмы; наследник знает конкретную сущность. База не содержит ветвлений по типам Project / Content / Task.
* Наследование является основным способом переиспользования общей целостной сущности при реальном `is-a` отношении, общем контракте и общем поведении.
* Composition применяется внутри целостной сущности для сложных независимых объектов с собственной ответственностью, состоянием или контрактом.
* Новый UI-класс не создаётся только потому, что участок интерфейса «надо вынести» или потому, что `.cpp` стал большим.
* Простые `QLabel`, `QPushButton`, layout и участки обычной разметки не получают отдельный архитектурный класс без самостоятельной причины.
* Отдельный компонент появляется только при самостоятельной ответственности, реальном повторном использовании, собственном контракте, сложном состоянии/жизненном цикле или отдельной технической границе.
* Application/domain содержат бизнес-правила, инварианты, вычисления, прикладные операции и жизненный цикл сущностей. Infrastructure/adapters содержат SQLite, файловые, сетевые и другие технические процессы.
* Общие прикладные алгоритмы не копируются между Project, Content и Task. После подтверждения повторения используется общий типобезопасный механизм.

### Архитектурная ревизия native UI
- Уточнён основной принцип архитектуры: UI-класс является целостной единицей и может содержать визуальную структуру, локальное состояние и логику взаимодействия пользователя в одном классе.
- Формальное разделение UI и UI-logic по разным файлам не используется. Пара .h/.cpp рассматривается как одна программная единица C++.
- Наследование становится предпочтительным механизмом повторного использования при реальном is-a отношении, общем контракте и общем поведении.
- Composition используется для независимых и опциональных частей, а не как обязательный способ построения всех специализированных UI-классов.
- Для повторяемых прикладных операций запрещено копировать один и тот же алгоритм по сущностям. Перед появлением нескольких одинаковых реализаций определяется общий типобезопасный механизм.
- План дальнейшей разработки заменён на «План последовательной реализации и рефакторинга».
- Архитектурная модель уточнена: базовый класс знает UI-механизмы, наследник знает конкретную сущность; inheritance является основным способом переиспользования целостной UI-сущности, composition используется для сложных независимых частей.
- `TECHNICAL_SPEC.md` и `PROGRAM_STRUCTURE.md` синхронизированы с новой моделью.

### Контрольная архитектурная ревизия — разработка остановлена
Перед продолжением функциональной разработки проведена проверка фактического кода по постоянным Правилам разработки из `docs/TECHNICAL_SPEC.md`.

Обнаруженные отклонения, требующие исправления:
1. **AppShell / navigation:** специализированная страница Tasks зарегистрирована, но ниже повторно вызывается регистрация placeholder с тем же route `tasks`. Одновременно исходная страница Home удалена, а в конце вызывается `navigateTo("home")` без зарегистрированного route. Это нарушает текущую схему навигации и является функциональной ошибкой.
2. **Composition root:** `MainWindow` напрямую создаёт инфраструктурные `Repository` и владеет ими. Для действующих правил граница UI ↔ application должна быть оформлена через отдельный composition/bootstrap-механизм, чтобы прикладной UI не был связан с конкретными инфраструктурными реализациями.
3. **Lifecycle Task:** удаление Project или Content не удаляет связанные Tasks. Поскольку `Task.parent_id` полиморфен и не может иметь прямой SQLite FK на оба типа сущностей, удаление родителя должно обеспечивать очистку/валидацию Tasks на application-уровне.
4. **Повторение UI-кода:** создание status-label с одинаковым оформлением повторяется в `ProjectCard`, `ContentCard` и `TaskCard`. Это противоречит правилу обязательного переиспользования реально общего поведения.
5. **TaskCard contract:** объявлен сигнал `openRequested`, но в текущем классе отсутствует соответствующее пользовательское действие. Контракт следует добавить только вместе с реальным сценарием открытия Task либо удалить до появления такого сценария.
6. **Переходный web-слой:** `WebUiHost`, `WebBridge`, `web.qrc` и обязательная линковка WebEngine/WebChannel пока сохраняются, хотя текущий прикладной UI работает через Qt Widgets. Это допустимо только как временное переходное решение и требует последующей очистки/проверки фактической необходимости.

Статус ревизии: **продолжение разработки приостановлено до устранения архитектурных отклонений и синхронизации документации с фактическим деревом проекта.**
