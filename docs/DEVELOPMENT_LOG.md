# Журнал разработки

## Правила разработки
* После каждого запроса/ответа пользователя GPT проверяет текущую архитектуру программы и код, внимательно читает TECHNICAL_SPEC и DEVELOPMENT_LOG, после чего дает ответ пользователю в соответствии с полученными данными.
* Все изменения выполняются постепенно и осознанно.
* GPT не вносит изменения в исходный код. Самостоятельно изменяются только документы из `/docs`.
* На каждом ответе GPT выдаёт инструкции для пользователя: в каком файле (прописывая полный путь до файла) и что нужно добавить/удалить/изменить. Полная перезапись файлов без необходимости запрещена. Предпочтительный формат изменений — точечные исправления с указанием конкретного места изменения и требуемых действий.
* После добавления нового(ых) файла(ов) в файл PROGRAM_STRUCTURE заносятся информация согласно расположению файла(ов).
* После удаления файла(ов) информация об этом файле(ах) удаляется из файла PROGRAM_STRUCTURE.
* После каждого крупного этапа выполняются проверка работоспособности и запись в DEVELOPMENT_LOG (журнал разработки) по схеме:
```
## <текущая дата>
### <тема>
  <описание>
### <тема>
  <описание>
...
```
Повторно одна и та же дата не проставляется.
* Временные решения (реализации кода) записываются в DEVELOPMENT_LOG в разделе Временные решения. Если временное решение было заменено на другое временное решение, запись о нем должна быть изменена. Если временное решение было заменено на постоянное решение, то запись о нем должна быть удалена из раздела временных решений. 
* Технические данные программы, архитектурные правила записываются в TECHNICAL_SPEC в соответствующих разделах.
* Название и версия программы хранятся в единственном источнике конфигурации `src/app/AppInfo.h`. Они не дублируются в CMake, HTML, CSS, JavaScript или других слоях. CMake не является источником настроек приложения и при необходимости получает build-метаданные из других источников без создания второй копии значения.
* Наследование применяется там, где необходимо, для уменьшения дублирования кода (в том числе и в UI).
* UI-класс должен оставаться целостной единицей: визуальная структура, локальное состояние и логика взаимодействия пользователя не разделяются на отдельные файлы только ради размера файла или формального разделения UI и logic.
* Новый класс выделяется только при наличии самостоятельной ответственности, общего повторного поведения, отдельного контракта или отдельной технической границы.
* При добавлении нового(ых) файла(ов) в рабочий код запись в PROGRAM_STRUCTURE обновляется в соответствии с фактическим расположением файла(ов). При удалении файла(ов) соответствующие записи удаляются.
* Для повторяемых UI-ролей используются стабильные идентификаторы только там, где они действительно нужны для навигации, событий или композиции.
* UI-класс является целостной единицей: его визуальная структура и логика пользовательского взаимодействия находятся вместе, если относятся к одной ответственности.
* Класс не дробится на отдельные UI/logic файлы только ради размера. Новая C++-единица появляется при самостоятельной ответственности, реальном повторном использовании, собственном контракте или отдельной технической границе.
* Повторное использование проверяется прежде всего через наследование при совместимом контракте и общем поведении; composition применяется для независимых частей.
* Общая прикладная операция не дублируется между сущностями. Если Project, Content и Task используют один и тот же алгоритм, повторяемая часть получает общий типобезопасный механизм, а специализированные классы добавляют только различия.
* Компоновщики UI применяются для сборки действительно независимых частей, например меню и shell. Они не являются обязательным посредником между каждым классом страницы и каждым дочерним QWidget.
* Локализуемые тексты хранятся в единой таблице `localization.tsv`; in-memory каталоги создаются LocalizationService.
* Все пользовательские тексты, зависящие от языка, используют translation key; динамические параметры формируются единым механизмом локализации.
* Для меню используются MenuItem и MenuSection с явными параметрами. Они сохраняют собственную ответственность и не получают бизнес-логику.
* Структурные ID слотов интерфейса не являются идентификаторами переводов.
* Прикладной UI CreatorOS строится из C++/Qt Widgets-классов. QWidget является базовой единицей визуального поведения, но это не означает, что каждая деталь разметки должна быть отдельным классом.
* Визуальная система приложения централизована в CreatorStyle, Colors, Metrics и Icons; уникальная визуальная реализация находится в соответствующем QWidget-классе.
* Навигация строится через Qt signals/slots и контейнер страниц, а не через web route/DOM.
* C++ UI не содержит SQL и прямой работы с инфраструктурой; application services/domain/infrastructure отвечают за данные, бизнес-правила и технические процессы.

## План последовательной реализации и архитектурной стабилизации

Этот план является обязательным рабочим порядком перехода и развития native C++/Qt архитектуры CreatorOS.

Главный архитектурный принцип плана:

~~~text
целостный UI-класс
        ↓
наследование для совместимого is-a отношения
        +
composition для независимых частей
        ↓
application/domain/infrastructure для бизнес-правил
        ↓
интеграции и внешние технические процессы
~~~

План больше не предполагает создание максимального количества маленьких UI-компонентов. Новые классы появляются по ответственности и переиспользованию, а не по размеру файла.

### Правила выполнения каждого этапа

~~~text
1. Получить инструкции только для текущего этапа.
2. Пользователь вносит изменения в код по этим инструкциям.
3. Выполнить локальную сборку и, когда указано, запуск приложения.
4. При успешной проверке пользователь создаёт commit и выполняет push.
5. Перед следующим этапом проверяются последний commit, дерево проекта,
   TECHNICAL_SPEC, DEVELOPMENT_LOG и PROGRAM_STRUCTURE.
6. Если сборка неуспешна, следующий этап не начинается:
   сначала исправляется текущий этап.
7. После добавления нового файла его описание сразу добавляется
   в PROGRAM_STRUCTURE по фактическому пути.
8. После удаления файла его описание удаляется из PROGRAM_STRUCTURE.
~~~

GPT изменяет только документы из /docs. Исходный код, CMake, ресурсы и другие файлы проекта изменяет пользователь по выданным инструкциям.

- Наследование становится предпочтительным механизмом повторного использования при реальном is-a отношении, общем контракте и общем поведении.
- Composition используется для независимых и опциональных частей, а не как обязательный способ построения всех специализированных UI-классов.
- Для повторяемых прикладных операций запрещено копировать один и тот же алгоритм по сущностям. Перед появлением нескольких одинаковых реализаций определяется общий типобезопасный механизм.
- Перед продолжением Stage 8 проводится архитектурная ревизия EntityCard/ProjectCard и EntityDetails/ProjectDetailsPage.
- TECHNICAL_SPEC.md и PROGRAM_STRUCTURE.md синхронизированы с новым принципом.
