# Журнал разработки

## Правила разработки
* Перед ответом, изменением существующего кода необходимо проверить текущую архитектуру, TECHNICAL_SPEC и DEVELOPMENT_LOG.
* Все изменения выполняются постепенно и осознанно.
* Полная перезапись файлов без необходимости запрещена. Предпочтительный формат изменений — точечные исправления с указанием конкретного места изменения и требуемых действий.
* Архитектурные решения сначала обсуждаются, затем реализуются.
* После каждого крупного этапа выполняются проверка работоспособности и запись в DEVELOPMENT_LOG (журнал разработки) по схеме:
```
## <текущая дата>
### <тема>
  <описание>
### <тема>
  <описание>
...
```
Повторно одна и та же дата не проставляется.
* Временные решения (реализации кода) записываются в DEVELOPMENT_LOG в разделе Временные решения. Если временное решение было заменено на другое временное решение, запись о нем должна быть изменена. Если временное решение было заменено на постоянное решение, то запись о нем должна быть удалена из раздела временных решений. 
* Технические данные программы, архитектурные правила записываются в TECHNICAL_SPEC в соответствующих разделах.
* Название и версия программы хранятся в единственном источнике конфигурации и не дублируются в HTML, CSS, JavaScript или других слоях. Web UI получает эти значения через предусмотренный bridge.
* HTML описывает структуру интерфейса и расположение UI-блоков, но не содержит конкретных названий, текстов или назначений элементов.
* Для UI-блоков используются стабильные универсальные ID, не привязанные к их текущему смыслу или названию. Назначение блока определяется UI Registry и может быть изменено без изменения HTML-структуры.
* UI Registry является централизованным агрегатором конфигурации UI-ресурсов. Через него задаются тип блока, параметры построения, translation key, route, icon и другие необходимые параметры.
* Визуальное построение UI-блока выполняется отдельным переиспользуемым компонентом. Компонент получает параметры и отвечает только за построение и поведение представления.
* Локализуемые тексты хранятся в языковых каталогах и не дублируются в HTML, компонентах или registry.
* Все пользовательские тексты, зависящие от языка, должны обращаться к translation key. Формирование текста с динамическими параметрами выполняется через единый механизм локализации.
* Архитектура UI должна позволять заменить назначение существующего блока без изменения структуры HTML, если его структурная роль остаётся прежней.
* Новые элементы интерфейса по возможности добавляются как переиспользуемые строительные блоки, а не как уникальная разметка внутри страницы.

* Программа развивается как desktop application на стеке C++20 + Qt 6 + CMake + SQLite + HTML/CSS + минимальный JavaScript.
* C++ является основой текущей архитектуры; native-слой больше не является будущим вариантом, а является основной реализацией приложения.

* Все CSS-файлы хранятся только в `src/styles/` и его подкаталогах.
* Общие стили, дизайн-токены, типографика, темы и состояния хранятся централизованно.
* Уникальные (используемые единожды) стили компонента или страницы также хранятся в `src/styles/` в соответствующем разделе ответственности; CSS-файлы рядом с `.tsx` не создаются.
* Не создавать отдельные стили без необходимости.

* Сохранять уже принятые удачные решения.
* Не усложнять архитектуру заранее.
* Каждое новое расширение должно учитывать будущие возможности:
  * API-интеграции;
  * публикации на внешние площадки;
  * автоматизацию;
  * командную работу;
  * возможное подключение native-модулей.
