# Журнал разработки

## Правила разработки
* После каждого запроса/ответа пользователя GPT проверяет текущую архитектуру программы и код, внимательно читает TECHNICAL_SPEC и DEVELOPMENT_LOG, после чего дает ответ пользователю в соответствии с полученными данными.
* Все изменения выполняются постепенно и осознанно.
* GPT не вносит изменения в исходный код. Самостоятельно изменяются только документы из `/docs`.
* На каждом ответе GPT выдаёт инструкции для пользователя: в каком файле (прописывая полный путь до файла) и что нужно добавить/удалить/изменить. Полная перезапись файлов без необходимости запрещена. Предпочтительный формат изменений — точечные исправления с указанием конкретного места изменения и требуемых действий.
* После каждого крупного этапа выполняются проверка работоспособности и запись в DEVELOPMENT_LOG (журнал разработки) по схеме:
```
## <текущая дата>
### <тема>
  <описание>
### <тема>
  <описание>
...
```
Повторно одна и та же дата не проставляется.
* Временные решения (реализации кода) записываются в DEVELOPMENT_LOG в разделе Временные решения. Если временное решение было заменено на другое временное решение, запись о нем должна быть изменена. Если временное решение было заменено на постоянное решение, то запись о нем должна быть удалена из раздела временных решений. 
* Технические данные программы, архитектурные правила записываются в TECHNICAL_SPEC в соответствующих разделах.
* Название и версия программы хранятся в единственном источнике конфигурации `src/app/AppInfo.h`. Они не дублируются в CMake, HTML, CSS, JavaScript или других слоях. CMake не является источником настроек приложения и при необходимости получает build-метаданные из других источников без создания второй копии значения.
* Наследование применяется там, где необходимо, для уменьшения дублирование кода (в том числе и в UI).
* Для повторяемых UI-ролей используются стабильные универсальные идентификаторы компонентов/слотов, не привязанные к конкретному тексту или текущему смыслу. Их назначение задаётся компоновщиком UI.
* Визуальное построение UI-блока выполняется отдельным переиспользуемым компонентом. Компонент получает параметры и отвечает только за построение и поведение представления.
* Локализуемые тексты хранятся в единой таблице `localization.tsv` и не дублируются в UI-компонентах. In-memory каталоги создаются LocalizationService.
* Все пользовательские тексты, зависящие от языка, должны обращаться к translation key. Формирование текста с динамическими параметрами выполняется через единый механизм локализации.
* Архитектура UI должна позволять заменять конкретную реализацию компонента без изменения application/domain слоя, если его публичная роль и контракт сохраняются.
* Новые элементы интерфейса по возможности добавляются как переиспользуемые строительные блоки, а не как уникальная разметка внутри страницы.
* UI-компонент является независимым строительным блоком. Он знает только свою структурную роль и способ визуального построения и не знает конкретных данных, текстов, иконок и назначений.
* Компоновщик UI отвечает за сборку интерфейса из компонентов и передаёт компонентам конкретные параметры.
* Для меню используются независимые компоненты MenuItem и MenuSection. MenuItem получает icon, text, route и другие параметры; MenuSection получает параметры своей секции. Компоненты не знают, что именно означает переданный текст или иконка.
* Структурные ID слотов интерфейса не являются идентификаторами переводов. Структурный ID указывает место/роль блока, а text ID указывает на локализуемую единицу.
* Повторяющееся локализуемое слово или словоформа хранится один раз и переиспользуется через один text ID. Полные фразы, для которых важен контекст языка, имеют собственный отдельный text ID.
* Источником локализации является единая таблица `localization.tsv`. Языковые каталоги не являются отдельными исходными файлами: они формируются в памяти из актуальной таблицы при запуске программы. Добавление языка, строки или изменение перевода автоматически отражается в соответствующем каталоге без ручной синхронизации.
* Прикладной UI CreatorOS строится из C++/Qt Widgets-компонентов. QWidget является базовой единицей визуального поведения, а страницы являются композициями компонентов.
* Визуальная система приложения централизована в `CreatorStyle : QProxyStyle`, классах `Colors` / `Metrics` и общем механизме `Icons`. Специализированная отрисовка выполняется через QPainter.
* MenuItem и MenuSection являются независимыми визуальными компонентами. Они не знают конкретного текста, иконки и назначения; конкретные параметры передаются компоновщиком UI.
* Навигация строится через Qt signals/slots и контейнер страниц (например, QStackedWidget), а не через web route/DOM.
* C++ UI не содержит SQL, сетевые вызовы и бизнес-правила; за данные и действия отвечают application services/domain/infrastructure.
* QWebEngineView и QWebChannel считаются специализированными, а не основными UI-компонентами. Их использование фиксируется только для конкретного web-сценария.
* Рефакторинг UI выполняется строго по последовательному плану из раздела "План последовательного рефакторинга UI" настоящего документа. Следующий этап начинается только после проверки текущего этапа, успешной сборки, commit/push пользователя и проверки нового состояния репозитория.

* Программа развивается как desktop application на стеке C++20 + Qt 6 Widgets + CMake + SQLite.
* C++ и Qt Widgets являются основной реализацией приложения и визуального интерфейса. HTML/CSS/JavaScript и QWebEngine/WebChannel используются только в специализированных web-сценариях при реальной необходимости.

* Сохранять уже принятые удачные решения.
* Не усложнять архитектуру заранее.
* Каждое новое расширение должно учитывать будущие возможности:
  * API-интеграции;
  * публикации на внешние площадки;
  * автоматизацию;
  * командную работу;
  * платформенные adapters там, где они действительно необходимы.


## План последовательного рефакторинга UI

Этот план является обязательным рабочим порядком перехода от текущего переходного web UI к целевой native Qt Widgets-архитектуре. Этапы выполняются последовательно и не перескакиваются без отдельного архитектурного решения, зафиксированного в TECHNICAL_SPEC.

### Правила выполнения каждого этапа

~~~text
1. Получить инструкции только для текущего этапа.
2. Пользователь вносит изменения в код по этим инструкциям.
3. Выполнить локальную сборку и, когда указано, запуск приложения.
4. При успешной проверке пользователь создаёт commit и выполняет push.
5. Перед следующим этапом проверяются последний commit, дерево проекта,
   TECHNICAL_SPEC и DEVELOPMENT_LOG.
6. Если сборка неуспешна, следующий этап не начинается:
   сначала исправляется текущий этап.
~~~

GPT изменяет только документы из /docs. Исходный код, CMake, ресурсы и другие файлы проекта изменяет пользователь по выданным инструкциям.

Статус: **завершён**

Создать фундамент:
~~~text

Metrics

Icons
~~~

Результат: централизованные визуальные токены и единая точка глобального стиля.

#### Этап 2 — система локализации
Статус: **завершён**

Создать:
~~~text
LocalizationService
resources/localization/localization.tsv
resources/localization.qrc
~~~

Результат: единый исходник переводов и формирование каталогов языков в памяти.

#### Этап 3 — базовые native UI-компоненты
Статус: **завершён**

Последовательно создать и проверить:

MenuSection

~~~

Компоненты получают параметры извне и не знают своего конкретного назначения.

#### Этап 4 — native AppShell
Статус: **завершён**

Создать:
~~~text
AppShell

~~~

Подключить LocalizationService к shell и собрать меню из компонентов.

Создать:
~~~text

QStackedWidget

~~~

Перевести переходы между разделами с web route/DOM на Qt signals/slots.

Перевести соответствующие UI на native Qt и подключить к C++ application services.

#### Этап 13 — удаление переходного web UI
Только после того, как все необходимые прикладные экраны и сценарии переведены:

~~~text

удалить web-only ресурсы и старые web-localization files
~~~

При этом QWebEngine/WebChannel могут остаться только в отдельно выделенном специализированном web-модуле, если к моменту завершения миграции такая функция действительно существует.

release build

Linux
navigation
localization
resource loading
window behavior
license/package contents
~~~

После стабилизации обновляются документация, USER_GUIDE и список third-party компонентов.

### Граница между UI-рефакторингом и развитием продукта

Рефакторинг UI не изменяет предметную модель и не должен одновременно менять бизнес-правила без необходимости. Сначала переносится визуальная реализация, затем добавляется новая функциональность.
