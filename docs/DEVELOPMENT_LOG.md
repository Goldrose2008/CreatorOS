# Журнал разработки CreatorOS

## Архитектурное правило:
	1. CreatorOS — система управления полным циклом создания контента: от идеи до публикации и анализа результата.
	2. Центральная бизнес-сущность приложения — Project (Проект).
	3. Один Project имеет ровно один основной Content.
	4. Дополнительного Content у Project может быть 0..N.
	5. Несколько связанных выпусков оформляются как отдельные Projects; сущность Series будет реализована позднее.
	6. Project объединяет основной и дополнительный Content, Tasks, Assets / Materials, Publications и Analytics.
	7. Связи между сущностями хранятся один раз; не следует дублировать одну и ту же связь в нескольких сущностях без необходимости.
	8. Publication связывается с Content, поэтому отдельный project_id в Publication не нужен.
	9. Account выбирается системой/пользователем из подключённых аккаунтов; account_id не вводится вручную.
	10. entity_type используется как техническое понятие на уровне приложения для универсальных компонентов, навигации, действий и автоматизации; одинаковое поле entity_type без необходимости не хранится в каждой таблице SQLite.
	11. Системные идентификаторы и даты не редактируются пользователем вручную.
	12. Связь Content с Project и техническая роль Content main/additional управляются системой, а не являются обычными пользовательскими полями.
	13. Статусы сущностей изменяются через предусмотренные действия и процессы, а не редактируются как обычные поля.
	14. Прогресс Project и Content рассчитывается системой; пользователь не вводит процент прогресса вручную.
	15. Приоритет Project не хранится; приоритет задаётся на уровне Content.
	16. Приоритет Task не хранится как обычное ручное поле; в будущем он рассчитывается системой на основании контекста, сроков и влияния задачи.
	17. production_deadline_at рассчитывается системой, а planned_release_at относится к планируемому выходу основного контента.
	18. User, Team, Platform, Account, Publication, Analytics, Automation, Series и другие сущности строятся как отдельные модули без смешивания их ответственности.
	19. UI-компоненты должны быть универсальными и не зависеть от конкретной бизнес-сущности.
	20. Конфигурация сущности не должна зависеть от UI-компонентов; используются нейтральные типы из src/types/.
	21. Страницы координируют данные, состояния и действия, а не реализуют напрямую низкоуровневую работу с БД.
	22. Работа с SQLite выполняется через сервисы; страницы и UI-компоненты не обращаются к SQLite напрямую.
	23. Универсальные компоненты располагаются отдельно от компонентов конкретных сущностей.
	24. Каждый компонент имеет собственную область ответственности; большие страницы по мере роста выделяются на подкомпоненты.
	25. Стили компонентов и страниц изолируются через CSS Modules; глобальные стили используются только для базовых правил и дизайн-токенов.
	26. Общие визуальные значения хранятся в системе design tokens в src/styles/theme.css.
	27. Внутри src/components не используются barrel-файлы index.ts; компоненты импортируются напрямую из своих директорий.
	28. Модели, типы, конфигурация, сервисы, компоненты и страницы сохраняют направленное разделение ответственности и не создают циклических зависимостей.
	29. Один и тот же универсальный механизм должен по возможности использоваться для Project, Content, Publication, Task, Asset и других сущностей вместо создания дублирующей реализации.
	30. Изменение структуры SQLite сопровождается увеличением версии схемы и синхронным обновлением контроля версии в приложении.
	31. После сообщения пользователя о том, что коммит запушен и можно продолжать работу, перед предложением следующего шага необходимо проверить последний коммит и актуальное состояние проекта в GitHub: дерево файлов, наличие/отсутствие файлов, ключевые связи между слоями и соответствие текущей архитектуре.

	32. Компонент в CreatorOS является законченной функциональной единицей: он может содержать собственную визуальную часть, состояние и логику поведения, необходимые именно для его ответственности.
	33. Универсальные компоненты используются как строительные блоки («лего»): их поведение определяется входными данными, параметрами и обработчиками событий, а не копированием одинаковой логики в месте использования.
	34. Компоненты конкретных сущностей могут собираться из универсальных компонентов и при этом содержать связанную с сущностью логику, включая взаимодействие нескольких внутренних UI-частей между собой.
	35. Страницы и контейнеры отвечают прежде всего за связывание компонентов между собой и за сценарии уровня страницы; одинаковая функциональность не должна дублироваться в разных страницах или обработчиках.
	36. Повторяющийся сценарий взаимодействия, например подтверждение действия, должен иметь единый переиспользуемый механизм с передачей ему нужных данных и действия, а не отдельную копию одинаковых функций в каждой сущности.

## Временное решение:
	1. Система статусов проекта пока временно находится в src/config/entities/projectConfig.ts; после проектирования общей системы статусов она будет вынесена в отдельный универсальный модуль, после чего временное решение удалить.
	2. Во время прототипирования изменение версии схемы SQLite приводит к пересозданию тестовой БД; после появления реальных пользовательских данных этот механизм будет заменён последовательными миграциями.
	3. В MVP фактически используется один пользователь; структура owner_id и assigned_user_id уже допускает дальнейшую командную работу.
	4. Series пока отложена и не реализована как отдельная сущность.
	5. Platform / Account / Publication, Analytics, Team, AI и расширенная автоматизация пока являются отложенными модулями согласно текущему этапу разработки.
	6. Страницы Dashboard, Tasks, Planning, Library и Analytics пока содержат заготовки и будут превращены в полноценные модули по мере разработки.
	7. SettingsPlaceholder.tsx временно используется для ещё не реализованных разделов настроек и должен быть удалён/заменён после реализации соответствующих разделов.
	8. Предложенный вариант ConfirmModal, при котором в каждой странице отдельно реализуются одинаковые функции открытия, подтверждения и завершения удаления, признан промежуточным и не соответствует принятой модели компонентной архитектуры; при дальнейшей реализации механизма подтверждения он должен быть заменён единым компонентным механизмом.
