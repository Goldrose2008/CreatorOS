# Технический документ проекта CreatorOS

**Рабочее название:** CreatorOS  
**Версия приложения:** 0.1  
**Версия документа:** 1.0  
**Статус:** Новый архитектурный этап  
**Тип продукта:** Desktop-приложение  
**Целевые платформы:** Windows / macOS / Linux

## Архитектурные правила:

	1. CreatorOS — система управления полным циклом создания контента: от идеи до публикации и анализа результата.
	2. Центральная бизнес-сущность CreatorOS — Project (Проект).
	3. Один Project представляет одну единицу производства контента.
	4. Один Project имеет ровно один основной Content.
	5. Project может иметь 0..N дополнительных Content.
	6. Несколько связанных выпусков являются отдельными Projects; Series является отдельной будущей сущностью.
	7. Project объединяет основной и дополнительный Content, Tasks, Assets / Materials, Publications и Analytics.
	8. Связи между сущностями хранятся один раз и не дублируются без необходимости.
	9. Publication относится к Content; отдельный project_id в Publication не требуется.
	10. Account выбирается из подключённых аккаунтов; account_id не вводится пользователем вручную.
	11. Системные идентификаторы, даты создания и технические значения не редактируются пользователем вручную.
	12. Связь Content с Project и роль Content main/additional управляются системой.
	13. Статусы сущностей изменяются через предусмотренные действия и процессы, а не произвольным вводом.
	14. Прогресс Project и Content рассчитывается системой; пользователь не вводит процент вручную.
	15. Приоритет хранится на уровне Content; отдельный приоритет Project не используется.
	16. Приоритет Task в дальнейшем рассчитывается системой на основании контекста, сроков и влияния задачи.
	17. production_deadline_at рассчитывается системой; planned_release_at относится к планируемому выходу основного контента.
	18. User, Team, Platform, Account, Publication, Analytics, Automation, Series и другие сущности имеют отдельные области ответственности.
	19. Доступ к SQLite выполняется только через слой сервисов/репозиториев; UI-компоненты и страницы не работают с БД напрямую.
	20. Страницы являются точками сборки сценариев и связей между компонентами; логика конкретной сущности не должна без необходимости размазываться по страницам.
	21. Компонент CreatorOS является законченной функциональной единицей и может содержать собственный UI, состояние и связанную с ним логику.
	22. Универсальные компоненты являются переиспользуемыми строительными блоками и не содержат бизнес-логики конкретной сущности.
	23. Для повторяющихся сущностных компонентов применяется «принцип ООП»: общий функциональный шаблон реализуется один раз в базовом компоненте, а конкретные компоненты сущностей наследуются от него и используют его свойства и методы.
	24. Для карточек используется базовый EntityCard. ProjectCard, ContentCard, TaskCard, AssetCard, PublicationCard и другие аналогичные компоненты наследуются от EntityCard.
	25. EntityCard содержит общий визуальный шаблон карточки, общие свойства, общие методы и общие правила поведения.
	26. EntityCard предоставляет точку инициализации общего шаблона InitialCard(...). Конкретный Card передаёт в неё данные, параметры и свои действия.
	27. Общие функции, относящиеся к карточке сущности, принадлежат EntityCard и наследуются конкретными Card. Например форматирование даты реализуется один раз в базовом компоненте через FormatDate (концептуально formatDate).
	28. Конкретный Card содержит только данные и логику своей сущности. При необходимости методы базового Card могут переопределяться через стандартный механизм C# наследования.
	29. Для подробных представлений используется базовый EntityDetails. ProjectDetails, ContentDetails, TaskDetails, AssetDetails, PublicationDetails и другие аналогичные компоненты наследуются от EntityDetails.
	30. EntityDetails содержит общий визуальный шаблон Details, общие свойства, общие методы и точку инициализации InitialDetails(...).
	31. Конкретный Details содержит логику своей сущности, загружает и изменяет её данные и передаёт представление в InitialDetails(...).
	32. «Принцип ООП» применяется и к другим повторяющимся функциональным механизмам, если между объектами существует естественная общая базовая ответственность.
	33. ConfirmModal является единым самодостаточным объектом подтверждения. Приложение использует единый механизм/экземпляр, а публичная точка запуска ConfirmModal.StartEvent(...) принимает заголовок, описание, callback/event и дополнительные параметры при необходимости.
	34. Callback ConfirmModal.StartEvent(...) передаётся лениво, например () => DeleteProject(id), и выполняется только после подтверждения пользователя.
	35. Страницы и сущности не дублируют состояние открытия, закрытия и подтверждения ConfirmModal.
	36. CSS Modules и React-специфическая архитектура не используются в новой версии CreatorOS.
	37. Визуальное оформление строится средствами Avalonia Styles и ресурсов. Стилевые файлы хранятся централизованно в src/Styles/ и распределяются по ответственности.
	38. Общий визуальный стиль EntityCard определяется один раз и не копируется в ProjectCard, ContentCard, TaskCard и другие наследники.
	39. Общий визуальный стиль EntityDetails определяется один раз и не копируется в конкретные Details.
	40. Отдельный стиль конкретной сущности создаётся только при доказанной уникальной визуальной ответственности.
	41. Не создаются отдельные файлы только для механического разделения UI и логики. Выделение выполняется только при наличии самостоятельной ответственности или реального повторного использования.
	42. Не используются чрезмерно абстрактные прослойки. Универсальность должна давать реальное повторное использование.
	43. Конфигурация сущностей не зависит от визуальных классов.
	44. Модели предметной области, сервисы, UI-компоненты и страницы сохраняют направленное разделение ответственности и не создают циклических зависимостей.
	45. Имена классов и файлов должны сразу показывать их роль: <Entity>Card, <Entity>Details, <Entities>Page и аналогичные формы.
	46. После каждого завершённого этапа фактически выполненная работа заносится в docs/DEVELOPMENT_LOG.md; при необходимости обновляется docs/USER_GUIDE.md.
	47. docs/TECHNICAL_SPEC.md является источником постоянных архитектурных правил; docs/DEVELOPMENT_LOG.md — журналом выполненных этапов и перечнем временных решений.
	48. Перед каждым новым архитектурным или кодовым решением необходимо опираться на актуальные docs/TECHNICAL_SPEC.md, docs/DEVELOPMENT_LOG.md и фактическое состояние проекта.
	49. После сообщения пользователя о запушенном коммите и готовности продолжать необходимо проверить последний коммит и актуальное состояние всего проекта в GitHub: дерево файлов, наличие/отсутствие файлов, ключевые связи и соответствие текущей архитектуре.
	50. Основной UI-язык новой версии CreatorOS — C# с .NET 10 LTS и Avalonia UI. Классическая модель наследования C# является допустимым и предпочтительным механизмом для базовых сущностных компонентов.
	51. Новая версия не использует React, TypeScript, Vite или Tauri.
	52. Avalonia UI используется как кроссплатформенный desktop UI-фреймворк для Windows, macOS и Linux.
	53. Используются возможности Avalonia Core/Controls, не требующие платных профессиональных инструментов. Платные инструменты и дополнительные коммерческие компоненты не являются обязательной частью архитектуры.
	54. Стандартная версия .NET для проекта — .NET 10 LTS.
	55. Доступ к SQLite в новой версии выполняется через Microsoft.Data.Sqlite; EF Core добавляется только при появлении реальной необходимости в ORM.
	56. Новая версия строится как отдельный проект с чистой кодовой базой; архитектура старого React/Tauri-прототипа не переносится автоматически.
	57. Бизнес-модель и уже принятые правила предметной области сохраняются при смене технологического стека, если в новой спецификации явно не принято обратное решение.

## Технологический стек

### Основной стек

- Язык: C#
- Платформа: .NET 10 LTS
- UI: Avalonia UI 12.1.3
- База данных: SQLite
- Доступ к SQLite: Microsoft.Data.Sqlite
- Система сборки: dotnet CLI / SDK
- Среда разработки: Visual Studio Code или Visual Studio
- Система контроля версий: Git + GitHub

.NET 10 выбран как активная LTS-версия с поддержкой до 14 ноября 2028 года. Avalonia 12.1.3 является актуальной версией на момент начала нового этапа и поддерживает desktop-приложения Windows, macOS и Linux.

### Принцип выбора UI-технологии

Критическим требованием является возможность строить архитектуру на классах, наследовании, переопределении методов и событиях без ограничений, характерных для React hooks и функциональной модели компонентов.

В новой версии CreatorOS базовые сущностные UI-компоненты строятся как C#-классы:

```text
EntityCard
    ↑
ProjectCard
ContentCard
TaskCard
AssetCard
PublicationCard
...
```

и:

```text
EntityDetails
    ↑
ProjectDetails
ContentDetails
TaskDetails
AssetDetails
PublicationDetails
...
```

### Стиль разработки

Главный объект приложения — объект с собственной ответственностью.

Базовый компонент предоставляет:

- общий UI;
- общие свойства;
- общие методы;
- общие события;
- базовое поведение.

Компонент-наследник предоставляет:

- данные конкретной сущности;
- логику конкретной сущности;
- уникальные действия;
- переопределения базового поведения при необходимости.

XAML/Avalonia Styles допускаются как средство декларативного описания оформления, но они не заменяют объектную модель компонентов.

## 1. Назначение приложения

CreatorOS предназначен для управления полным циклом создания контента:

```text
Идея
↓
Проект
↓
Создание контента
↓
Производство
↓
Подготовка публикации
↓
Публикация
↓
Аналитика
```

Главная цель:

> CreatorOS должен брать на себя рутинную организацию процесса и позволять пользователю сосредоточиться на содержательных решениях.

## 2. Основная модель предметной области

```text
Project
├── 1 Main Content
├── 0..N Additional Content
├── Tasks
├── Assets / Materials
├── Publications
└── Analytics
```

## 3. Project

Project является центральной бизнес-сущностью.

Основные данные:

```text
id
name
description
owner_id
planned_release_at
status
progress
created_at
updated_at
```

Project не хранит отдельный приоритет.

## 4. Content

Content является самостоятельной сущностью, находящейся внутри Project.

Основные данные:

```text
id
project_id
content_type_id
content_role
name
description
priority
production_deadline_at
status
progress
created_at
updated_at
```

Роли:

```text
main
additional
```

Для одного Project допускается только один Content с ролью main.

## 5. ContentType

ContentType является справочником типов контента.

Примеры:

```text
Видео
Short
Статья
```

Пользователь может добавлять и изменять типы контента через Settings.

## 6. Task

Task имеет контекст родительской сущности.

Основная модель:

```text
parent_id
parent_type
parent_task_id
```

Это позволяет связывать задачу с Project, Content или другой поддерживаемой сущностью без создания отдельной таблицы связей для каждого типа объекта.

## 7. Publication

Publication относится к конкретному Content и конкретному Account.

Основные направления данных:

```text
content_id
platform_id
account_id
status
scheduled_at
published_at
external_id
external_url
title
description
publication_data
error_message
```

## 8. Platform и Account

Platform описывает площадку публикации.

Account представляет конкретный аккаунт/канал пользователя на этой площадке.

Связь:

```text
Platform
    ↓
Account
    ↓
Publication
    ↓
Content
```

## 9. EntityCard

EntityCard — базовый визуальный и функциональный класс для карточек сущностей.

Он содержит:

- общий визуальный шаблон;
- общие поля карточки;
- общие действия;
- общие методы;
- FormatDate;
- InitialCard(...).

Принцип использования:

```text
EntityCard
    │
    ├── InitialCard(...)
    ├── FormatDate(...)
    └── общий UI
          ↑
          │
      ProjectCard
      ContentCard
      TaskCard
      ...
```

## 10. EntityDetails

EntityDetails — базовый класс подробного представления сущности.

Он содержит:

- общий UI;
- общую структуру Details;
- общие свойства;
- общие методы;
- InitialDetails(...).

## 11. ConfirmModal

ConfirmModal является единственным общим механизмом подтверждения действий.

Концептуальный вызов:

```csharp
ConfirmModal.StartEvent(
    "Удаление проекта",
    "Удалить проект «Мой проект»?",
    () => DeleteProject(project.Id)
);
```

StartEvent не знает, какое именно действие выполняется. Он отвечает только за:

```text
показ подтверждения
↓
ожидание решения пользователя
↓
отмена ИЛИ выполнение callback
```

## 16. ООП-архитектура CreatorOS

Основной принцип:

> Общая функциональность реализуется один раз в базовом классе и наследуется конкретными объектами.

Пример:

```csharp
class EntityCard
{
    protected void InitialCard(...);
    protected string FormatDate(...);
}

class ProjectCard : EntityCard
{
    ...
}

class ContentCard : EntityCard
{
    ...
}
```

Для переопределяемого поведения используются стандартные механизмы C#:

```csharp
virtual
override
protected
public
```

Наследование применяется там, где объект действительно является специализированной версией базового объекта.

## 20. Кроссплатформенность

Целевые desktop-платформы:

```text
Windows
macOS
Linux
```

Одна кодовая база должна использовать общие доменные модели, сервисы и UI-компоненты.

Platform-specific код выделяется только там, где без него невозможно использовать системную функцию.

## 21. Лицензирование

Для новой версии используется Avalonia UI как основной UI-фреймворк.

Avalonia framework распространяется по MIT-лицензии. Профессиональные инструменты и дополнительные продукты Avalonia не являются обязательной частью проекта и не должны становиться архитектурной зависимостью.

Перед выпуском продукта дополнительно проверяются лицензии всех сторонних NuGet-пакетов и включается необходимая информация о лицензиях в дистрибутив.

## 22. Что не переносится из старого прототипа

Старый React/Tauri-прототип не является базой новой кодовой реализации.

Не переносится автоматически:

```text
React
TypeScript
Vite
Tauri
CSS Modules
React Router
старое расположение компонентов
старые page-level confirmation states
старые промежуточные abstractions
```

Переносится на уровне требований:

```text
модель Project
модель Content
модель Task
отношения сущностей
правила статусов
правила прогресса
бизнес-правила
UX-цели
идеи автоматизации
```

## 24. Главный принцип проекта

CreatorOS строится вокруг процесса производства контента, а не вокруг отдельных экранов.

Главная цепочка:

```text

↓
Content
↓
Production
↓
Publication
↓
```

А программная архитектура строится вокруг законченных объектов:

```text
Base Component
↓
Specialized Component
↓
Page
↓
Service
↓

```

Это позволяет использовать сильные стороны объектно-ориентированного подхода C# и одновременно сохранять единый кроссплатформенный desktop UI.
