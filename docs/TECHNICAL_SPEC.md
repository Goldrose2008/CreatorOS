# Технический документ проекта CreatorOS

**Рабочее название:** CreatorOS
**Версия приложения:** 0.1
**Версия документа:** 0.2
**Статус:** Проектирование
**Тип продукта:** Desktop-приложение
**Платформа:** Windows / macOS / Linux

### Технологический стек

* Frontend: React + TypeScript
* Desktop Framework: Tauri 2
* Backend Core: Rust
* Database: SQLite
* Version Control: Git + GitHub


## 1. Назначение приложения

### 1.1 Общая идея

Приложение предназначено для организации полного цикла создания контента:

```text
Идея
↓
Планирование
↓
Создание
↓
Подготовка публикации
↓
Публикация
↓
Анализ результата
↓
Улучшение следующих проектов
```

Приложение объединяет:
* контент-план;
* управление проектами;
* управление задачами;
* автоматизацию процессов;
* подготовку и публикацию контента;
* сбор аналитики;
* работу команды.

Главная идея продукта:

> CreatorOS — система управления процессом превращения идеи в опубликованный контент.

## 2. Основной принцип архитектуры

### 2.1 Центральная сущность — Проект

**Проект** представляет собой одну единицу производства контента.

Например:
Проект
«Как создать приложение автора»

Основной контент
- Видео

Дополнительный контент
- Short
- Статья
- Пост

#### Важное правило

> Один проект имеет ровно один основной контент.

Дополнительного контента может быть: 0..N

То есть:

```text
Проект
├── Основной контент — 1
├── Дополнительный контент — 0..N
├── Задачи
├── Материалы
├── Публикации
└── Аналитика
```

### 2.2 Серия

Если несколько видео относятся к одной серии, это несколько самостоятельных проектов:

```text
Серия «Создание приложения»
│
├── Проект 1
│   └── Основной контент: Видео
│
├── Проект 2
│   └── Основной контент: Видео
│
└── Проект 3
    └── Основной контент: Видео
```

Сущность **Серия** будет реализована позднее как дополнительная функциональность.

## 4. Сущности системы

### 4.1 Пользователь

Человек, использующий приложение.

Поля:

```text

name
email
avatar
created_at
updated_at
```

Некоторые пользовательские настройки хранятся отдельно в системе настроек приложения.
### 4.2 Команда

Группа пользователей, работающих над контентом.

Функциональность командной работы не входит в MVP.

Предварительная структура:

```text
teams
team_members
```

Команда будет реализована позднее.
### 4.3 Платформа

Площадка, на которой может быть опубликован контент.

Примеры:

```text
YouTube
Telegram
VK
RuTube
Boosty
Сайт
```

Платформа описывает технические особенности сервиса, но не является конкретным каналом пользователя.

Предварительная структура:

```text
platforms
```

Поля:

```text
id
name
platform_type
settings
created_at
updated_at
```
### 4.4 Аккаунт / канал

Конкретный аккаунт пользователя на определённой платформе.

Например:

```text
YouTube
└── Канал CreatorOS

YouTube
└── Другой канал

Telegram
└── Канал CreatorOS
```

Предварительная структура:

```text
accounts
```

Поля:

```text
id
platform_id
name
url
settings
created_at
updated_at
```

Аккаунт выбирается при создании публикации.

Пользователь не вводит `account_id` вручную.

Если на выбранной платформе подключён только один аккаунт, система может выбрать его автоматически.

## 5. Проект

### 5.1 Назначение

Проект — центральная сущность приложения.

Проект объединяет весь процесс производства одного основного результата.

Пример:

```text
Проект:
«Как создать приложение автора»

Основной контент:
Видео

Дополнительный контент:
Short
Пост
Статья

Задачи:
...

Материалы:
...

Публикации:
YouTube
VK
RuTube
```

### 5.2 Поля проекта

#### `id`

Уникальный идентификатор.
Системное поле.
Пользователь не изменяет его.

#### `name`

Название проекта.
Редактируется пользователем.

#### `description`

Описание проекта.
Необязательное поле.
Редактируется пользователем.

#### `owner_id`

Ответственный за проект.
Выбирается пользователем из доступных пользователей.
В MVP фактически будет использоваться для одного пользователя, но структура сразу допускает расширение до команды.

#### `planned_release_at`

Планируемая дата выхода основного контента.
Это именно дата выхода проекта / основного контента.
Изменяет система при автоматическом создании/применении шаблона и пользователь вручную.
Она отличается от дат отдельных публикаций:

```text
Проект
Планируемая дата выхода: 15 ноября

Публикация YouTube:
15 ноября, 10:00

Публикация VK:
15 ноября, 12:00
```

На основании `planned_release_at` система в будущем сможет рассчитывать производственные сроки.

#### `status`

Статус проекта.
Статус не является обычным редактируемым полем.
Изменение происходит через предусмотренные действия системы.

Например:
```text
Создать проект
↓
Взять в работу
↓
Поставить на паузу
↓
Завершить
↓
Архивировать
```

Конкретный набор статусов и действий будет определён отдельно.

#### `progress`

Процент готовности проекта.
Рассчитывается системой.
Пользователь не вводит значение вручную.
Прогресс может вычисляться на основании состояния задач, этапов производства и готовности связанного контента.

#### `created_at`

Дата и время создания проекта.
Системное поле.

#### `updated_at`

Дата и время последнего изменения проекта.
Системное поле.

## 6. Технический тип сущности

Система должна понимать, с какой сущностью работает интерфейс, автоматизация или универсальная карточка.

Для этого используется техническое понятие:

```text
entity_type
```

Примеры:

```text
project
content
publication
task
asset
```

`entity_type` не является бизнес-параметром, который пользователь заполняет вручную.

Важно:

> Не следует без необходимости хранить одинаковое поле `entity_type` в каждой таблице SQLite.

Тип сущности уже определяется структурой данных:

```text
projects → project
content_items → content
publications → publication
tasks → task
```

На уровне приложения `entity_type` может использоваться для:

* универсальных карточек;
* навигации;
* действий;
* автоматизаций;
* контекстных команд;
* обработки разных типов объектов одним интерфейсом.

## 7. Контент

### 7.1 Назначение

Контент — материал, создаваемый внутри проекта.

Примеры:

```text
Видео
Short
Статья
Пост
Изображение
Аудио
Другие типы
```

### 7.2 Роли контента

Контент бывает:

#### Основной

Главный результат проекта.
В каждом проекте ровно один основной контент.

#### Дополнительный

Материалы, создаваемые в рамках проекта дополнительно к основному.

Например:

```text
Проект
│
├── Основной контент
│   └── Видео
│
└── Дополнительный контент
    ├── Short 1
    ├── Short 2
    ├── Статья
    └── Пост
```

### 7.3 Поля контента

#### `id`

Уникальный идентификатор.
Системное поле.

#### `project_id`

Проект, которому принадлежит контент.
Контент не должен свободно переноситься между проектами через обычное редактирование поля.
Связь устанавливается системой при создании контента.
В будущем, если потребуется перенос, это должно быть отдельным действием: Переместить в другой проект

#### `content_type_id`

Тип контента.

Примеры:

```text
Видео
Short
Статья
Пост
Подкаст
Изображение
Аудио
```

Поле доступно для изменения пользователю.
При изменении типа система должна учитывать связанные workflow, шаблоны, допустимые платформы и другие зависимости.

#### `content_role`

Техническая роль:

```text
main
additional
```

Пользователь не редактирует это поле напрямую.
Оно необходимо системе для отображения:

```text
Основной контент
Дополнительный контент
```

#### `name`

Название контента.
Редактируется пользователем.

#### `description`

Описание контента.
Необязательное поле.
Редактируется пользователем.

#### `priority`

Приоритет контента.
Редактируется пользователем вручную.

Пример:

```text
Низкий
Обычный
Высокий
Критический
```

Конкретный набор значений будет определён справочником.
Приоритет контента используется системой при расчёте приоритетности связанных задач.

#### `production_deadline_at`

Внутренний срок завершения производства контента.
Рассчитывается системой.

В отличие от `planned_release_at`:

```text
planned_release_at → когда должен выйти контент

production_deadline_at → когда производство должно быть завершено
```

Расчёт в будущем может учитывать:
* планируемую дату выхода;
* тип контента;
* workflow;
* длительность этапов;
* автоматизации.

#### `status`

Статус контента.
Изменяется через предусмотренные действия и процессы системы.

#### `progress`

Процент готовности контента.
Рассчитывается системой.

#### `created_at`

Дата создания.
Системное поле.

#### `updated_at`

Дата последнего изменения.
Системное поле.

## 8. Приоритеты и задачи

### 8.1 Основной принцип

Приоритет не должен превращаться в дополнительную рутинную работу пользователя.

Поэтому на первом этапе:

```text
Приоритет проекта        — нет
Приоритет контента       — да
Приоритет задачи         — не хранится вручную
```

Пользователь один раз задаёт важность контента.
Система использует эту информацию для определения приоритетности связанных задач.

### 8.2 Вычисляемый приоритет задачи

В будущем приоритет задачи может рассчитываться автоматически с учётом:

```text
приоритета контента
+
срока задачи
+
просрочки
+
состояния задачи
+
влияния задачи на производство
+
блокировки следующих этапов
```

Конкретная формула расчёта будет разработана позже.

## 14. Публикация

### 14.1 Назначение

Публикация — это конкретное размещение определённого контента на определённом аккаунте определённой платформы.

Связь:

```text
Контент
│
├── Публикация → YouTube / аккаунт 1
├── Публикация → VK / аккаунт 1
└── Публикация → RuTube / аккаунт 1
```

### 14.2 Поля

#### `id`

Уникальный идентификатор.
Системное поле.
Пользователь не изменяет его.

#### `content_id`

Контент, который публикуется.
Редактирование пользователем не предусматривается.

#### `platform_id`

Платформа публикации.
Платформы устанавливаются системой согласно справочнику в зависимости от типа контента.

#### `account_id`

Конкретный аккаунт на платформе.
Хранится в публикации, чтобы история всегда сохраняла информацию:

> на какой именно аккаунт была выполнена публикация.

Пользователь не вводит это значение вручную.

#### `status`

Состояние публикации.
Управляется действиями пользователя и системой.
Предварительно:

```text
Новая
Подготовка
Запланирована
Публикуется
Опубликована
Ошибка
Архив
```

Финальный набор статусов будет определён позднее.

#### `scheduled_at`

Планируемая дата и время публикации.
Может изменяться пользователем.

#### `published_at`

Фактическая дата и время публикации.
Устанавливается системой.

#### `external_id`

Идентификатор опубликованного объекта на платформе.
Заполняется системой, если платформа его предоставляет.
Технический параметр, пользователь его не видит.

#### `external_url`

Адрес опубликованного материала.
Заполняется системой.

#### `title`

Название публикации на платформе.
Может отличаться от названия контента.
Редактируется пользователем.

#### `description`
Описание публикации на платформе.
Может отличаться от описания контента.
Редактируется пользователем.
Необязательное поле.

#### `publication_data`

Параметры, необходимые для конкретной публикации.
Редактируется пользователем.
Необязательное поле.

Это поле используется вместо общего названия `tags`.

Причина:
разные платформы поддерживают разные форматы данных.

Поэтому это не «теги объекта», а именно:

> данные, которые система должна передать платформе при публикации.

Формат конкретных данных может храниться в JSON и обрабатываться адаптером соответствующей платформы.

#### `error_message`

Информация об ошибке публикации.
Только для просмотра.

#### `created_at`

Дата и время создания.
Системное поле.

#### `updated_at`

Дата и время последнего изменения.
Системное поле.

## 15. Попытки публикации

Количество попыток публикации не является обязательным полем `publications`.

На первом этапе отдельную таблицу создавать не требуется.

В будущем при необходимости может появиться техническая сущность:

```text
publication_attempts
```

Она будет хранить историю:

```text
Публикация
├── Попытка 1 → ошибка
├── Попытка 2 → ошибка
└── Попытка 3 → успешно
```

Это отложенная функциональность.

### 16.2 Таблица `analytics`

## 18. Связи между сущностями

Основная модель:

```text

│
└── Account
       │
       └── Publication

                └── Content
```

```text
Project
├── Content
├── Tasks
├── Assets
├── Publications (через Content)
```

Основные кардинальности:


Один из принципов приложения:

## 23. Архитектура пользовательского интерфейса

### 23.1 Основной принцип

Проект — центральный объект интерфейса.

Пользователь должен в любой момент понимать:

> В каком состоянии находится проект и что необходимо сделать дальше.

Страница проекта показывает:

```text
Проект
│
├── Параметры проекта
├── Основной контент
├── Дополнительный контент
├── Этапы производства
├── Задачи
├── Материалы
├── Публикации
└── Аналитика
```

### 23.2 Компонентная модель

Компонент CreatorOS является законченной функциональной единицей. Он может содержать собственную визуальную часть, состояние и логику поведения, относящиеся к его ответственности.

Универсальный компонент является единым носителем повторяющегося шаблона. Компоненты конкретных сущностей не копируют этот шаблон, а используют его через предусмотренную точку входа и передают свои данные, параметры и события.

Это правило распространяется на:

\`\`\`text
Card
Details
Modal
Form
Header
и другие повторяющиеся функциональные компоненты
\`\`\`

Страница является точкой сборки сценария и связей между компонентами, а не местом копирования общего UI-кода.

### 23.3 «Принцип ООП»

В проекте используется внутреннее название **«принцип ООП»** для следующего архитектурного приёма: общий функциональный шаблон реализуется один раз внутри универсального компонента через его точку входа/инициализатор, а конкретный компонент сущности вызывает этот шаблон с собственными параметрами.

Это не требование использовать классический JavaScript class-based OOP. Название обозначает архитектурный принцип повторного использования поведения и представления через единый компонент.

Для карточек:

\`\`\`text
EntityCard
│
└── InitialCard(...)
      ↑
      │
ProjectCard
ContentCard
TaskCard
AssetCard
PublicationCard
...
\`\`\`

Концептуально:

\`\`\`ts
InitialCard(
    title,
    description,
    status,
    progress,
    meta,
    actions,
    parameters
)
\`\`\`

Конкретная сущность:

\`\`\`text
ProjectCard
    ↓
InitialCard(данные Project)
\`\`\`

ProjectCard отвечает за то, **какие данные и какие действия** принадлежат Project, а EntityCard отвечает за то, **как этот набор данных визуально представлен**.

Таким образом, один и тот же визуальный шаблон карточки не дублируется в ProjectCard, ContentCard, TaskCard и других компонентах.

### 23.4 Модель Details

Для подробных представлений используется тот же принцип.

\`\`\`text
EntityDetails
│
└── InitialDetails(...)
      ↑
      │
ProjectDetails
ContentDetails
TaskDetails
AssetDetails
PublicationDetails
...
\`\`\`

EntityDetails содержит общий визуальный шаблон подробного представления сущности.

Компонент конкретной сущности отвечает за:

- загрузку и изменение данных своей сущности;
- связанные с ней действия;
- определение того, какие данные и блоки необходимо показать;
- передачу этих данных и действий в InitialDetails.

В результате общий UI Details реализуется один раз и не копируется между ProjectDetails, ContentDetails, TaskDetails и будущими компонентами.

### 23.5 Модель повторяющихся функциональных механизмов

«Принцип ООП» применяется не только к Card и Details, но и к другим повторяющимся механизмам.

Для подтверждения действия используется:

\`\`\`text
ConfirmModal
│
└── StartEvent(...)
      ↑
      │
любая сущность / любая страница
\`\`\`

ConfirmModal является единым самодостаточным компонентом, который хранит собственное состояние подтверждения, показывает общий UI и после подтверждения вызывает переданное событие.

Концептуальный вызов:

\`\`\`ts
StartEvent(
    "Удаление проекта",
    "Удалить проект «Мой проект»?",
    () => deleteProject(project.id)
)
\`\`\`

StartEvent получает как минимум:

\`\`\`text
заголовок
описание
callback / event
\`\`\`

и может в дальнейшем получать дополнительные параметры.

Callback передаётся в ленивой форме:

\`\`\`ts
() => deleteProject(project.id)
\`\`\`

а не:

\`\`\`ts
deleteProject(project.id)
\`\`\`

чтобы действие выполнялось только после подтверждения пользователя.

Страница или entity-компонент не должны создавать собственные копии состояния подтверждения, обработчиков открытия/закрытия и обработчика подтверждения для каждого нового сценария.

### 23.6 Архитектура CSS

Все CSS-файлы приложения располагаются внутри src/styles/.

Рекомендуемая организация:

\`\`\`text
src/styles/
│
├── index.css
├── theme.css
│
├── ui/
│   ├── Button.module.css
│   ├── Card.module.css
│   ├── Badge.module.css
│   ├── Modal.module.css
│   └── ...
│
├── entities/
│   ├── EntityCard.module.css
│   ├── EntityDetails.module.css
│   └── ...
│
├── layout/
│   ├── AppShell.module.css
│   ├── Sidebar.module.css
│   └── Workspace.module.css
│
└── pages/
    ├── DashboardPage.module.css
    ├── ProjectsPage.module.css
    └── ...
\`\`\`

Общий визуальный шаблон сущности имеет один источник стилей:

\`\`\`text
EntityCard
    → src/styles/entities/EntityCard.module.css

EntityDetails
    → src/styles/entities/EntityDetails.module.css
\`\`\`

Отдельные ProjectCard.module.css, ContentCard.module.css, TaskCard.module.css, ProjectDetails.module.css, ContentDetails.module.css и аналогичные файлы не создаются, если для конкретной сущности отсутствует самостоятельная уникальная визуальная ответственность.

Если в будущем конкретной сущности действительно понадобится уникальное оформление, сначала должно быть установлено, относится ли оно к общему шаблону. В общий шаблон оно добавляется, если поведение общее; отдельный стиль допускается только для действительно уникальной части.

### 23.7 Смысл разделения ответственности

Итоговая модель:

\`\`\`text
Universal Component
    │
    ├── общий UI
    ├── общий стиль
    └── общий механизм поведения
            ↑
            │ Initial...
            │
Entity Component
    │
    ├── данные конкретной сущности
    ├── правила конкретной сущности
    └── собственные действия
            ↑
            │
Page
    │
    └── сборка сценария и связей
\`\`\`

Главный результат этой модели — один общий шаблон используется многократно, а логика конкретной сущности не теряется и не переносится в универсальный компонент.

Архитектура должна позволять в будущем добавить:

```text
Series
Teams
Roles
Permissions
Platform integrations
Automatic publishing
Publication attempts
Advanced automation
Analytics
AI assistant
Synchronization
```

При этом добавление новых возможностей не должно требовать перестройки базового принципа:

```text
Project
→ Content
→ Publication
```

## 40. Главный вывод

CreatorOS строится не вокруг файлов, заметок или отдельных задач.

Он строится вокруг **процесса производства контента**.

Основная модель:

```text
Проект
│
├── 1 основной контент
├── 0..N дополнительного контента
├── задачи
├── материалы
└── публикации
       │
       └── аналитика
```

Ключевые правила модели:

```text
Один проект имеет ровно один основной контент.

Дополнительного контента может быть несколько.

Приоритет задаётся контенту.

Приоритет задач в дальнейшем рассчитывается системой.

Статусы проекта и контента не редактируются произвольным вводом,
а изменяются через предусмотренные действия и процессы.

Публикация относится к контенту и конкретному аккаунту платформы.

Данные для площадки называются publication_data,
а не tags.

Серия является отдельной будущей сущностью,
а не способом объединить несколько основных контентов в одном проекте.

Данные не дублируются без необходимости.
```

Главный принцип:

> CreatorOS должен сам понимать структуру производства и выполнять рутинную работу, оставляя пользователю принятие содержательных решений.
