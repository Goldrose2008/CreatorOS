# Технический документ проекта

**Название приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия документа:** 1.5 
**Статус:** Основной UI реализуется на native Qt Widgets; переходный web-слой сохраняется только до завершения рефакторинга и удаления необязательных зависимостей
**Тип продукта:** Desktop-приложение  
**Целевые платформы:** Windows / macOS / Linux

## Архитектурные правила:
	1. CreatorOS — система управления полным циклом создания контента: от идеи до публикации и анализа результата.
	2. Центральная бизнес-сущность CreatorOS — Project (Проект).
	3. Один Project представляет одну единицу производства контента.
	4. Один Project имеет ровно один основной Content.
	5. Project может иметь 0..N дополнительных Content.
	6. Несколько связанных выпусков являются отдельными Projects; Series является отдельной будущей сущностью.
	7. Project объединяет основной и дополнительный Content, Tasks, Assets / Materials, Publications и Analytics.
	8. Связи между сущностями хранятся один раз и не дублируются без необходимости.
	9. Publication относится к Content; отдельный project_id в Publication не требуется.
	10. Account выбирается из подключённых аккаунтов; account_id не вводится пользователем вручную.
	11. Системные идентификаторы, даты создания и технические значения не редактируются пользователем вручную.
	12. Связь Content с Project и роль Content main/additional управляются системой.
	13. Статусы сущностей изменяются через предусмотренные действия и процессы, а не произвольным вводом.
	14. Прогресс Project и Content рассчитывается системой; пользователь не вводит процент вручную.
	15. Приоритет хранится на уровне Content; отдельный приоритет Project не используется.
	16. Приоритет Task в дальнейшем рассчитывается системой на основании контекста, сроков и влияния задачи.
	17. production_deadline_at рассчитывается системой; planned_release_at относится к планируемому выходу основного контента.
	18. User, Team, Platform, Account, Publication, Analytics, Automation, Series и другие сущности имеют отдельные области ответственности.
	19. Доступ к SQLite выполняется только через слой сервисов/репозиториев; UI-компоненты и страницы не работают с БД напрямую.
	20. Страницы являются полноценными UI-классами прикладных сценариев. Их структура, состояние и локальное поведение могут находиться в одном классе, если это одна целостная ответственность.
	21. UI-класс является законченной единицей представления и взаимодействия: в одном классе могут находиться визуальная структура, дочерние QWidget, локальное состояние, отрисовка, обработчики пользовательских действий и UI-логика.
	22. UI-код не разделяется на отдельные визуальные и логические файлы только ради размера файла или формального разделения UI и logic. Разделение выполняется только при появлении самостоятельной ответственности, реального повторного использования или внешней технической границы.
	23. Повторное использование кода является обязательной целью. Если несколько классов имеют общий контракт и общее поведение, общий код выносится в базовый класс и наследование рассматривается как основной механизм повторного использования.
	24. Наследование применяется, когда дочерний класс является специализированным вариантом базового класса, сохраняет его контракт и использует его общее поведение. Поверхностного сходства полей недостаточно.
	25. Композиция применяется для независимых или опциональных объектов, которые не являются разновидностью содержащего их класса. Composition дополняет наследование, а не заменяет его как универсальное правило.
	26. Специализированный UI-класс наследует общую реализацию и добавляет только уникальные свойства, элементы, обработчики и поведение своей области. Повторная реализация общего визуального каркаса запрещается.
	27. Общая UI-функциональность выносится в базовые классы, переиспользуемые классы или helpers только при наличии реального общего поведения. Искусственные уровни только для уменьшения размера файлов не создаются.
	28. Если один и тот же прикладной механизм появляется у нескольких сущностей, повторяемая часть алгоритма должна иметь общий механизм. Конкретная сущность добавляет только свои ограничения и правила.
	29. Общий CRUD-механизм не должен порождать отдельный дублирующий алгоритм для каждой сущности, если различается только тип объекта. Конкретные сервисы могут наследовать общий механизм либо использовать другой типобезопасный общий механизм, а entity-specific правила остаются в специализированном классе.
	30. UI может иметь явную зависимость от application service/use case для выполнения пользовательского действия. UI не обращается напрямую к SQLite, SQL, файловой системе, HTTP, секретному хранилищу или инфраструктурному adapter.
	31. Бизнес-логика, доменные инварианты, вычисления и правила жизненного цикла сущностей находятся в domain/application слоях. UI отвечает за представление, пользовательское взаимодействие и передачу намерения.
	32. Бизнес-операция, вызванная UI, может проходить через application service, но обработка результата, визуального состояния и реакции на пользователя остаётся внутри UI-класса.
	33. ООП является основной моделью построения приложения. Классы, наследование, интерфейсы, композиция, инкапсуляция, RAII и Qt signals/slots применяются согласно реальным отношениям и ответственности объектов.
	34. ConfirmModal является единым самодостаточным объектом подтверждения. Для запуска используется единый публичный механизм класса, принимающий заголовок, описание и действие после подтверждения.
	35. Действие подтверждения передаётся лениво, например callback/std::function, и выполняется только после подтверждения пользователя.
	36. Страницы и сущности не дублируют состояние открытия, закрытия и подтверждения ConfirmModal.
	37. C++20 и Qt 6 являются основой приложения, а прикладной интерфейс реализуется нативными Qt Widgets.
	38. Основной desktop-shell и всё прикладное содержимое UI реализуются как объекты C++/Qt Widgets. Корневое окно и страницы не зависят от web-фреймворков.
	39. QWebEngineView и Qt WebChannel допускаются только для специализированных web-сценариев, которым действительно нужен web-рендеринг.
	40. Граница между UI и application/domain слоями проходит через обычные C++ интерфейсы, application services, явные зависимости и Qt signals/slots. UI не получает прямой доступ к инфраструктурным реализациям.
	41. Визуальный код и UI-поведение могут находиться в одном QWidget-классе. Отдельный application/domain код нужен для отделения бизнес-правил и технических процессов от пользовательского представления, а не для формального разделения UI и logic.
	42. Компонент не обязан получать каждый текст, иконку или дочерний элемент извне. Внешними параметрами передаются только значения, которые действительно зависят от сценария или должны быть заменяемыми.
		43. Локализуемые тексты хранятся в единой таблице `localization.tsv`; языковые каталоги формируются в памяти сервисом локализации при запуске приложения.
	44. Все пользовательские тексты, зависящие от языка, обращаются к text ID. Структурные ID компонентов и пунктов меню не являются идентификаторами переводов. Полные фразы с языковым контекстом получают отдельный text ID.
	45. Имена C++ классов и файлов должны сразу показывать их роль: <Entity>Service, <Entity>Repository, <Entity>Model, <Entity>Adapter, MainWindow, AppShell, Sidebar, MenuItem, MenuSection, PageHeader, EntityCard, EntityDetails, ConfirmModal и аналогичные формы.
	46. После каждого завершённого этапа фактически выполненная работа заносится в docs/DEVELOPMENT_LOG.md; при необходимости обновляется docs/USER_GUIDE.md.
	47. docs/TECHNICAL_SPEC.md является источником постоянных архитектурных правил; docs/DEVELOPMENT_LOG.md — журналом выполненных этапов и перечнем временных решений.
	48. Перед каждым новым архитектурным или кодовым решением необходимо опираться на актуальные docs/TECHNICAL_SPEC.md, docs/DEVELOPMENT_LOG.md и фактическое состояние проекта.
	49. После сообщения пользователя о запушенном коммите и готовности продолжать необходимо проверить последний коммит и актуальное состояние всего проекта в GitHub: дерево файлов, наличие/отсутствие файлов, ключевые связи и соответствие текущей архитектуре.
	50. Основной технологический стек новой версии CreatorOS: C++20 + Qt 6 Widgets + CMake + SQLite. HTML/CSS/JavaScript не являются обязательным UI-слоем и применяются только в специализированных web-сценариях.
	51. CMake является единственной основной системой сборки проекта. qmake не используется как архитектурный инструмент проекта.
	52. Стандарт языка C++ фиксируется на современном стандарте, поддерживаемом выбранной версией Qt 6; целевой базовый стандарт проекта — C++20.
	53. Qt-модули выбираются по принципу минимально необходимого набора. Базовый набор: Qt Core, Gui, Widgets, Sql и Network; Qt Svg, WebEngineWidgets, WebChannel и другие дополнительные модули добавляются только при наличии конкретной функции и после проверки лицензии.
	54. Для распространения CreatorOS под LGPL используются только совместимые open-source варианты Qt-модулей. Qt-модули, доступные open-source пользователям только под GPL, не включаются в proprietary-сборку CreatorOS без отдельного лицензионного решения.
	55. Qt распространяется динамически, отдельными библиотеками, чтобы приложение не было неразрывно связано со встроенной копией LGPL-библиотек и чтобы выполнить требования LGPL по возможности замены/relinking.
	56. При распространении Qt-компонентов CreatorOS предоставляет копию текста соответствующей лицензии, явное уведомление об использовании Qt и информацию об исходном коде используемых LGPL-компонентов и связанных с ними лицензионных обязательствах.
	57. Если исходный код Qt-компонента изменяется нами, такие изменения не считаются закрытой частью CreatorOS и распространяются в соответствии с лицензией соответствующего Qt-компонента.
	58. Qt WebEngine допускается только как специализированная зависимость для реально требуемого web-сценария и не входит в обязательную архитектуру прикладного UI. При включении WebEngine для конкретной функции учитываются его отдельные лицензионные и дистрибуционные требования, включая third-party компоненты.
	59. Qt WebView не является частью обязательного UI-стека. Он может рассматриваться только для отдельного специализированного web-сценария после проверки стабильности и совместимости с целевыми платформами.
	60. Qt Network Authorization не используется в LGPL-only варианте проекта без отдельного лицензионного решения: OAuth 2.0/PKCE реализуется через разрешённые Qt Network API, системный браузер и собственный слой авторизации либо через отдельно проверенную permissive/LGPL-совместимую библиотеку.
	61. SQLite является локальной основной БД MVP. Доступ к SQLite выполняется из C++ infrastructure-слоя через Qt SQL (QSQLITE) и репозитории; UI и presentation-слой SQL не выполняют.
	62. Доступ к данным строится через application services/use cases и repositories. UI не знает структуру таблиц и не содержит SQL-запросов.
	63. Внешние площадки подключаются отдельными C++ интеграционными адаптерами. Для HTTP/REST используется Qt Network; UI не вызывает API площадок напрямую.
	64. Секреты, OAuth-токены, refresh tokens и ключи не передаются в прикладной UI без крайней необходимости. Для защищённого хранения используется отдельный security adapter с использованием системного защищённого хранилища ОС. При наличии специализированного web-модуля секреты не передаются в его JavaScript без отдельного обоснования.
	65. Native C++ является основой текущей архитектуры CreatorOS. UI, application, domain, infrastructure и integrations реализуются как единая C++ архитектура с чёткими границами ответственности; отдельные платформенные adapters допускаются только там, где они действительно необходимы.
	68. Архитектурная граница между UI и application/domain слоями выполняется через C++ интерфейсы, контроллеры/компоновщики и application services. Замена конкретной реализации визуального компонента не должна требовать изменения доменной модели и репозиториев.
	69. Отсутствие файла в GitHub Code Search не является доказательством отсутствия файла в репозитории. При работе с проектом сначала проверяются дерево репозитория/каталоги, затем файл при необходимости запрашивается напрямую по известному пути.
	70. Все новые зависимости до добавления в проект проходят проверку лицензии, необходимости, кроссплатформенности и способа распространения. Для релиза поддерживается список third-party components и их лицензий.


## Технологический стек

### Основной стек

| Слой | Технология | Назначение |
|---|---|---|
| Основной язык | C++20 | Доменная модель, application services, инфраструктура, интеграции и UI |
| Desktop framework | Qt 6 | Окна, GUI, события, SQL, сеть и кроссплатформенная основа |
| Desktop UI | Qt Widgets | Основной нативный интерфейс приложения |
| Визуальная система | QStyle / QProxyStyle + QPainter | Единый визуальный стиль, состояния и специализированная отрисовка |
| UI-компоненты | C++ classes / QWidget | Переиспользуемые элементы интерфейса и страницы |
| Иконки | Qt Resource System + SVG/Qt Svg | Хранение и отображение иконок |
| Локализация | localization.tsv + LocalizationService | Единый исходник переводов и in-memory каталоги |
| Сборка | CMake | Конфигурация и сборка всех target'ов |
| База данных | SQLite через Qt SQL / QSQLITE | Локальное хранилище MVP |
| Сеть | Qt Network | HTTP/REST, загрузки, сетевые операции |
| Специализированный web UI | QWebEngineWidgets / QWebChannel | Только для функций, которым действительно требуется web-рендеринг |
| Контроль версий | Git + GitHub | Исходный код и история изменений |
| Среда разработки | Visual Studio Code или другой редактор | Разработка и отладка |

Конкретная patch-версия Qt 6 фиксируется при настройке среды разработки. Версия выбирается по стабильности, доступности open-source пакетов, совместимости с CMake/MSVC/Clang и потребностям целевых платформ.

### Принцип технологического стека

Целевая архитектура:

~~~text
                         CreatorOS
                            │
             ┌──────────────┴──────────────┐
             │                             │
        Qt Presentation               C++ Application Core
             │                             │
      ┌──────┼──────┐              ┌───────┼────────┐
      │      │      │              │       │        │
 MainWindow AppShell Pages     Services  Domain  Integrations
      │      │      │              │       │        │
      └──────┴──────┴──────────────┼───────┼────────┘
                                   │       │
                              Repositories  │
                                   │       │
                                SQLite   File System / APIs

      Optional specialized web branch:
      QWidget/Web UI host
             ↓
        QWebEngineView
             ↓
        HTML/CSS/JS
             ↓
        QWebChannel
             ↓
        C++ application services
~~~

Главное правило:

> **Qt Widgets отвечает за прикладное представление. C++ отвечает за данные, правила и действия приложения. Web-технологии не являются обязательной частью интерфейса.**

### Принцип native UI и компонентов

Прикладной UI CreatorOS строится из целостных C++/Qt Widgets-классов. Главный критерий выделения класса — самостоятельная ответственность, а не стремление вынести каждый визуальный фрагмент в отдельный «кирпичик».

UI-класс может одновременно содержать собственную структуру QWidget, дочерние widgets, layout, визуальное оформление, локальное состояние, обработчики пользовательских действий и Qt signals/slots.

~~~text
Base UI class
   ↓ inheritance
Specialized UI class
   ├── inherited visual structure
   ├── inherited common behavior
   └── specialized behavior
~~~

Внутри класса используется обычная composition из Qt-объектов:

~~~text
ProjectCard
├── QLabel
├── QPushButton
├── QProgressBar
└── optional specialized QWidget
~~~

Наследование используется, когда один UI-класс действительно является специализированной разновидностью другого.

~~~text
Card
  ↓
EntityCard
  ├── ProjectCard
  ├── ContentCard
  └── TaskCard
~~~

Специализированные классы переиспользуют общий layout, визуальное оформление и поведение базового класса и добавляют только свою уникальную часть.

Страницы также могут образовывать иерархии, когда существует общий контракт и общее поведение. Если страницы только случайно похожи внешне, они остаются отдельными классами.

### Принцип UI ↔ Application

~~~text
Qt UI class
   ↓
Application Service / Use Case
   ↓
Domain
   ↓
Repository / Adapter
   ↓
SQLite / File System / External API
~~~

UI-класс отвечает за пользовательское представление и взаимодействие. Application/domain отвечают за бизнес-правила и прикладные операции. Infrastructure отвечает за конкретные технические процессы.

### Принцип визуального стиля

Глобальная визуальная система реализуется в C++:

~~~text
CreatorStyle : QProxyStyle
      │
      ├── Colors / palette
      ├── Typography metrics
      ├── Control metrics
      ├── Spacing / radii
      ├── Hover / focus / active states
      └── Common control drawing
               │
               ▼
       Custom QWidget / QPainter
~~~

QStyle/QProxyStyle задаёт общие правила. Отдельные сложные компоненты используют собственную отрисовку через QPainter, не дублируя дизайн-токены.

Qt Style Sheets допускаются только локально, когда они действительно упрощают конкретный небольшой визуальный сценарий. QSS не является основной системой дизайна приложения.

### Принцип API и интеграций

Интеграции организуются в C++:

~~~text
src/integrations/
├── youtube/
├── rutube/
├── vk_video/
├── dzen/
└── common/
~~~

Каждый адаптер получает отдельный внутренний контракт и скрывает детали конкретной площадки.

~~~text
authorize()
upload()
create/update metadata
publish/schedule
getStatus()
getPublication()
getStatistics()
disconnect()
~~~

Не все операции обязаны существовать у каждой платформы. Адаптер отражает реальные возможности API.

### Принцип лицензирования Qt

Основной open-source вариант Qt для CreatorOS — LGPL v3 при соблюдении её условий. Это не означает, что все Qt-модули лицензированы одинаково; перед добавлением любого модуля проверяется его актуальный лицензионный статус.

Практические правила CreatorOS:

## 1. Назначение приложения

CreatorOS предназначен для управления полным циклом создания контента:

```text
Идея
↓
Проект
↓
Создание контента
↓
Производство
↓
Подготовка публикации
↓
Публикация
↓
Аналитика
```

Главная цель:

> CreatorOS должен брать на себя рутинную организацию процесса и позволять пользователю сосредоточиться на содержательных решениях.

## 2. Основная модель предметной области

```text
Project
├── 1 Main Content
├── 0..N Additional Content
├── Tasks
├── Assets / Materials
├── Publications
└── Analytics
```

## 3. Project

Project является центральной бизнес-сущностью.

Основные данные:

```text
id
name
description
owner_id
planned_release_at
status
progress
created_at
updated_at
```

Project не хранит отдельный приоритет.

## 4. Content

Content является самостоятельной сущностью, находящейся внутри Project.

Основные данные:

```text
id
project_id
content_type_id
content_role
name
description
priority
production_deadline_at
status
progress
created_at
updated_at
```

Роли:

```text
main
additional
```

Для одного Project допускается только один Content с ролью main.

## 5. ContentType

ContentType является справочником типов контента.

Примеры:

```text
Видео
Short
Статья
```

Пользователь может добавлять и изменять типы контента через Settings.

## 6. Task

Task имеет контекст родительской сущности.

Основная модель:

```text
parent_id
parent_type
parent_task_id
```

Это позволяет связывать задачу с Project, Content или другой поддерживаемой сущностью без создания отдельной таблицы связей для каждого типа объекта.

## 7. Publication

Publication относится к конкретному Content и конкретному Account.

Основные направления данных:

```text
content_id
platform_id
account_id
status
scheduled_at
published_at
external_id
external_url
title
description
publication_data
error_message
```

## 8. Platform и Account

Platform описывает площадку публикации.

Account представляет конкретный аккаунт/канал пользователя на этой площадке.

Связь:

```text
Platform
    ↓
Account
    ↓
Publication
    ↓
Content
```

## 9. EntityCard

EntityCard — базовый C++/Qt-класс для целостного UI-представления карточки сущности.

База знает общие механизмы карточки: поверхность, заголовок, описание, статус, прогресс, метаданные, области дополнительного содержимого и действия. Эти механизмы могут существовать в базе заранее, даже если конкретному наследнику часть из них не нужна.

База не знает, что перед ней Project, Content или Task. В ней не должно быть ветвлений вида `if (isProject) ... else if (isTask) ...`.

Конкретная сущность определяется специализированным наследником:

~~~text
Card
  ↓
EntityCard
  ├── ProjectCard
  ├── ContentCard
  ├── TaskCard
  ├── AssetCard
  └── PublicationCard
~~~

Наследник настраивает и заполняет общие UI-механизмы, показывает или скрывает подходящие области и добавляет только специфические элементы и поведение. Общий визуальный каркас не копируется.

## 10. EntityDetails

EntityDetails — базовый C++/Qt-класс для целостных подробных представлений сущностей.

База знает UI-механизмы details-представления: прокрутку, общую структуру страницы, навигационную область, header, стандартные состояния, summary/info-области, действия, дополнительные content-регионы и управление их видимостью.

Это не означает, что база должна заранее содержать поля каждой будущей сущности. В базе находятся именно повторяемые UI-механизмы. Конкретное содержание и условия показа определяет наследник.

~~~text
EntityDetails
   ├── ProjectDetailsPage
   ├── ContentDetails
   └── TaskDetails
~~~

Например, `ProjectDetailsPage` может включить summary, release date, owner и progress, а `TaskDetails` — только те механизмы, которые подходят Task. База предоставляет механизм, наследник принимает решение.

База не проверяет тип конкретной сущности и не содержит entity-specific ветвления.

Если в details появляется действительно независимый сложный объект с собственным контрактом и поведением, он подключается через composition. Простая разметка, QLabel, QPushButton и layout остаются внутри details-класса.

Бизнес-операции, доменные правила и инварианты выполняются через application/domain слои.

## 11. ConfirmModal

ConfirmModal является единым механизмом подтверждения действий в native UI.

Концептуальный поток:

~~~text
Qt UI
↓
Application Service / Use Case
↓
ConfirmModal
↓
решение пользователя
↓
callback / signal
↓
C++ действие
~~~

Отображение, состояние диалога и пользовательский выбор принадлежат UI-компоненту. Само удаление или изменение сущности выполняется C++ service после проверки правил.

## 11.1 Правило самодостаточности UI-компонента

Компонент отвечает за собственное:
- визуальное состояние;
- дочерние widgets;
- сигналы/слоты;
- локальные UI-правила;
- передачу пользовательского намерения наружу.

Компонент не выполняет SQL и не содержит бизнес-правила.

## 12. Pages

Основные страницы:
~~~text
DashboardPage
ProjectsPage
ProjectDetailsPage
ContentDetailsPage
TasksPage
PlanningPage
LibraryPage
AnalyticsPage
SettingsPage
~~~

Каждая страница является полноценным C++/Qt UI-классом своего прикладного сценария. Внутри неё находятся собственная визуальная структура, локальное UI-состояние и обработчики взаимодействия.

Страница может использовать самостоятельные классы через composition, когда эти объекты действительно имеют отдельную ответственность или собственный контракт. Но страница не дробится на классы только ради вынесения участка layout.

Page не содержит SQL, сетевых вызовов, прямой работы с файлами или бизнес-правил. Для запуска прикладных действий используются application services/use cases.

## 16. ООП-архитектура CreatorOS

C++ является основной ООП-моделью CreatorOS. Наследование является основным способом повторного использования целостной специализированной сущности при совместимом контракте и общем поведении. Composition используется внутри сущности для сложных независимых частей.

~~~text
«является» + общий контракт + общее поведение
        → наследование

«содержит» / «использует» + независимый контракт
        → композиция

только совпадают поля
        → не повод для наследования
~~~

UI-класс не обязан разделять визуал и UI-поведение на разные файлы. Пара .h/.cpp является техническим устройством C++ для объявления и реализации одного класса, а не архитектурным разделением UI и logic.

Повторяющийся прикладной механизм также не должен копироваться по сущностям только из-за разных типов данных. Если Project, Content и Task используют одинаковую часть алгоритма, повторяемая часть должна находиться в общем типобезопасном механизме; специализированный класс добавляет уникальные проверки и правила.

При этом domain и application остаются независимыми от конкретной визуальной реализации. Бизнес-правила не переносятся в QWidget только ради уменьшения числа файлов.

Интерфейсы репозиториев и интеграций вводятся там, где они дают реальную заменяемость и тестируемость. Искусственные абстракции не создаются.

## 17. Стили

Визуальное оформление прикладного интерфейса выполняется нативными средствами Qt.

Целевая организация:

~~~text
src/ui/
├── style/
│   ├── CreatorStyle.*
│   ├── Colors.*
│   ├── Metrics.*
│   └── Icons.*
├── components/
├── pages/
├── shell/
└── localization/
~~~

CreatorStyle наследуется от QProxyStyle и является центральной точкой общих визуальных правил. Colors и Metrics хранят дизайн-токены приложения. Icons предоставляет единый доступ к иконкам из Qt Resource System.

Для сложных или нестандартных компонентов используется собственная отрисовка через QPainter. Компоненты не должны самостоятельно дублировать общие цвета, размеры, отступы и состояния.

На первом этапе реализуется тёмная тема. Архитектура должна позволять добавить светлую тему без изменения доменной модели и без переписывания страниц.

Qt Style Sheets допускаются только локально, когда это действительно упрощает небольшой визуальный сценарий. QSS не является основой дизайн-системы.

## 18. База данных

SQLite является локальной основной БД MVP.

Доступ к БД строится только через C++ infrastructure/repository layer:

~~~text
Native Qt UI
↓
Application Service / Use Case
↓
Repository
↓
Qt SQL / QSQLITE
↓
SQLite
~~~

UI-компоненты и страницы не работают с БД напрямую. UI не выполняет SQL.

### DatabaseManager

Отдельный инфраструктурный объект отвечает за:
~~~text
открытие подключения
↓
проверку/создание схемы
↓
применение миграций
↓
управление транзакциями
↓
закрытие подключения
~~~

Репозитории отвечают за операции конкретных сущностей:

~~~text
IProjectRepository
IContentRepository
ITaskRepository
...
~~~

SQLite-файл хранится в пользовательском каталоге данных приложения, а не рядом с исполняемым файлом.

### Миграции

Структура БД изменяется последовательными SQL-миграциями. Версия схемы хранится в самой БД.

~~~text
schema v1
↓
migration 2
↓
schema v2
↓
migration 3
↓
...
~~~

Миграции контролируются механизмом версии схемы и выполняются транзакционно, когда это возможно.

## 21. Лицензирование

CreatorOS планируется как proprietary/closed-source приложение, поэтому лицензии сторонних компонентов должны позволять такое распространение.

### Qt

Основной open-source вариант — использование LGPL v3 компонентов Qt при полном соблюдении LGPL.

Qt не является однородно лицензированным пакетом: в актуальном Qt 6.12 часть модулей доступна open-source пользователям только под GPL v3. Эти GPL-only модули не включаются в базовую proprietary-сборку без отдельного лицензионного решения.

Для CreatorOS принимаются следующие практические меры:

~~~text
Qt DLLs
↓
динамическая поставка
↓
license notices
↓
информация об исходниках LGPL-компонентов
↓
возможность замены/relinking согласно LGPL
~~~

Особое внимание:
~~~text
модульный состав Qt
Qt WebEngine и third-party/Chromium лицензии
Qt Network Authorization
изменения исходного кода Qt
~~~

### SQLite

SQLite используется через Qt SQL/QSQLITE. В документации Qt 6.12 SQLite указан как third-party компонент под SQLite Blessing.

### Прочие зависимости

Каждая дополнительная библиотека проверяется до включения в основной target:

~~~text
license
commercial redistribution
source/notice obligations
static/dynamic linking requirements
platform compatibility
~~~

В релизе CreatorOS должен существовать раздел О программе → Лицензии.

Этот раздел является архитектурным правилом проекта, а не индивидуальным юридическим заключением. Перед первым коммерческим релизом итоговый набор распространяемых компонентов и их лицензий проверяется по актуальным лицензионным текстам.

## 23. Главный принцип проекта

CreatorOS строится вокруг процесса производства контента, а не вокруг отдельных экранов.

Главная цепочка:

~~~text
Project
↓
Content
↓
Production
↓
Publication
↓
Analytics
~~~

Программная архитектура:

~~~text
Native Qt UI
↓
Application Services / Use Cases
↓
Domain
↓
Repository / Integration Adapter
↓
SQLite / File System / Platform API
~~~

Общая UI-функциональность переиспользуется преимущественно через целостные C++/Qt-классы и наследование при совместимом контракте; composition используется для независимых и опциональных частей. Signals/slots и общая визуальная система дополняют эту модель. ООП применяется на всех слоях там, где классы и инкапсуляция дают реальную архитектурную пользу.


~~~text
database/             schema и SQL migrations
resources/licenses/   license notices / third-party information
tests/                автоматические тесты
~~~

Каталоги создаются по мере появления соответствующей ответственности.

## 27. Архитектура UI-классов CreatorOS

### 27.1. Цель

CreatorOS строится как понятное C++/Qt-приложение с целостными UI-классами, а не как набор классов для каждого участка разметки.

Основные правила:

~~~text
целостная UI-сущность
        ↓
наследование как основной способ повторного использования
        +
composition для сложных независимых частей
        ↓
application/domain для бизнес-правил
        ↓
infrastructure/adapters для технических операций
~~~

Новый UI-класс не появляется только потому, что участок UI кажется большим или его «надо вынести».

### 27.2. Роли уровней

~~~text
Qt Widgets UI
    ↓
Application Services / Use Cases
    ↓
Domain
    ↓
Repositories / Adapters
    ↓
SQLite / File System / External APIs
~~~

UI отвечает за отображение, пользовательское взаимодействие, локальное UI-состояние и передачу прикладного намерения.

Application/domain отвечают за бизнес-правила, инварианты, вычисления, жизненный цикл сущностей и прикладные операции.

Infrastructure/adapters отвечают за SQLite, файлы, HTTP и другие технические процессы.

### 27.3. Целостность UI-класса

Один UI-класс может содержать:

~~~text
class
├── child QWidget
├── layouts
├── visual state
├── local UI state
├── event handlers
├── signals / slots
├── private helper methods
└── calls to application services
~~~

Визуальная структура и UI-поведение не разделяются на разные классы только ради размера файла.

### 27.4. База знает UI-механизмы

Базовый UI-класс может заранее содержать все общие механизмы отображения, которые потенциально нужны производным классам.

Например, `EntityDetails` может иметь механизмы header, navigation, summary, status, progress, metadata, actions, error и дополнительных content-регионов. Отсутствие необходимости у конкретной сущности не требует создания другого базового класса.

База знает только UI-механизмы:

~~~text
База:
«умею показать / скрыть / заполнить / заменить этот UI-регион»
~~~

База не знает конкретные типы сущностей и не содержит проверок Project/Content/Task.

### 27.5. Наследник знает конкретную сущность

Специализированный класс отвечает за конкретную предметную сущность и сценарий её отображения:

~~~text
EntityDetails
   ↓
ProjectDetailsPage
~~~

`ProjectDetailsPage` решает, какие общие механизмы использовать для Project, какие показать, чем их заполнить и какое собственное поведение добавить.

Аналогично:

~~~text
EntityCard
   ↓
ProjectCard / ContentCard / TaskCard
~~~

Наследник не копирует общую разметку базы. Он расширяет или настраивает её.

### 27.6. Наследование как основной способ повторного использования

Наследование применяется, когда одновременно выполняются условия:

- специализированный объект является разновидностью базового;
- базовый контракт сохраняется;
- общее поведение реально переиспользуется;
- специализация расширяет или настраивает базу.

Совпадение набора полей само по себе не является причиной для наследования.

### 27.7. Composition внутри UI-сущности

Composition используется для сложных независимых объектов, которые действительно имеют собственную ответственность, состояние или контракт.

~~~text
ProjectDetailsPage
├── inherited EntityDetails mechanisms
├── simple QLabel / QPushButton / layout
└── complex independent widget, when genuinely needed
~~~

Обычные Qt controls и layout не становятся отдельными архитектурными классами.

### 27.8. EntityCard

Целевая иерархия:

~~~text
SurfaceWidget
└── Card
    └── EntityCard
        ├── ProjectCard
        ├── ContentCard
        └── TaskCard
~~~

`EntityCard` содержит общий целостный UI карточки и предоставляет наследникам общие механизмы.

Конкретные карточки определяют данные сущности, условия отображения и уникальные действия.

### 27.9. EntityDetails

Целевая иерархия:

~~~text
EntityDetails
├── ProjectDetailsPage
├── ContentDetails
└── TaskDetails
~~~

Новая промежуточная иерархия вроде `BaseDetails → EntityDetails` не создаётся заранее. Сначала используется реальное общее поведение `EntityDetails`; дополнительный уровень появляется только при доказанной самостоятельной ответственности.

### 27.10. Опциональные UI-регионы

База может иметь опциональные регионы или механизмы отображения. Производный класс управляет их использованием.

Правильная схема:

~~~text
EntityDetails
    ├── общий механизм Summary
    ├── общий механизм Metadata
    ├── общий механизм Progress
    └── ...
             ↑
      ProjectDetailsPage
      включает нужное
~~~

Неправильная схема:

~~~text
EntityDetails
    └── if (Project) ...
        else if (Task) ...
        else if (Content) ...
~~~

При большом количестве entity-specific условий такой код превращает базу в God class и запрещается архитектурой.

### 27.11. Pages

Страница является полноценным UI-классом прикладного сценария.

Она может содержать список, фильтры, состояния загрузки, обработчики действий, собственные helper methods и зависимости от application services.

Не требуется создавать `PageHeaderController`, `ProjectPageLayout`, `ProjectPageLogic` и другие классы только ради разделения UI на части.

### 27.12. Когда появляется отдельный компонент

Отдельный UI-класс создаётся только при наличии хотя бы одной реальной причины:

1. самостоятельная ответственность;
2. реальное повторное использование в нескольких местах;
3. собственный стабильный публичный контракт;
4. сложное внутреннее состояние и жизненный цикл;
5. независимый технический или интеграционный объект.

Само наличие большого участка layout причиной не является.

### 27.13. States, Forms и Shell

`StateWidget → EmptyState / ErrorState` сохраняется, если state-классы действительно имеют общий контракт и поведение.

Форма остаётся целостным UI-классом. `FormField` используется там, где роль поля действительно повторяется и имеет самостоятельную ответственность.

Для повторяющегося модального сценария редактирования используется иерархия:

```text
QDialog
└── EditorDialog
    ├── ProjectEditorDialog
    ├── ContentEditorDialog
    └── другие специализированные editor'ы
```

`EditorDialog` содержит общий lifecycle editor-диалога: content region, Save/Cancel, завершение диалога после успешного `save()` и режим редактора `Create/Edit`.

Режим является UI-механизмом базового editor'а и предоставляется наследникам через `isEditMode()`. Базовый класс не знает тип конкретной сущности и не содержит ветвлений Project/Content/Task.

Специализированный editor отвечает за конкретные поля, состояние редактируемой сущности, validation и application-операцию. Идентификатор/модель конкретной сущности остаются в специализированном editor-классе.

`AppShell`, `Sidebar` и `Workspace` остаются отдельными классами, потому что это самостоятельные части shell с собственными ролями и жизненным циклом.

`MenuItem` и `MenuSection` остаются отдельными классами как самостоятельные элементы навигации.

### 27.14. UI ↔ Application

~~~text
ProjectCard / ProjectDetailsPage / ProjectsPage
        ↓
ProjectService / Use Case
        ↓
Domain + Repository
        ↓
SQLite
~~~

UI не получает прямой доступ к SQL, `QSqlQuery`, файловой системе или конкретной инфраструктурной реализации.

### 27.15. Повторяемые прикладные механизмы

Если одинаковый прикладной алгоритм появляется у Project, Content и Task, он не копируется по сервисам.

Сначала подтверждается реальное повторение, затем общий механизм строится один раз в типобезопасной форме.

Не требуется создавать универсальный CRUD-framework заранее. Но после появления повторяющегося алгоритма повторять его вручную запрещено.

### 27.16. Сигналы и локальное UI-поведение

Qt signals/slots используются для связи UI-объектов и передачи пользовательских событий.

Если обработка относится к локальному поведению конкретного QWidget, она остаётся в этом классе.

Бизнес-операция, которую запускает обработчик, передаётся в application service/use case.

### 27.17. Стили и локализация

Общие цвета, размеры, иконки и типовые визуальные правила централизованы в `CreatorStyle`, `Colors`, `Metrics` и `Icons`.

Уникальная визуальная реализация остаётся в соответствующем UI-классе.

Локализуемые тексты используют единый `localization.tsv` и `LocalizationService`.

### 27.18. Что не создаём заранее

~~~text
класс только ради большого .cpp
класс только ради отдельного layout-фрагмента
отдельный ViewModel только для UI-логики
отдельный Composer для каждого QWidget
новую базовую иерархию без реального общего поведения
универсальный CRUD framework до появления повторения
ветвление базы по Project / Content / Task
~~~

### 27.19. Организация .h/.cpp

Пара `.h + .cpp` — одна программная единица класса.

Разделение header/source является особенностью C++, а не разделением UI и logic.

Классы `ClassView.*`, `ClassLogic.*`, `ClassLayout.*` для одной и той же UI-сущности не создаются без отдельной архитектурной причины.

### 27.20. PROGRAM_STRUCTURE и фактическая структура

Каталоги используются для смысловой навигации по коду.

`PROGRAM_STRUCTURE.md` всегда отражает фактические файлы: после добавления файл сразу получает запись с путём и назначением; после удаления запись удаляется.

Физическое наличие каталога `components` не означает, что каждый участок UI обязан становиться «component class».

### 27.21. Визуальная модель зависимостей

~~~text
                    ┌──────────────────────────────┐
                    │       Specialized UI         │
                    │ ProjectCard / ProjectDetails │
                    └──────────────┬───────────────┘
                                   │ inherits
                                   ▼
                    ┌──────────────────────────────┐
                    │        Common UI base        │
                    │ EntityCard / EntityDetails   │
                    │ common UI mechanisms         │
                    └──────────────┬───────────────┘
                                   │
                    composition    │
                    ┌──────────────▼──────────────┐
                    │ Complex independent widgets │
                    └─────────────────────────────┘

UI → Application → Domain → Infrastructure
~~~

### 27.22. Порядок архитектурной проверки

Перед реализацией следующей сущности сначала проверяется:

1. есть ли подходящая базовая UI-сущность;
2. что именно уже умеет база;
3. какие механизмы действительно относятся к будущему наследнику;
4. требуется ли независимый сложный объект;
5. существует ли уже общий application-механизм;
6. не возникнет ли дублирование.

После проверки выдаются только точечные изменения текущего кода.
