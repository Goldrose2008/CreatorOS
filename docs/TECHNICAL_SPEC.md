# Технический документ проекта

**Название приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия документа:** 2.2
**Тип продукта:** Desktop-приложение  
**Целевые платформы:** Windows / macOS / Linux

## Основные правила приложения
1. CreatorOS — универсальная рабочая среда для авторской деятельности, объединяющая управление объектами и задачами, полноценную базу знаний, а также подготовку, публикацию и анализ результатов.
2. Object — самостоятельный конечный продукт авторской деятельности. Каждый Object имеет один основной ObjectType.
3. Общие базовые свойства Object: уникальный идентификатор, ObjectType, название и описание. Системные свойства включают дату создания и дату последнего изменения.
4. Общими свойствами Object также являются прогресс и необязательный дедлайн. Реализация и правила расчёта прогресса будут определены отдельно. При создании и редактировании дедлайн можно включать или отключать; в форме флажок «Указать срок» включён по умолчанию.
5. Статусы и приоритет пока не включаются в согласованный общий набор свойств. Дата выпуска и другие подобные характеристики могут быть специфичными для ObjectType.
6. Object может иметь дочерние Object. Дочерние объекты участвуют в жизненном цикле родительского объекта; завершение родителя зависит от завершения его дочерних объектов. Детальные правила этого условия определяются отдельно.
7. Объекты связываются друг с другом самостоятельными отношениями. У отношения есть тип и роль (основной или дополнитель); роль относится к связи, а не к самому объекту.
8. Один Object может быть связан с несколькими родительскими Object.
9. ObjectType — самостоятельная настраиваемая сущность, определяющая дополнительные свойства и доступные функциональные возможности объектов данного типа. Пользователь может создавать собственные типы на основе возможностей, поддерживаемых приложением.
10. Объекты любого типа могут поддерживать дочерние объекты, задачи и завершение.
11. Задачи, публикации, аналитика, документы базы знаний, файлы, материалы и другие рабочие данные являются отдельными вспомогательными сущностями и не являются Object.
12. Вспомогательные сущности могут связываться с объектами в соответствии со своим назначением. Один и тот же вспомогательный материал может использоваться в нескольких контекстах.
13. База знаний является полноценной интегрированной частью CreatorOS и поддерживает самостоятельные документы, не привязанные к задачам или публикациям.
14. Содержимое документов базы знаний хранится в обычных Markdown-файлах в выбранном пользователем рабочем пространстве; текст документа не хранится исключительно в SQLite.
15. SQLite хранит структурированные сущности CreatorOS, метаданные документов, индекс содержимого и связей, а также данные, необходимые для быстрого поиска и навигации.
16. Markdown-файлы должны оставаться доступными для открытия и редактирования вне CreatorOS; изменение файла сторонним редактором должно приводить к обновлению индекса.
17. Индекс и связи должны восстанавливаться из доступных файлов; недоступность или повреждение индекса не должны приводить к потере содержимого документов.
18. Публикация связывается с объектом, поддерживающим публикации, и с Account; Platform определяется через Account.
19. Account выбирается из подключённых аккаунтов; account_id не вводится пользователем вручную.
20. Системные идентификаторы, даты создания и технические значения не редактируются пользователем вручную.
21. Статусы сущностей изменяются через предусмотренные действия и процессы, а не произвольным вводом.
22. Прогресс и приоритеты, определённые как системные производные значения, рассчитываются приложением.
23. Работа с файлами выполняется через отдельный application/infrastructure слой; UI не содержит файловых операций и SQL.
24. Все пользовательские тексты, зависящие от языка, получаются через text ID; переводы хранятся в едином resources/localization/localization.tsv.
25. Общие пользовательские формулировки используют единый ID, когда совпадают смысл и контекст; правила именования ключей и выбора канонических ID приведены в docs/LOCALIZATION.md.
## Технологический стек

### Основной стек

| Слой | Технология | Назначение |
|---|---|---|
| Основной язык | C++20 | Доменная модель, application services, инфраструктура, интеграции и UI |
| Desktop framework | Qt 6 | Окна, GUI, события, SQL, сеть и кроссплатформенная основа |
| Desktop UI | Qt Widgets | Основной нативный интерфейс приложения |

Приложение использует Qt 6 и C++20. Состав Qt-модулей ограничен функциональными потребностями приложения и требованиями к распространению.

Целевая архитектура:

~~~text
                         CreatorOS

             ┌──────────────┴──────────────┐
             │                             │
        Qt Presentation               C++ Application Core
             │                             │
      ┌──────┼──────┐              ┌───────┼────────┐
      │      │      │              │       │        │

      │      │      │              │       │        │
~~~

Главное правило:

> **Qt Widgets отвечает за прикладное представление. C++ отвечает за данные, правила и действия приложения. HTML/CSS/JavaScript не являются частью текущего desktop UI.**

### Принцип native UI и компонентов

Прикладной UI CreatorOS строится из целостных C++/Qt Widgets-классов. Главный критерий выделения класса — самостоятельная ответственность, а не стремление вынести каждый визуальный фрагмент в отдельный «кирпичик».

UI-класс может одновременно содержать собственную структуру QWidget, дочерние widgets, layout, визуальное оформление, локальное состояние, обработчики пользовательских действий и Qt signals/slots.

~~~text
Base UI class
   ↓ inheritance
Specialized UI class
   ├── inherited visual structure
   ├── inherited common behavior
   └── specialized behavior
~~~

Внутри класса используется обычная composition из Qt-объектов:

~~~text
ObjectCard
├── QLabel
├── QPushButton
├── QProgressBar
└── optional specialized QWidget
~~~

Наследование используется, когда один UI-класс действительно является специализированной разновидностью другого.

~~~text
Card
  ↓
EntityCard
  ├── ObjectCard
  └── TaskCard
~~~

Специализированные классы переиспользуют общий layout, визуальное оформление и поведение базового класса и добавляют только свою уникальную часть.

Страницы также могут образовывать иерархии, когда существует общий контракт и общее поведение. Если страницы только случайно похожи внешне, они остаются отдельными классами.

### Принцип UI ↔ Application

~~~text
Qt UI class
   ↓
Application Service / Use Case
   ↓
Domain
   ↓
Repository / Adapter
   ↓
SQLite / File System / External API
~~~

UI-класс отвечает за пользовательское представление и взаимодействие. Application/domain отвечают за бизнес-правила и прикладные операции. Infrastructure отвечает за конкретные технические процессы.

### Принцип визуального стиля

Глобальная визуальная система реализуется в C++:

~~~text
CreatorStyle : QProxyStyle
      │
      ├── Colors / palette
      ├── Typography metrics
      ├── Control metrics
      ├── Spacing / radii
      ├── Hover / focus / active states
      └── Common control drawing
               │
               ▼
       Custom QWidget / QPainter
~~~

QStyle/QProxyStyle задаёт общие правила. Отдельные сложные компоненты используют собственную отрисовку через QPainter, не дублируя дизайн-токены.

Qt Style Sheets допускаются только локально, когда они действительно упрощают конкретный небольшой визуальный сценарий. QSS не является основной системой дизайна приложения.

### Принцип API и интеграций

Интеграции организуются в C++:

~~~text
src/integrations/
├── youtube/
├── rutube/
├── vk_video/
├── dzen/
└── common/
~~~

Каждый адаптер получает отдельный внутренний контракт и скрывает детали конкретной площадки.

~~~text
authorize()

create/update metadata
publish/schedule
~~~

Не все операции обязаны существовать у каждой платформы. Адаптер отражает реальные возможности API.

## 1. Назначение приложения

CreatorOS — универсальная рабочая среда для авторской деятельности. Она объединяет управление объектами и задачами, полноценную базу знаний на Markdown-файлах и инструменты подготовки, публикации и анализа результатов. Приложение подходит для разработки игр, видеоблогинга, написания книг, исследований и других процессов, в которых пользователь создаёт конечные продукты и организует связанную с ними работу.

Основные направления работы:

```text
Рабочее пространство
├── Объекты и задачи
├── База знаний
│   ├── Markdown-документы и папки
│   ├── Ссылки, обратные ссылки и теги
│   └── Поиск и граф связей
├── Создание и развитие объектов
└── Публикации и аналитика
```

Пример: проект разработки игры может содержать задачи реализации механики, Markdown-документ с техническим описанием, заметки о принятых решениях, список ошибок и материалы для будущего видеоролика. Эти элементы связаны между собой, но сохраняют собственные назначения.

Главная цель:

> CreatorOS помогает автору организовать работу и знания в единой среде, сохраняя доступ к документам в обычных файлах и позволяя сосредоточиться на содержательных решениях.

## 1.1. Продуктовая концепция и границы CreatorOS

CreatorOS сочетает три равноправно связанные области: управление объектами и рабочими процессами, полноценную базу знаний и подготовку/публикацию результатов. Объекты представляют конечные продукты, задачи и другие вспомогательные сущности обеспечивают организацию работы, база знаний сохраняет и связывает накопленные знания, а публикационные и аналитические инструменты обслуживают соответствующие типы объектов. Ни одна из областей не должна сводиться к приложению-дополнению для другой. База знаний должна быть полезна сама по себе и одновременно интегрироваться с проектами, задачами, материалами и контентом.

CreatorOS использует сильные идеи приложений для заметок и знаний, включая Obsidian-подобные Markdown-документы, внутренние ссылки, обратные ссылки, теги, поиск и граф связей. При этом продукт не является копией Obsidian с добавленным списком задач: проекты, задачи, сроки, материалы, публикации и аналитика остаются полноценными структурированными сущностями со своими сценариями и правилами.

База знаний не ограничивается документами, прикреплёнными к задачам. Пользователь может создавать самостоятельные заметки, справочники, технические спецификации, дневники разработки, исследования и другие документы, а затем связывать их между собой и с рабочими сущностями CreatorOS. Базовый опыт работы со знаниями включает дерево папок, Markdown-редактор с предварительным просмотром, внутренние ссылки, обратные ссылки, теги, поиск по названию и содержимому и граф связей. Эти возможности должны развиваться как единый рабочий процесс, а не как несвязанные инструменты.

CreatorOS предназначен для разных авторских процессов, а не только для разработки игр или видеоблогинга. Шаблоны и типы рабочих пространств могут учитывать разные сценарии — разработку, видеопроизводство, книги, исследования и другие проекты — без жёсткого ограничения доменной модели одним видом деятельности.

## 2. Основная модель предметной области

### 2.1. Object

Object — самостоятельный конечный продукт авторской деятельности. Это базовая предметная сущность CreatorOS, объединяющая ранее рассматривавшиеся Project и Content на концептуальном уровне. Object не является контейнером для всех данных рабочего процесса: он представляет именно создаваемый результат.

Примеры Object:
- Project — самостоятельный крупный результат, который может включать другие объекты;
- Video — видеоматериал;
- Article — полноценная статья;
- Post — самостоятельная публикация для социальной сети или другой площадки;
- Game — игра;
- Book — книга;
- Research — исследование.

Object может существовать без дочерних объектов и вспомогательных сущностей. Он имеет собственный жизненный цикл и может быть завершён в соответствии с правилами своего типа и состоянием дочерних объектов.

Каждый Object имеет ровно один основной ObjectType. Дополнительная классификация при необходимости может обеспечиваться категориями, тегами и другими классификаторами, не заменяющими основной тип.

Для организации объектов в серии, рубрики и другие группы предполагается предусмотреть общий механизм организации и группировки Object. Это не отдельное специфическое свойство Video или Shorts. Конкретная модель такого механизма и способы представления групп будут определены позднее.

**Общие базовые свойства Object:**
- уникальный идентификатор;
- основной ObjectType;
- название;
- описание.

**Общие системные свойства Object:**
- дата создания;
- дата последнего изменения.

**Дополнительные общие свойства Object:**
- прогресс — общее свойство всех Object. Правила его определения, расчёта и обновления будут разработаны отдельно;
- дедлайн — необязательный срок, который может быть указан для Object любого типа. При создании и редактировании пользователь может включить или отключить его указание. В форме флажок «Указать срок» включён по умолчанию. В технической документации используется термин «дедлайн»; для короткой подписи в интерфейсе предварительно предлагается «Срок».

Статусы и приоритет на данном этапе не включаются в согласованный общий набор свойств Object и будут рассмотрены отдельно либо не будут добавлены. Дата выпуска и другие характеристики, смысл которых зависит от вида конечного продукта, относятся к дополнительным свойствам соответствующего ObjectType.

### 2.2. ObjectType

ObjectType — самостоятельная сущность, определяющая тип объектов. В приложении предусмотрены предустановленные типы; пользователь также может создавать и настраивать собственные типы.

Все ObjectType представлены одной универсальной сущностью и общей моделью данных. Различия между типами задаются их настройками и данными, а не отдельными C++ классами или наследниками ObjectType.

Предустановленные типы (Project, Video, Shorts, Article, Post, Game, Book) создаются как обычные записи в базе данных при первоначальной установке приложения. Они не являются специальными программными классами или неизменяемыми системными типами.

Пользователь может изменять предустановленные ObjectType, в том числе переименовывать их и менять доступные настройки, а также создавать новые типы и удалять существующие. Предустановленные типы не должны иметь специальных ограничений на редактирование только из-за того, что они поставляются вместе с приложением.

Удаление ObjectType, который уже используется существующими Object, не должно приводить к автоматическому удалению этих Object. Перед удалением такого типа пользователь должен переназначить связанные с ним Object на другой ObjectType. Если тип не используется, его можно удалить без этого дополнительного действия.

Тип определяет:
- набор дополнительных свойств объектов этого типа;
- типы значений этих свойств (например, текст, число, логическое значение, список значений, ссылка на другую сущность или список ссылок);
- доступные объектам функциональные возможности и соответствующие ограничения.

Общие базовые, системные и согласованные общие дополнительные свойства Object не должны дублироваться в конфигурации каждого типа. Конкретный состав дополнительных свойств, правила их хранения и валидации будут определены при проектировании системы типов.

Функциональные возможности типа выбираются из механизмов, реализованных в CreatorOS. Пользовательская конфигурация ObjectType может включать и настраивать поддерживаемые приложением возможности, но не создаёт произвольную новую программную функциональность.

Предполагается предусмотреть возможность добавления пользователем собственных свойств: общих для всех Object и специфических для выбранных ObjectType. Такие свойства позволят учитывать индивидуальные сценарии работы без включения узкоспециализированных характеристик в стандартную модель приложения. Конкретная модель пользовательских свойств и правила их настройки будут определены отдельно.
Также предполагается, что пользователь сможет удалять некоторые предустановленные необязательные свойства. 

ObjectType может включать функциональную возможность публикации. Если эта возможность включена для типа, у объектов этого типа становятся доступны связанные с публикацией настройки, включая выбор Platform, а также свойство Object «Планируемая дата выпуска». Если возможность отключена, эти элементы не должны навязываться объектам данного типа. Планируемая дата выпуска относится к Object, а не к отдельной Publication. Конкретный состав публикационных данных и правила Publication будут определены отдельно.

ObjectType может задавать список Platform — ссылок на соответствующие сущности справочника платформ — как исходный список площадок для объектов этого типа. При создании Object этот список используется как начальное значение; один Object может быть предназначен для нескольких Platform одновременно, а пользователь может изменить список у конкретного Object, удалив или добавив Platform. Таким образом, список у ObjectType задаёт значение по умолчанию, а не жёсткое ограничение доступных площадок. Конкретные списки Platform для каждого ObjectType и возможные ограничения совместимости (например, YouTube для Video и Shorts, LitRes для Book) будут рассмотрены отдельно при проектировании сущности Platform.

#### Предварительно согласованный состав основных ObjectType

Для текущего проектирования в качестве основных типов рассматриваются:
- Project;
- Video;
- Shorts;
- Article;
- Post;
- Game;
- Book.

**Project** на текущем этапе не имеет дополнительных специфических свойств и использует только общие свойства Object. Его особенности определяются назначением и отношениями с другими объектами, а не отдельными полями. Это решение не является окончательным ограничением: если в дальнейшем появится практическая необходимость, для Project можно будет определить дополнительные свойства.

**Video и Shorts** являются двумя самостоятельными ObjectType:
- **Video** — обычное видео;
- **Shorts** — короткое самостоятельное видео, например YouTube Shorts или Instagram Reels.

Один Video или Shorts может быть связан с одним или несколькими объектами другого формата, если материал перерабатывается из одного формата в другой. Такая возможность не должна искусственно ограничиваться типом объекта; конкретные виды отношений будут определены отдельно.

Для Video и Shorts согласованы следующие положения:
- отдельные свойства для подготовки видео (например, сценарий, план монтажа или исходники) на текущем этапе не вводятся: соответствующие данные могут быть представлены задачами, документами базы знаний, файлами, материалами или связанными Object;
- отдельные этапы подготовки и статусы Video/Shorts на текущем этапе не определяются;
- отдельное свойство для серий, рубрик или групп не вводится. Для организации Video и Shorts предполагается использовать будущий общий механизм организации и группировки Object.

**Article** — полноценная статья, например материал для блога, сайта или онлайн-журнала.

**Post** — самостоятельная публикация для социальной сети или другой площадки, обычно более компактная и ориентированная на формат соответствующей площадки.

Article и Post являются разными ObjectType, но на текущем этапе для них согласован одинаковый набор специфических свойств и правил:
- отдельное встроенное свойство «Язык» не вводится. При необходимости пользователь сможет добавить его как собственное общее свойство или свойство соответствующего ObjectType;
- отдельные этапы подготовки и свойства, связанные с подготовкой материала, не вводятся;
- отдельные свойства для серий, рубрик и групп не вводятся. Для организации Article и Post предполагается использовать будущий общий механизм организации и группировки Object.

Article и Post могут быть связаны друг с другом как самостоятельные Object; преобразование материала из одного формата в другой не ограничивается направлением. Конкретные виды отношений будут определены при проектировании общей модели отношений Object. Создание языковых версий одного материала на текущем этапе не предусматривается; такая возможность может быть рассмотрена в будущем.

Эти решения не определяют структуру Publication и не устанавливают правила связи Account с Platform; соответствующие вопросы рассматриваются отдельно.


**Game** — самостоятельный объект, представляющий создаваемую игру. Тип не ограничивается видеоиграми: он должен подходить и для настольных, карточных и других видов игр. Пользователь самостоятельно организует работу над игрой; CreatorOS предоставляет инструменты для этого, но не предписывает конкретный рабочий процесс.

Для Game согласованы следующие положения:
- необязательное свойство **«Версия»**, позволяющее указать версию игры, например 1.0 или 1.1;
- необязательное свойство **«Жанр»**;
- необязательное свойство **«Формат первого публичного выпуска»** со значениями «Демоверсия», «Ранний доступ» и «Полноценный релиз». Оно определяет, с какого варианта игра начнёт публично выходить, а не текущий этап или статус разработки;
- отдельные встроенные этапы или статусы разработки не вводятся. Организацию процесса пользователь определяет самостоятельно с помощью задач и других возможностей CreatorOS;
- отдельные встроенные свойства для подготовки игры не вводятся. Для связанных материалов, документов и рабочих данных используются соответствующие вспомогательные сущности и инструменты приложения;
- DLC, продолжения, ремейки и другие самостоятельные продукты могут быть отдельными Object. Пользователь самостоятельно определяет, создавать ли их как отдельные объекты и как организовывать связи между ними; тип Game не должен навязывать единственную схему организации;
- языковые версии игры как отдельные связанные Object на текущем этапе не предусматриваются.


**Book** — самостоятельный объект, представляющий создаваемую книгу как конечный продукт. ObjectType Book охватывает книги разных видов и форматов, включая бумажные, электронные и аудиокниги. Тип описывает саму книгу независимо от того, как пользователь организует её создание и подготовку.

Для Book согласованы следующие положения:
- необязательное свойство **«Жанр»**;
- отдельные встроенные свойства «Версия», «Издание», ISBN, количество страниц, количество слов и другие библиографические характеристики не вводятся. При необходимости пользователь сможет добавить их как собственные свойства;
- понятие публикации для Book на текущем этапе охватывает все способы публикации и распространения книги, включая цифровые площадки, издательства и распространение печатных изданий. Возможное разделение этих способов будет рассмотрено отдельно в будущем;
- отдельные встроенные этапы или статусы работы над книгой не вводятся. Пользователь самостоятельно организует процесс с помощью задач и других возможностей CreatorOS;
- отдельные встроенные свойства для хранения структуры книги, глав, персонажей, содержания, заметок и материалов не вводятся. Для организации этих данных используются соответствующие вспомогательные сущности и инструменты приложения;
- отдельные правила или свойства для серий, циклов, томов, сборников, переизданий и переработанных версий не вводятся. Пользователь самостоятельно определяет, как организовать такие материалы и нужны ли для них отдельные Object;
- языковые версии книги как отдельные связанные Object на текущем этапе не предусматриваются.


### 2.3. Связи между Object

На текущем этапе предусматривается один тип отношений между Object: **«родительский объект — дочерний объект»**. Отношение направленное: оно определяет родительский и дочерний Object. Дополнительные типы отношений на данном этапе не вводятся; необходимость в них может быть рассмотрена позднее на основании практических сценариев использования.

Связь универсальна: совместимость ObjectType не ограничивается. Любой Object может быть родительским или дочерним по отношению к Object любого типа.

Иерархия объектов обладает следующими свойствами:
- один Object может иметь несколько родительских объектов;
- один Object может иметь любое количество дочерних объектов;
- Object может одновременно быть родительским и дочерним;
- вложенность объектов не ограничивается одним уровнем;
- циклические отношения запрещены: объект не может быть своим собственным предком или потомком, в том числе через цепочку отношений.

У каждого отношения есть роль дочернего Object в контексте конкретного родительского Object. На текущем этапе предусматриваются следующие роли:
- **основной** — основной продукт, создаваемый в рамках родительского Object;
- **дополнительный** — побочный или сопутствующий продукт, создаваемый в рамках родительского Object;
- **вспомогательный** — самостоятельный Object, создаваемый для поддержки работы над родительским Object, например отдельный результат исследования или анализа.

Роль показывает значимость и назначение дочернего Object относительно конкретного родителя, но не определяет порядок создания или выполнения, степень готовности либо самостоятельную ценность дочернего Object. Дополнительный и вспомогательный Object также могут быть крупными и самостоятельными продуктами.

Роль является характеристикой отношения, а не самого Object. Один и тот же дочерний Object может иметь разные роли по отношению к разным родителям. У одного родительского Object может быть несколько дочерних объектов с каждой из ролей. Роль Object в отношении со своим родителем не влияет на роли его собственных дочерних объектов.

Роль должна учитываться при определении прогресса родительского Object: основной дочерний Object влияет на прогресс родителя сильнее, чем дополнительный. Влияние вспомогательного Object на прогресс, конкретный алгоритм расчёта и веса ролей будут определены отдельно. На текущем этапе роль также используется для визуального различения дочерних объектов. Иные последствия роли пока не устанавливаются.

Роль может изменяться после создания отношения. Способ её первоначального назначения, значение по умолчанию и защита от случайного изменения будут определены при проектировании интерфейса. При создании связей с несколькими родителями роль относится к каждому отношению отдельно и может различаться. Удобство массового назначения одинаковой роли и последующей индивидуальной настройки будет рассмотрено при проектировании интерфейса.

На текущем этапе предполагается, что дочерние Object являются частью жизненного цикла родительского Object. Родительский Object не может быть завершён, пока не завершены все его дочерние Object. Если дочерний Object имеет несколько родителей, его завершение учитывается каждым из них. Возможность иных правил участия связанных объектов в жизненном цикле может быть рассмотрена позднее вместе с возможными дополнительными типами отношений.

Дополнительное название или описание отношения не предусматривается.
Стоит рассмотреть Роль как сущность (наподобие типа объекта). У сущности Роль может быть свойство Приоритет, в зависимости от которого могут определяться некоторые аспекты родительского или дочернего объекта. Например, как дочерний объект будет отображаться в родительском (визуальное различие, о котором мы говорили ранее между основным и дополнительным)

#### Представление и управление иерархией Object

Дочерние Object отображаются на странице родительского Object в отдельном блоке. Внутри блока дочерние объекты разделяются по роли: основные и дополнительные. Конкретное визуальное оформление различий между ролями будет определено при проектировании интерфейса.

Для дочернего Object предусматривается переход на его страницу. На странице Object также отображается список его родительских объектов в виде ссылок, позволяющих перейти к каждому из них. Если у объекта несколько родителей, отображаются все соответствующие ссылки. Во всех таких представлениях используется один и тот же Object, а не отдельные копии.

Предварительный вариант представления дочерних объектов — карточки. При этом интерфейс должен предусматривать возможность выбора пользователем другого способа отображения. Карточка или другой элемент списка должен показывать название и ObjectType, роль в контексте текущего родителя, прогресс, дедлайн и планируемую дату выпуска, если она задана. Статус также предполагается отображать после того, как система статусов Object будет спроектирована и реализована.

Вложенные уровни иерархии должны поддерживать раскрытие и сворачивание. Не требуется показывать всю вложенную структуру одновременно: пользователь должен иметь возможность управлять видимостью уровней. Конкретный способ визуализации вложенности будет определён при проектировании интерфейса. Если Object имеет нескольких родителей, он отображается как дочерний в контексте каждого из них, но остаётся одной сущностью.

Помимо страницы отдельного Object, предусматривается общая страница со списком всех Object независимо от наличия и характера отношений. Пользователь сможет сортировать и фильтровать объекты. На этой же странице должна быть предусмотрена возможность включать и отключать представление иерархии, чтобы использовать её как общий список или как визуализацию связей между объектами. Таким образом, отдельная страница иерархии пока не фиксируется как обязательная: её назначение может выполнять общая страница Object с переключаемым режимом представления.

В блоке дочерних объектов предусматриваются:
- сортировка по названию, ObjectType, роли, прогрессу, дедлайну и дате создания;
- возможность менять направление сортировки;
- ручная перестановка дочерних объектов с сохранением порядка отдельно для каждого родительского Object;
- возможность менять роль дочернего Object непосредственно в списке. Способ защиты от случайного изменения будет определён при проектировании интерфейса.

Добавление дочерних объектов должно поддерживать оба сценария: создание нового Object непосредственно из контекста родителя и добавление уже существующего Object. При создании Object в целом также предусматривается возможность сразу установить отношения с одним или несколькими существующими объектами, выбирая для каждого отношения направление: создаваемый Object будет родительским или дочерним по отношению к выбранному объекту. Роль задаётся для каждого отношения отдельно.

Удаление дочернего Object из блока означает удаление только соответствующего отношения. Перед удалением связи приложение должно запросить подтверждение; сам Object при этом сохраняется.

Удаление отношения удаляет только связь между объектами и не удаляет сами Object. При удалении Object все его отношения удаляются, но остальные связанные с ним Object сохраняются, если пользователь отдельно не выбрал их удаление.


#### Удаление Object и корзина

Удаление Object не должно приводить к его немедленному безвозвратному уничтожению. Предусматривается корзина удалённых объектов, из которой пользователь сможет восстановить объект.

- После удаления Object помещается в корзину; дата удаления фиксируется.
- Удалённый Object может быть восстановлен в течение 30 дней с даты удаления.
- По истечении 30 дней Object автоматически удаляется безвозвратно.
- Автоматическое окончательное удаление должно распространяться также на файлы и другие данные, относящиеся к удалённому Object и подлежащие удалению вместе с ним.
- Помещение Object в корзину и его восстановление не должны приводить к удалению или повреждению других самостоятельных Object. Правила обработки отношений и общих вспомогательных данных при удалении, восстановлении и окончательной очистке будут уточнены при проектировании соответствующих механизмов.

Конкретная реализация корзины, правила определения принадлежащих Object файлов и данных, поведение общих материалов, а также состав восстанавливаемых отношений определяются на этапах проектирования Domain, Infrastructure и Application.

### 2.4. Вспомогательные сущности и данные

Задачи, публикации, аналитика, документы базы знаний, файлы, материалы и другие данные рабочего процесса не являются Object. Это отдельные сущности со своими моделями, жизненными циклами и правилами.

Object может быть связан со вспомогательными сущностями в соответствии с назначением этих сущностей. Такие связи концептуально отличаются от отношений Object–Object и не превращают вспомогательную сущность в Object. Например, Object может быть связан со своими задачами, публикациями, документами базы знаний и файлами. Один и тот же вспомогательный материал может использоваться в нескольких контекстах.

Все типы Object поддерживают возможность иметь дочерние Object, задачи и завершение. Наличие этих возможностей не означает, что у каждого объекта обязательно должны быть дочерние объекты или задачи.

### 2.5. База знаний и Markdown-документы

База знаний — полноценная часть CreatorOS, а её документы являются самостоятельными вспомогательными сущностями, а не Object.

Документы базы знаний:
- хранятся как обычные файлы Markdown (.md) в папках выбранного пользователем рабочего пространства;
- доступны для открытия и редактирования сторонними редакторами без экспорта из CreatorOS;
- поддерживают стандартные возможности Markdown, включая заголовки, списки, таблицы, кодовые блоки и изображения;
- могут содержать внутренние ссылки на другие документы и ссылки на сущности CreatorOS;
- поддерживают теги, обратные ссылки (backlinks), поиск и граф связей;
- могут создаваться из шаблонов и организовываться в папки;
- могут существовать независимо от задач и публикаций и связываться с одним или несколькими Object и другими документами;
- не обязаны физически находиться в папке какого-либо объекта.

Используется гибридная модель хранения с разделением ответственности:
- **Markdown-файлы** — основное и переносимое хранилище текста документов; пользователь может читать и редактировать их вне CreatorOS.
- **SQLite** — основное хранилище структурированных сущностей CreatorOS, а также метаданных документов, поискового индекса, результатов разбора Markdown и связей между документами и рабочими сущностями.
- **Файловая система** — хранилище вложений и других пользовательских материалов; документы базы знаний могут ссылаться на эти файлы.

Индекс SQLite является производным от файлов и может быть восстановлен повторным сканированием рабочего пространства. SQLite не должна становиться единственной копией текста Markdown-документов. При конфликте источников содержимое Markdown-файла считается авторитетным для текста документа, а SQLite — для структурированных сущностей и служебных связей CreatorOS.

Приложение должно учитывать внешние изменения файлов. При перемещении, переименовании или удалении документа необходимо обновлять индекс и корректно обрабатывать неразрешённые ссылки. Если файл недоступен, запись индекса не должна приводить к потере самого документа или создавать впечатление, что файл существует.

Путь к документу не является единственной устойчивой идентичностью. Внутренние ссылки должны разрешаться с учётом переименования и перемещения файлов настолько, насколько это возможно на основе идентификаторов и актуального индекса.

## 3. Task

Task — отдельная вспомогательная сущность, используемая для организации работы над Object. Задача не является Object и не представляет конечный продукт. Задачи могут быть связаны с объектами любого типа.

Task поддерживает собственную иерархию задач. Связь задачи с Object и связь с родительской Task являются разными отношениями. Модель связей задачи с объектами должна учитывать предметные сценарии CreatorOS и не должна ограничиваться только Project или Content. Конкретная структура этих связей будет определена при проектировании задач в рамках целевой модели Object.

Статусы Task:

~~~text
todo
in_progress
done
cancelled
~~~

Статус изменяется через предусмотренный workflow, а не произвольным вводом в редакторе.

Приоритет является системным производным значением. Система рассчитывает его по контексту задачи, срокам, зависимостям и влиянию задачи; пользователь не изменяет приоритет вручную.

Дедлайн задаётся для конкретной задачи и используется системой при последующем расчёте приоритета.

Создание/редактирование Task не должно позволять пользователю изменять системный контекст, статус или приоритет через обычную форму редактора.

## 4. Publication

Publication — отдельная вспомогательная сущность, представляющая публикацию объекта на внешней площадке. Publication связывается с конкретным Object, который поддерживает возможность публикации, и конкретным Account. Не каждый Object обязан поддерживать публикации; доступность этой возможности определяется ObjectType.

Основные направления данных:

```text
object_id
platform_id
account_id
status
scheduled_at
published_at
external_id
external_url
title
description
publication_data
error_message
```

## 5. Platform и Account

Platform описывает площадку публикации.

Account представляет конкретный аккаунт/канал пользователя на этой площадке.

Связь:

```text
Platform
    ↓
Account
    ↓
Publication
    ↓
Object
```

В форме создания и редактирования Account пользователь выбирает существующую Platform из выпадающего списка. Если список Platform пуст, форма создания Account не открывается; пользователю показывается сообщение с указанием сначала добавить Platform. Выпадающий список Platform раскрывается вниз при обычных условиях отображения.

## 6. EntityCard

EntityCard — базовый C++/Qt-класс для целостного UI-представления карточки сущности.

База знает общие механизмы карточки: поверхность, заголовок, описание, статус, прогресс, метаданные, области дополнительного содержимого и действия. Эти механизмы могут существовать в базе заранее, даже если конкретному наследнику часть из них не нужна.

База не знает конкретный ObjectType или тип вспомогательной сущности. В ней не должно быть ветвлений вида `if (isProject) ... else if (isTask) ...`.

Конкретная сущность определяется специализированным наследником:

~~~text
Card
  ↓
EntityCard
  ├── ObjectCard
  ├── TaskCard
  ├── AssetCard
  └── PublicationCard
~~~

Наследник настраивает и заполняет общие UI-механизмы, показывает или скрывает подходящие области и добавляет только специфические элементы и поведение. Общий визуальный каркас не копируется.

## 7. EntityDetails

EntityDetails — базовый C++/Qt-класс для целостных подробных представлений сущностей.

База знает UI-механизмы details-представления: прокрутку, общую структуру страницы, навигационную область, header, стандартные состояния, summary/info-области, действия, дополнительные content-регионы и управление их видимостью.

Базовый EntityCard содержит повторяемые UI-механизмы. Конкретное содержание и условия показа определяет специализированная карточка.

~~~text
EntityDetails
   ├── ObjectDetailsPage
   └── TaskDetails
~~~

Например, `ObjectDetailsPage` может отображать общие свойства Object и специфические свойства его ObjectType, а `TaskDetails` — только те механизмы, которые подходят Task. База предоставляет механизм, наследник принимает решение.

База не проверяет тип конкретной сущности и не содержит entity-specific ветвления.

Если в details появляется действительно независимый сложный объект с собственным контрактом и поведением, он подключается через composition. Простая разметка, QLabel, QPushButton и layout остаются внутри details-класса.

Бизнес-операции, доменные правила и инварианты выполняются через application/domain слои.

## 8. ConfirmModal

ConfirmModal является единым механизмом подтверждения действий в native UI.

Концептуальный поток:

~~~text
Qt UI
↓
ConfirmModal
↓
решение пользователя
↓
callback
↓
Application Service / Use Case
↓
C++ действие
~~~

Отображение, состояние диалога и пользовательский выбор принадлежат UI-компоненту. Само удаление или изменение сущности выполняется C++ service после проверки правил.

## 8.1 Правило самодостаточности UI-компонента

Компонент отвечает за собственное:
- визуальное состояние;
- дочерние widgets;
- сигналы/слоты;
- локальные UI-правила;
- передачу пользовательского намерения наружу.

Компонент не выполняет SQL и не содержит бизнес-правила.

## 13. ООП-архитектура CreatorOS

C++ является основной ООП-моделью CreatorOS. Общий принцип организации кода действует во всех слоях приложения, а не только в UI: связанные данные и поведение одной ответственности остаются вместе, а повторяющиеся механизмы объединяются по смыслу и контракту. Предпочтительны передача данных/параметров и типобезопасная конфигурация вместо копирования одинаковой реализации. Уникальные правила остаются специализированными; похожие фрагменты с разными контрактами не объединяются искусственно. Наследование используется при совместимом контракте и отношении «является», composition — для частей с самостоятельной ответственностью. Абстракции создаются только при подтверждённой пользе для повторного использования, тестируемости, заменяемости или ясности границ.

~~~text
«является» + общий контракт + общее поведение
        → наследование

«содержит» / «использует» + независимый контракт
        → композиция

только совпадают поля
        → не повод для наследования
~~~

UI-класс не обязан разделять визуал и UI-поведение на разные архитектурные классы. Пара .h/.cpp является техническим устройством C++ для объявления и реализации одного класса, а не архитектурным разделением UI и logic. Неиспользуемые файлы удаляются только после проверки ссылок, CMake и зависимостей; само наличие пары .h/.cpp не является причиной для удаления.

### Общие UI-сущности и специализация

Каждый повторно используемый тип UI-сущности — карточка, список, страница подробностей, редактор, модальное окно и т. п. — централизует свой визуальный каркас, стандартное поведение, локальное UI-состояние и общие действия в одном компоненте. Общий компонент определяет, какие элементы существуют, как они размещены и что происходит при стандартном взаимодействии.

Специализированные UI-классы конкретных доменных сущностей (например, ObjectCard и TaskCard) по возможности передают в общий компонент данные и конфигурацию: заголовок, описание, метаданные, статус, прогресс, подписи действий и идентификатор/маршрут перехода. Они не должны повторно собирать одинаковую разметку и повторно реализовывать стандартное поведение, уже предоставленное общим компонентом.

Если конкретная сущность требует дополнительной надписи, метаданных или действия, расширение должно подключаться через предусмотренный общий механизм (например, дополнительный metadata/action widget или типобезопасную конфигурацию). Не создавать новый архитектурный класс или отдельную копию UI только ради единичного отличия. При этом общий компонент не должен содержать ветвлений по конкретным ObjectType или по типам вспомогательных сущностей: специализированные данные передаются извне, а уникальное поведение выражается небольшим явным расширением.

Эти правила относятся ко всем повторно используемым UI-сущностям, а не только к карточкам. При рефакторинге нужно переиспользовать существующие EntityCard, EntityDetails, EntityHeader, EntityList, EditorDialog, FormField, ConfirmModal и StateWidget там, где их контракт подходит, расширяя его при необходимости вместо создания параллельных реализаций.

### Типизированные страницы и расширяемые метаданные

Страницы списков должны строиться на общем механизме, который централизует стандартный каркас и поведение: загрузку и обновление данных, loading/empty/error состояния, список, общие поля и типовые действия. Конкретная страница передаёт тип сущности, источник данных/адаптер, фабрику представления элемента и конфигурацию. Общая часть не должна проверять конкретный тип сущности через ветвления.

Общие поля страницы задаются единым контрактом, а метаданные описываются типизированными элементами/представлениями: у разных сущностей может быть разное число полей и разные значения. Уникальные действия и дополнительные секции подключаются через явные расширения или callbacks, а не через копирование страницы. Типизация должна сохраняться на границе конкретной страницы и адаптера; не следует сводить все данные к неструктурированным строкам или универсальным словарям без необходимости. При выборе реализации учитывать ограничения Qt MOC: шаблонный механизм не должен требовать Q_OBJECT там, где Qt signals/slots необходимы; конкретные QObject-страницы могут оставаться небольшими адаптерами.

### Типизированные репозитории

Репозитории могут использовать общий типизированный инфраструктурный механизм для повторяющихся операций с запросами: выполнение SQL, привязка параметров, обработка ошибок, чтение одной/нескольких строк и общие шаблоны результата. Конкретные репозитории сохраняют собственные контракты, SQL и преобразование строки результата в соответствующую доменную модель. Специфические транзакции и бизнес-ограничения не прячутся в универсальном CRUD-классе. Общий механизм должен сокращать дублирование, не ослабляя типизацию и не стирая различия предметных сущностей.

Повторяющийся прикладной механизм также не должен копироваться по сущностям только из-за разных типов данных. Если разные ObjectType или вспомогательные сущности используют одинаковую часть алгоритма, повторяемая часть должна находиться в общем типобезопасном механизме; специализированный класс добавляет уникальные проверки и правила.

При этом domain и application остаются независимыми от конкретной визуальной реализации. Бизнес-правила не переносятся в QWidget только ради уменьшения числа файлов. UI-компоненты и страницы не обращаются к SQLite и не выполняют файловые операции напрямую.

Интерфейсы репозиториев и интеграций вводятся там, где они дают реальную заменяемость и тестируемость. Искусственные абстракции не создаются. Файловая структура должна отражать ответственность компонентов; перемещение каталогов и удаление файлов выполняются только после проверки фактических зависимостей и сборки.

## 14. Стили

Визуальное оформление прикладного интерфейса выполняется нативными средствами Qt.

Целевая организация:

~~~text
src/ui/
├── style/
│   ├── CreatorStyle.*
│   ├── Colors.*
│   ├── Metrics.*
│   └── Icons.*
├── components/
├── pages/
├── shell/
└── localization/
~~~

CreatorStyle наследуется от QProxyStyle и является центральной точкой общих визуальных правил. Colors и Metrics хранят дизайн-токены приложения. Icons предоставляет единый доступ к иконкам из Qt Resource System.

Для сложных или нестандартных компонентов используется собственная отрисовка через QPainter. Компоненты не должны самостоятельно дублировать общие цвета, размеры, отступы и состояния.

Интерфейс использует единую визуальную систему: цвета, размеры, отступы, радиусы, типографика и состояния элементов определены согласованно и применяются на всех страницах.

Qt Style Sheets допускаются только локально, когда это действительно упрощает небольшой визуальный сценарий. QSS не является основой дизайн-системы.

## 15. База данных и файловое хранилище

SQLite является локальной базой структурированных данных приложения. Содержимое Markdown-документов хранится в обычных файлах в выбранном пользователем рабочем пространстве.

Доступ к структурированным данным строится только через C++ infrastructure/repository layer:

~~~text
Native UI
↓
Application Service / Use Case
├── Repository → Qt SQL / QSQLITE → SQLite
└── File Service → File System → Markdown documents and attachments
~~~

UI-компоненты и страницы не работают с БД напрямую и не выполняют файловые операции напрямую.

### DatabaseManager

Отдельный инфраструктурный объект отвечает за открытие подключения, проверку/создание схемы, применение миграций, управление транзакциями и закрытие подключения. SQLite-файл хранится в пользовательском каталоге данных приложения, а не рядом с исполняемым файлом.

Репозитории отвечают за операции структурированных сущностей и индекса документов, например `IProjectRepository`, `IContentRepository`, `ITaskRepository` и `IDocumentIndexRepository`.

### Markdown и файловый сервис

Отдельный файловый сервис отвечает за чтение, создание, запись, переименование, перемещение и удаление Markdown-файлов, проверку доступности и синхронизацию индекса. Содержимое документа не дублируется в SQLite как единственная или основная копия. SQLite хранит индексируемые метаданные, теги, разобранные внутренние ссылки и связи с сущностями приложения. Индекс должен поддерживать полное перестроение из рабочего пространства, а операции с файлами и индексом должны обрабатывать частичные ошибки без автоматического удаления пользовательских данных.

CreatorOS должен обнаруживать изменения, сделанные внешними редакторами, и обновлять индекс. При недоступности файла, повреждённой ссылке или конфликте изменения приложение показывает понятное состояние и не удаляет данные автоматически.

### Миграции

Структура SQLite изменяется последовательными SQL-миграциями. Версия схемы хранится в самой БД. Миграции контролируются механизмом версии схемы и выполняются транзакционно, когда это возможно.

## 16. Основные пользовательские возможности

CreatorOS предназначен для организации авторской деятельности и работы с объектами разных типов в рамках локального рабочего пространства пользователя.

Основные возможности:
- управление Object разных типов, связями между объектами, задачами, сроками, статусами, приоритетами и жизненным циклом;
- полноценная база знаний из обычных Markdown-файлов с организацией по папкам;
- создание, редактирование, переименование, перемещение и удаление документов с обработкой ошибок файловой системы;
- переходы по внутренним ссылкам, просмотр обратных ссылок, теги и граф связей;
- поиск по документам и структурированным сущностям;
- шаблоны документов и рабочих процессов для разных типов авторских проектов;
- связывание документов с Object, Tasks, Publications и другими документами;
- управление ObjectType, свойствами объектов и доступными возможностями типов;
- обзор проектов, задач, документов и ближайших сроков на Dashboard;
- планирование работы и выпуска контента;
- хранение и повторное использование материалов и вложений;
- ведение публикаций и связь публикаций с аккаунтами платформ;
- доступные интеграции с платформами, автоматизация и сбор аналитики;
- возможность совместной работы с ролями и правами доступа;
- локализация интерфейса и AI-функции, в которых пользователь контролирует предложенные результаты.

SQLite хранит структурированные данные, метаданные и поисковый индекс базы знаний. Содержимое документов хранится в обычных Markdown-файлах, а вложения — в файловой системе. CreatorOS должен сохранять возможность работы с Markdown-файлами вне приложения и не должен делать SQLite единственным хранилищем текста документов.

## 17. Кроссплатформенность

Целевые desktop-платформы:

~~~text
Windows
macOS
Linux
~~~

Qt используется как основной кроссплатформенный framework.

Platform-specific код допускается только через явно выделенные adapters.

Для каждой ОС отдельно проверяются:

~~~text
window management
native dialogs
secure storage
browser/OAuth callback
font rendering
Qt Widgets rendering
application data directory
packaging
~~~

Общая предметная модель, application services, repositories и native UI-компоненты должны оставаться максимально платформонезависимыми.

## 18. Лицензирование

CreatorOS распространяется как proprietary/closed-source приложение; лицензии сторонних компонентов должны допускать такое распространение.

### Qt

Основной open-source вариант — использование LGPL v3 компонентов Qt при полном соблюдении LGPL.

Qt не является однородно лицензированным пакетом: в актуальном Qt 6.12 часть модулей доступна open-source пользователям только под GPL v3. Эти GPL-only модули не включаются в базовую proprietary-сборку без отдельного лицензионного решения.

Для CreatorOS принимаются следующие практические меры:

~~~text
Qt DLLs
↓
динамическая поставка
↓
license notices
↓
информация об исходниках LGPL-компонентов
↓
возможность замены/relinking согласно LGPL
~~~

Особое внимание:
~~~text
модульный состав Qt
лицензирование дополнительных Qt-модулей
Qt Network Authorization
изменения исходного кода Qt
~~~

### SQLite

SQLite используется через Qt SQL/QSQLITE. В документации Qt 6.12 SQLite указан как third-party компонент под SQLite Blessing.

### Прочие зависимости

Каждая дополнительная библиотека проверяется до включения в основной target:

~~~text
license
commercial redistribution
source/notice obligations
static/dynamic linking requirements
platform compatibility
~~~

В релизе CreatorOS должен существовать раздел О программе → Лицензии.

Этот раздел фиксирует технические требования к распространению, но не является индивидуальным юридическим заключением. Состав компонентов каждого распространяемого пакета и их лицензии должны соответствовать актуальным лицензионным текстам.
