# Технический документ проекта

**Название приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия приложения:** определяется единственным источником `src/app/AppInfo.h`
**Версия документа:** 2.4
**Тип продукта:** Desktop-приложение  
**Целевые платформы:** Windows / macOS / Linux

## Основные правила приложения
1. CreatorOS — универсальная рабочая среда для авторской деятельности, объединяющая управление объектами и задачами, полноценную базу знаний, а также подготовку, публикацию и анализ результатов.
2. Object — самостоятельный конечный продукт авторской деятельности. Каждый Object имеет один основной ObjectType.
3. Общие базовые свойства Object: целочисленный внутренний ID, глобальный UUID, ObjectType, название и описание. Системные свойства включают дату создания и дату последнего изменения.
4. Общими свойствами Object также являются прогресс и необязательный дедлайн. Реализация и правила расчёта прогресса будут определены отдельно. При создании и редактировании дедлайн можно включать или отключать; в форме флажок «Указать срок» включён по умолчанию.
5. Статусы и приоритет пока не включаются в согласованный общий набор свойств. Дата выпуска и другие подобные характеристики могут быть специфичными для ObjectType.
6. Object может иметь дочерние Object. Дочерние объекты участвуют в жизненном цикле родительского объекта; завершение родителя зависит от завершения его дочерних объектов. Детальные правила этого условия определяются отдельно.
7. Объекты связываются друг с другом самостоятельными отношениями. У отношения есть тип и одна из трёх ролей (основной, дополнительный или вспомогательный); роль относится к связи, а не к самому объекту.
8. Один Object может быть связан с несколькими родительскими Object.
9. ObjectType — самостоятельная настраиваемая сущность, определяющая дополнительные свойства и доступные функциональные возможности объектов данного типа. Пользователь может создавать собственные типы на основе возможностей, поддерживаемых приложением.
10. Объекты любого типа могут поддерживать дочерние объекты, задачи и завершение.
11. Задачи, публикации, аналитика, документы базы знаний, файлы, материалы и другие рабочие данные являются отдельными вспомогательными сущностями и не являются Object.
12. Вспомогательные сущности могут связываться с объектами в соответствии со своим назначением. Один и тот же вспомогательный материал может использоваться в нескольких контекстах.
13. База знаний является полноценной интегрированной частью CreatorOS и поддерживает самостоятельные документы, не привязанные к задачам или публикациям.
14. Содержимое документов базы знаний хранится в обычных Markdown-файлах в выбранном пользователем рабочем пространстве; текст документа не хранится исключительно в SQLite.
15. SQLite хранит структурированные сущности CreatorOS, метаданные документов, индекс содержимого и связей, а также данные, необходимые для быстрого поиска и навигации.
16. Markdown-файлы должны оставаться доступными для открытия и редактирования вне CreatorOS; изменение файла сторонним редактором должно приводить к обновлению индекса.
17. Индекс и связи должны восстанавливаться из доступных файлов; недоступность или повреждение индекса не должны приводить к потере содержимого документов.
18. Публикация связывается с объектом, поддерживающим публикации, и с Account; Platform определяется через Account.
19. Account выбирается из подключённых аккаунтов; account_id не вводится пользователем вручную.
20. Системные идентификаторы, даты создания и технические значения не редактируются пользователем вручную.
21. Статусы сущностей изменяются через предусмотренные действия и процессы, а не произвольным вводом.
22. Прогресс и приоритеты, определённые как системные производные значения, рассчитываются приложением.
23. Работа с файлами выполняется через отдельный application/infrastructure слой; UI не содержит файловых операций и SQL.
24. Все пользовательские тексты, зависящие от языка, получаются через text ID; переводы хранятся в едином resources/localization/localization.tsv.
25. Общие пользовательские формулировки используют единый ID, когда совпадают смысл и контекст; правила именования ключей и выбора канонических ID приведены в docs/LOCALIZATION.md.
## Технологический стек

### Основной стек

| Слой | Технология | Назначение |
|---|---|---|
| Основной язык | C++20 | Доменная модель, application services, инфраструктура, интеграции и UI |
| Desktop framework | Qt 6 | Окна, GUI, события, SQL, сеть и кроссплатформенная основа |
| Desktop UI | Qt Widgets | Основной нативный интерфейс приложения |
| Визуальная система | QStyle / QProxyStyle + QPainter | Единый визуальный стиль, состояния и специализированная отрисовка |
| UI-компоненты | C++ classes / QWidget | Переиспользуемые элементы интерфейса и страницы |
| Иконки | Qt Resource System + SVG/Qt Svg | Хранение и отображение иконок |
| Локализация | localization.tsv + LocalizationService | Единый исходник переводов и in-memory каталоги |
| База данных | SQLite через Qt SQL / QSQLITE | Локальное хранилище структурированных данных приложения |
| Сеть | Qt Network | HTTP/REST, загрузки, сетевые операции |

Приложение использует Qt 6 и C++20. Состав Qt-модулей ограничен функциональными потребностями приложения и требованиями к распространению.

### Принцип технологического стека

Целевая архитектура:

~~~text
                         CreatorOS
                            │
             ┌──────────────┴──────────────┐
             │                             │
        Qt Presentation               C++ Application Core
             │                             │
      ┌──────┼──────┐              ┌───────┼────────┐
      │      │      │              │       │        │
 MainWindow AppShell Pages     Services  Domain  Integrations
      │      │      │              │       │        │
      └──────┴──────┴──────────────┼───────┼────────┘
                                   │       │
                              Repositories  │
                                   │       │
                                SQLite   File System / APIs

~~~

Главное правило:

> **Qt Widgets отвечает за прикладное представление. C++ отвечает за данные, правила и действия приложения. HTML/CSS/JavaScript не являются частью текущего desktop UI.**

### Принцип native UI и компонентов

Прикладной UI CreatorOS строится из целостных C++/Qt Widgets-классов. Главный критерий выделения класса — самостоятельная ответственность, а не стремление вынести каждый визуальный фрагмент в отдельный «кирпичик».

UI-класс может одновременно содержать собственную структуру QWidget, дочерние widgets, layout, визуальное оформление, локальное состояние, обработчики пользовательских действий и Qt signals/slots.

~~~text
Base UI class
   ↓ inheritance
Specialized UI class
   ├── inherited visual structure
   ├── inherited common behavior
   └── specialized behavior
~~~

Внутри класса используется обычная composition из Qt-объектов:

~~~text
EntityCard
├── QLabel
├── QPushButton
├── QProgressBar
└── optional content widgets
~~~

Наследование используется, когда один UI-класс действительно является специализированной разновидностью другого и обладает самостоятельным контрактом или поведением.

~~~
Card
  ↓
EntityCard
  ├── TaskCard
  ├── AssetCard
  └── PublicationCard
~~~

Если сущности достаточно общего механизма карточки, отдельный специализированный класс не создаётся: страница формирует и настраивает экземпляр EntityCard напрямую. Специализированные классы переиспользуют общий layout, визуальное оформление и поведение базового класса и добавляют только действительно уникальную часть.

Страницы также могут образовывать иерархии, когда существует общий контракт и общее поведение. Если страницы только случайно похожи внешне, они остаются отдельными классами.

### Принцип UI ↔ Application

~~~text
Qt UI class
   ↓
Application Service / Use Case
   ↓
Domain
   ↓
Repository / Adapter
   ↓
SQLite / File System / External API
~~~

UI-класс отвечает за пользовательское представление и взаимодействие. Application/domain отвечают за бизнес-правила и прикладные операции. Infrastructure отвечает за конкретные технические процессы.

### Принцип визуального стиля

Глобальная визуальная система реализуется в C++:

~~~text
CreatorStyle : QProxyStyle
      │
      ├── Colors / palette
      ├── Typography metrics
      ├── Control metrics
      ├── Spacing / radii
      ├── Hover / focus / active states
      └── Common control drawing
               │
               ▼
       Custom QWidget / QPainter
~~~

QStyle/QProxyStyle задаёт общие правила. Отдельные сложные компоненты используют собственную отрисовку через QPainter, не дублируя дизайн-токены.

Qt Style Sheets допускаются только локально, когда они действительно упрощают конкретный небольшой визуальный сценарий. QSS не является основной системой дизайна приложения.

### Принцип API и интеграций

Интеграции организуются в C++:

~~~text
src/integrations/
├── youtube/
├── rutube/
├── vk_video/
├── dzen/

~~~

Каждый адаптер получает отдельный внутренний контракт и скрывает детали конкретной площадки.


Не все операции обязаны существовать у каждой платформы. Адаптер отражает реальные возможности API.

## 1. Назначение приложения

CreatorOS — универсальная рабочая среда для авторской деятельности. Она объединяет управление объектами и задачами, полноценную базу знаний на Markdown-файлах и инструменты подготовки, публикации и анализа результатов. Приложение подходит для разработки игр, видеоблогинга, написания книг, исследований и других процессов, в которых пользователь создаёт конечные продукты и организует связанную с ними работу.

Основные направления работы:

```text
Рабочее пространство
├── Объекты и задачи
├── База знаний
│   ├── Markdown-документы и папки
│   ├── Ссылки, обратные ссылки и теги
│   └── Поиск и граф связей
├── Создание и развитие объектов
└── Публикации и аналитика
```

Пример: проект разработки игры может содержать задачи реализации механики, Markdown-документ с техническим описанием, заметки о принятых решениях, список ошибок и материалы для будущего видеоролика. Эти элементы связаны между собой, но сохраняют собственные назначения.

Главная цель:

> CreatorOS помогает автору организовать работу и знания в единой среде, сохраняя доступ к документам в обычных файлах и позволяя сосредоточиться на содержательных решениях.

## 1.1. Продуктовая концепция и границы CreatorOS

CreatorOS сочетает три равноправно связанные области: управление объектами и рабочими процессами, полноценную базу знаний и подготовку/публикацию результатов. Объекты представляют конечные продукты, задачи и другие вспомогательные сущности обеспечивают организацию работы, база знаний сохраняет и связывает накопленные знания, а публикационные и аналитические инструменты обслуживают соответствующие типы объектов. Ни одна из областей не должна сводиться к приложению-дополнению для другой. База знаний должна быть полезна сама по себе и одновременно интегрироваться с проектами, задачами, материалами и контентом.

CreatorOS использует сильные идеи приложений для заметок и знаний, включая Obsidian-подобные Markdown-документы, внутренние ссылки, обратные ссылки, теги, поиск и граф связей. При этом продукт не является копией Obsidian с добавленным списком задач: проекты, задачи, сроки, материалы, публикации и аналитика остаются полноценными структурированными сущностями со своими сценариями и правилами.

База знаний не ограничивается документами, прикреплёнными к задачам. Пользователь может создавать самостоятельные заметки, справочники, технические спецификации, дневники разработки, исследования и другие документы, а затем связывать их между собой и с рабочими сущностями CreatorOS. Базовый опыт работы со знаниями включает дерево папок, Markdown-редактор с предварительным просмотром, внутренние ссылки, обратные ссылки, теги, поиск по названию и содержимому и граф связей. Эти возможности должны развиваться как единый рабочий процесс, а не как несвязанные инструменты.

CreatorOS предназначен для разных авторских процессов, а не только для разработки игр или видеоблогинга. Шаблоны и типы рабочих пространств могут учитывать разные сценарии — разработку, видеопроизводство, книги, исследования и другие проекты — без жёсткого ограничения доменной модели одним видом деятельности.

## 2. Основная модель предметной области

### 2.1. Object

Object — самостоятельный конечный продукт авторской деятельности. Это базовая предметная сущность CreatorOS, объединяющая ранее рассматривавшиеся Project и Content на концептуальном уровне. Object не является контейнером для всех данных рабочего процесса: он представляет именно создаваемый результат.

Примеры Object:
- Project — самостоятельный крупный результат, который может включать другие объекты;
- Video — видеоматериал;
- Article — полноценная статья;
- Post — самостоятельная публикация для социальной сети или другой площадки;
- Game — игра;
- Book — книга;
- Research — исследование.

Object может существовать без дочерних объектов и вспомогательных сущностей. Он имеет собственный жизненный цикл и может быть завершён в соответствии с правилами своего типа и состоянием дочерних объектов.

Каждый Object имеет ровно один основной ObjectType. Дополнительная классификация при необходимости может обеспечиваться категориями, тегами и другими классификаторами, не заменяющими основной тип.

Для организации объектов в серии, рубрики и другие группы предполагается предусмотреть общий механизм организации и группировки Object. Это не отдельное специфическое свойство Video или Shorts. Конкретная модель такого механизма и способы представления групп будут определены позднее.

**Общие базовые свойства Object:**
- уникальный идентификатор;
- основной ObjectType;
- название;
- описание.

**Описание Object:**
- Описание необязательно: Object можно создать без описания и добавить его позднее.
- Описание является общим свойством всех ObjectType. Оно не настраивается через ObjectType и не может быть исключено из набора общих свойств.
- Формат — обычный текст без форматирования и автоматического распознавания ссылок. Поддержку ссылок можно добавить позднее.
- Пользователь может вводить несколько абзацев; переносы строк сохраняются при сохранении и отображении.
- Содержимое описания не проходит дополнительную проверку или автоматическую нормализацию: пользователь самостоятельно определяет его содержание.
- Для описания устанавливается разумное ограничение длины — 10 000 символов. Превышение лимита должно быть явно обозначено пользователю; текст не должен молча обрезаться.
- Описание отображается в подробностях Object (Details), но не отображается на карточках.

**Уникальность названия Object:**
- Название обязательно и должно быть уникальным среди всех Object, не находящихся в корзине, независимо от ObjectType и отношений между объектами.
- При проверке уникальности регистр букв не учитывается: названия, отличающиеся только регистром, считаются одинаковыми.
- Перед сохранением название нормализуется удалением пробелов в начале и конце. Последовательности пробелов внутри названия автоматически не изменяются.
- Проверка уникальности выполняется при создании и редактировании Object. При редактировании текущий объект исключается из проверки, поэтому сохранение неизменённого названия допустимо.
- Если введённое название уже занято, приложение предлагает пользователю свободный вариант, например с числовым суффиксом «(1)». Предложение не применяется без согласия пользователя; пользователь может принять его или изменить предложенное название.
- Object, помещённые в корзину, не участвуют в проверке уникальности. Их названия могут быть использованы другими Object. После окончательного удаления название также становится доступным.

**Общие системные свойства Object:**
- целочисленный внутренний идентификатор SQLite;
- глобальный UUID;
- дата создания;
- дата последнего изменения.

**Правила идентификаторов Object:**
- Внутренний ID — целочисленный первичный ключ, используемый для связей и работы SQLite.
- Дополнительно каждому Object назначается глобальный UUID версии 4 для будущей синхронизации и обмена данными между установками приложения.
- UUID генерируется приложением через Qt (`QUuid::createUuid()`) при создании записи и хранится в SQLite как строка стандартного формата из 36 символов без фигурных скобок.
- Уникальность UUID дополнительно обеспечивается ограничением `UNIQUE` в SQLite. UUID не изменяется после создания записи.

**Правила системных дат Object:**
- Дата создания устанавливается приложением автоматически при создании Object и не может быть изменена пользователем вручную.
- При восстановлении Object из корзины сохраняется первоначальная дата создания.
- Дата последнего изменения автоматически обновляется при каждом успешном сохранении изменений собственных данных Object.
- Изменения отношений Object с другими объектами и изменения самостоятельных связанных сущностей (например, задач или публикаций) не изменяют дату последнего изменения данного Object.
- Восстановление Object из корзины не изменяет дату последнего изменения.
- Обе даты хранятся в UTC в формате ISO 8601 с точностью до миллисекунд и отображаются пользователю с учётом его локального часового пояса.
- Временные метки формируются приложением, а не значениями по умолчанию SQLite.
- Дата создания и дата последнего изменения отображаются только в подробностях Object (Details), но не на карточках.
- На данном этапе отдельная история изменений Object не ведётся.


**Дополнительные общие свойства Object:**
- прогресс — общее свойство всех Object, рассчитываемое приложением автоматически;
- дедлайн — необязательный срок, который может быть указан для Object любого типа. Дедлайн задаётся только датой, без времени. При создании и редактировании пользователь может включить или отключить его указание; в форме флажок «Указать срок» включён по умолчанию.
  - Если флажок включён, дата автоматически устанавливается на следующий календарный день относительно текущей даты пользователя. Пользователь может изменить её вручную.
  - Если при создании Object пользователь выключает флажок до первого сохранения, дата не сохраняется даже как временное значение. При повторном включении флажка дата снова автоматически устанавливается на следующий день.
  - Если Object уже был сохранён с включённым дедлайном, последующее отключение флажка временно сохраняет ранее заданную дату. При повторном включении восстанавливается сохранённое значение.
  - Если флажок выключен, дата не требуется.
  - Дедлайн должен поддерживать сортировку и фильтрацию.
  - Дедлайн считается просроченным со следующего календарного дня после указанной даты. В течение самой даты дедлайна он ещё не считается просроченным. Проверка выполняется с учётом локального часового пояса пользователя.
  - Просроченный дедлайн визуально выделяется.
  - Напоминания о приближении дедлайна будут рассмотрены отдельно позднее.
  - В технической документации используется термин «дедлайн»; для короткой подписи в интерфейсе предварительно предлагается «Срок».

**Правила расчёта прогресса Object:**
- Прогресс рассчитывается автоматически как взвешенное среднее прогресса учитываемых задач и непосредственных дочерних Object:
  \[
  P = \frac{\sum(P_i \times W_i)}{\sum W_i}
  \]
  где \(P_i\) — прогресс составляющей, а \(W_i\) — её вес.
- Задачи имеют вес 1. Дочерние Object имеют вес в зависимости от роли в отношении с текущим родителем: основной — 1; дополнительный — 0,5; вспомогательный — 0,2.
- Прогресс задачи определяется по её статусу: Done — 100%; Todo и InProgress — 0%. Задачи со статусом Cancelled полностью исключаются из расчёта.
- Родительская задача с подзадачами учитывается только через свои непосредственные подзадачи и сама отдельно в расчёт не включается. Если у задачи нет подзадач, она учитывается как обычная задача.
- В расчёт Object включаются только его непосредственные дочерние Object. Прогресс каждого такого ребёнка уже учитывает его собственные задачи и дочерние Object, поэтому вложенные уровни не учитываются повторно на уровне более высокого родителя.
- Учёт прогресса дочерних Object можно отключить в настройках приложения. При отключении дочерние Object не влияют на прогресс родителя.
- Дочерний Object, для которого пока невозможно рассчитать прогресс из-за отсутствия учитываемых составляющих, не участвует в расчёте прогресса родителя.
- Если у Object нет ни одной учитываемой составляющей, прогресс не отображается: полоса прогресса не показывается. Нулевой прогресс при наличии составляющих отображается как 0%.
- Прогресс нельзя изменять вручную. Полоса прогресса отображается везде, где представлен Object, и сопровождается числовым значением в процентах.
- Расчётное значение прогресса сохраняется с полной точностью; при отображении оно округляется до ближайшего целого процента.
- Числовое значение прогресса хранится непосредственно у Object. Отсутствие значения (NULL) означает, что у объекта нет учитываемых составляющих для расчёта; 0 означает, что составляющие есть, но их прогресс равен нулю.
- Прогресс пересчитывается при изменениях, влияющих на его расчёт, а не при любом редактировании Object. После изменения пересчитывается собственный прогресс затронутого Object, затем прогресс всех его родительских Object по цепочкам вверх.
- Если у Object несколько родителей, пересчёт выполняется для всех затронутых родительских ветвей. Пересчёт должен учитывать пересекающиеся ветви и не выполнять повторную обработку одного и того же родителя в рамках одной операции.
- Изменение роли связи ребёнка с родителем изменяет вес этого ребёнка в расчёте родителя и поэтому требует пересчёта прогресса родителя с дальнейшим распространением пересчёта вверх по его родительским связям.
- Пересчёт всей затронутой цепочки выполняется согласованно в рамках одной транзакции.
- Пересчёт прогресса сам по себе не изменяет `updated_at` ни у пересчитываемого Object, ни у его родителей.

Статусы и приоритет на данном этапе не включаются в согласованный общий набор свойств Object и будут рассмотрены отдельно либо не будут добавлены. Дата выпуска и другие характеристики, смысл которых зависит от вида конечного продукта, относятся к дополнительным свойствам соответствующего ObjectType.

### 2.2. ObjectType

ObjectType — самостоятельная сущность, определяющая тип объектов. В приложении предусмотрены предустановленные типы; пользователь также может создавать и настраивать собственные типы.

Все ObjectType представлены одной универсальной сущностью и общей моделью данных. Различия между типами задаются их настройками и данными, а не отдельными C++ классами или наследниками ObjectType.

Собственные свойства ObjectType:
- целочисленный внутренний идентификатор SQLite;
- глобальный UUID;
- обязательное название;
- необязательное описание;
- дата создания и дата последнего изменения — системные поля, которые не отображаются в пользовательском интерфейсе на текущем этапе.

Для ObjectType применяются те же правила внутренних ID и UUID, что и для Object: целочисленный ID используется для внутренних связей, UUID версии 4 генерируется приложением через Qt, хранится в SQLite строкой стандартного формата из 36 символов без фигурных скобок, имеет ограничение `UNIQUE` и не меняется после создания записи. Даты создания и последнего изменения ObjectType также формируются приложением и хранятся в UTC в формате ISO 8601 с точностью до миллисекунд.

Эти свойства относятся непосредственно к ObjectType. Дополнительные свойства, определяемые типом для объектов, описаны отдельно ниже.

**Описание ObjectType:**
- Описание необязательно.
- Описание редактируется вместе с названием в общей форме создания и редактирования ObjectType.
- В списке типов описание отображается под названием, если оно заполнено.
- Пустое после удаления пробелов описание сохраняется как отсутствие значения.

**Функциональные возможности ObjectType:**
- Архитектура ObjectType должна допускать расширение перечня и настроек функциональных возможностей по мере появления в приложении реальных функций, которые имеют смысл настраивать отдельно для разных типов.
- На текущем этапе отдельные функциональные возможности не определены. Поэтому интерфейс управления ObjectType не показывает фиктивные переключатели или пустые настройки возможностей.
- Поддержка дочерних Object, задач и завершения является общей для всех ObjectType и не настраивается переключателями ObjectType.
- Новые настройки возможностей добавляются только вместе с реализацией соответствующей функциональности и её конкретными правилами. Не следует заранее вводить универсальные флаги, произвольные поля или обобщённый механизм конфигурации без подтверждённого сценария использования.

**Управление ObjectType в интерфейсе:**
- Управление типами размещается внутри раздела «Настройки», отдельным подразделом «Типы объектов»; отдельный основной пункт навигации для ObjectType не создаётся.
- Список показывает название и, если оно заполнено, описание каждого ObjectType.
- Создание и редактирование выполняются через одну форму с обязательным названием и необязательным описанием.
- Предустановленные и пользовательские типы отображаются и редактируются одинаково; отдельная маркировка или блокировка действий для предустановленных типов не требуется.
- Для удаления используется подтверждение, явно объясняющее последствия: удаление ObjectType также удаляет связанные пользовательские свойства, их настройки, варианты и значения; активные Object должны быть предварительно переназначены на другой тип. Объекты в корзине не блокируют удаление, но при восстановлении им потребуется выбрать существующий тип.
- Удаление последнего ObjectType запрещено. Пользовательский интерфейс должен сообщать об этом понятным текстом и не создавать впечатление, что запрет связан с тем, был ли тип предустановленным.

Предустановленные типы (Project, Video, Shorts, Article, Post, Game, Book) создаются как обычные записи в базе данных при первоначальном заполнении. Они не являются специальными программными классами или неизменяемыми системными типами. Признак системного/предустановленного типа не используется: после создания предустановленные и пользовательские ObjectType равноправны.

Пользователь может изменять и удалять любые ObjectType, включая предустановленные, а также создавать новые. Для предустановленных типов нет специальных ограничений на редактирование или удаление. Удаление последнего оставшегося ObjectType запрещено независимо от того, был ли он предустановленным или создан пользователем.

Удаление ObjectType не должно приводить к автоматическому удалению связанных Object. Если на тип ссылается хотя бы один активный Object, перед удалением пользователь должен переназначить такие объекты на другой ObjectType. Наличие в корзине Object, ссылающихся на этот тип, не блокирует удаление: для них сохраняются UUID и название прежнего типа, а при восстановлении пользователь выбирает существующий ObjectType.

В базе данных всегда должен существовать хотя бы один ObjectType. Это постоянное правило приложения, а не только техническое условие первоначальной инициализации. Проверка выполняется на уровне ObjectTypeService до вызова Repository; если тип является последним, Service отклоняет операцию удаления. В пользовательском интерфейсе последнему типу недоступно действие удаления либо при попытке удаления показывается понятное объяснение запрета.

#### Первоначальные данные и инициализация базы

- Наборы начальных данных CreatorOS хранятся централизованно в `src/application/defaults/DefaultData.h`. Файл содержит только определения данных, без логики записи в базу данных и без управления транзакциями. В нём могут размещаться типизированные наборы предустановленных ObjectType, общих определений свойств, шаблонов свойств и других данных, необходимых новой установке приложения.
- При первом запуске первоначальное заполнение выполняется, если таблица `object_types` пуста. Если в ней уже есть хотя бы одна запись, повторное первоначальное заполнение не запускается. Удаление пользователем предустановленных типов не должно приводить к их автоматическому восстановлению.
- Первоначальное заполнение всех предусмотренных наборов данных выполняется атомарно в рамках одной SQLite-транзакции: при успешном выполнении всех операций транзакция фиксируется; при любой ошибке все изменения первоначального заполнения откатываются. Это исключает ситуацию, когда частично заполненная база ошибочно воспринимается как уже инициализированная.
- Для определения факта первоначального заполнения не используется отдельный маркер в QSettings. Непустая таблица `object_types` служит признаком того, что первоначальные данные уже были созданы. Постоянный запрет удаления последнего ObjectType гарантирует, что после успешной инициализации этот признак не будет утрачен.


Название ObjectType уникально без учёта регистра: два типа с названиями, различающимися только регистром букв, не могут существовать одновременно.

Тип определяет:
- набор дополнительных свойств объектов этого типа;
- типы значений этих свойств (например, текст, число, дата, логическое значение или ссылка на другую сущность);
- доступные объектам функциональные возможности и соответствующие ограничения.

Общие базовые и системные свойства Object не дублируются в конфигурации ObjectType. Дополнительные свойства, включённые в конкретный ObjectType, являются определениями параметров, доступных объектам этого типа. Общий механизм пользовательских свойств, включая общие свойства всех Object, свойства конкретного ObjectType и индивидуальные свойства отдельного Object, описан в подразделе «Пользовательские свойства Object».

Тип значения определяет формат данных свойства (например, текст, число, дата или логическое значение), а возможность хранить одно или несколько значений является отдельной настройкой свойства и не образует самостоятельный тип значения. Один и тот же тип данных может поддерживать как одиночное, так и множественное значение, если это применимо к данному типу. Подробные ограничения, правила хранения и представление этой настройки в интерфейсе будут определены при реализации.

Функциональные возможности типа выбираются из механизмов, реализованных в CreatorOS. Пользовательская конфигурация ObjectType может включать и настраивать поддерживаемые приложением возможности, но не создаёт произвольную новую программную функциональность.

#### Таблицы `object_types` и `objects`

Для новой схемы SQLite используются две основные таблицы предметной модели: `object_types` и `objects`. Схема создаётся заново: существующая тестовая база данных и прежние миграции удаляются, перенос данных из старых таблиц Project, Content и Task не выполняется. Новые миграции будут описывать новую схему с нуля. Предустановленные ObjectType (Project, Video, Shorts, Article, Post, Game, Book) будут добавлены отдельным этапом после реализации сущности ObjectType; на этапе первоначального проектирования таблиц начальные записи не создаются.

**Таблица `object_types`**

| Поле | Тип SQLite | Ограничения и назначение |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ: `INTEGER PRIMARY KEY AUTOINCREMENT`. Внутренний целочисленный идентификатор. |
| `uuid` | `TEXT` | Обязательный глобальный UUID: `NOT NULL UNIQUE`. |
| `name` | `TEXT` | Обязательное название. Уникально без учёта регистра. |
| `description` | `TEXT` | Необязательное описание; если не задано, хранится `NULL`, а не пустая строка. |
| `created_at` | `TEXT` | Обязательная дата создания. |
| `updated_at` | `TEXT` | Обязательная дата последнего изменения. |

**Таблица `objects`**

| Поле | Тип SQLite | Ограничения и назначение |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ: `INTEGER PRIMARY KEY AUTOINCREMENT`. Внутренний целочисленный идентификатор. |
| `uuid` | `TEXT` | Обязательный глобальный UUID: `NOT NULL UNIQUE`. |
| `object_type_id` | `INTEGER` | Внешний ключ на `object_types.id` с `ON DELETE SET NULL`; обязателен для активного Object, может быть `NULL` у Object в корзине, если прежний ObjectType удалён. |
| `name` | `TEXT` | Обязательное название. |
| `description` | `TEXT` | Необязательное описание; если не задано, хранится `NULL`, а не пустая строка. |
| `deadline_at` | `TEXT` | Необязательный дедлайн в формате ISO `YYYY-MM-DD`, без времени. |
| `progress` | `REAL` | Рассчитанный прогресс; допускает `NULL` либо значение от 0 до 100 включительно. |
| `created_at` | `TEXT` | Обязательная дата создания. |
| `updated_at` | `TEXT` | Обязательная дата последнего изменения. |
| `deleted_at` | `TEXT` | Дата помещения в корзину; `NULL` означает, что Object не удалён. |
| `former_object_type_uuid` | `TEXT` | UUID прежнего ObjectType; заполняется вместе с `former_object_type_name`, если ObjectType удалён, пока Object находится в корзине. Иначе `NULL`. |
| `former_object_type_name` | `TEXT` | Название прежнего ObjectType для отображения в корзине; хранится вместе с его UUID. Иначе `NULL`. |
| `deleted_timezone` | `TEXT` | Идентификатор часового пояса, действовавшего при помещении Object в корзину; `NULL` вне корзины. Используется для расчёта 30 календарных дней. |

**Ограничения уникальности названий**

- Для `objects` создаётся частичный уникальный индекс по `name` без учёта регистра, применяемый только к строкам, у которых `deleted_at IS NULL`. Поэтому активные Object не могут иметь одинаковые названия независимо от ObjectType, но название Object из корзины может быть использовано другим активным Object. После окончательного удаления название также становится доступным.
- Для `object_types` название уникально без учёта регистра для всех записей; удалённые ObjectType не сохраняются в этой таблице как записи корзины.
- Уникальность названий ObjectType и активных Object должна обеспечиваться самой SQLite, а не только предварительной проверкой в интерфейсе или Application-слое. Application-слой при этом отвечает за понятную обработку конфликта и предложение свободного названия в соответствии с правилами предметной модели.

**Ограничения связей и значений**

- Для активных Object `object_type_id` обязателен и должен ссылаться на существующий `object_types.id`. Для Object в корзине поле может быть `NULL`, если прежний ObjectType был удалён. Удаление ObjectType блокируется, если на него ссылается хотя бы один активный Object; ссылки из объектов в корзине не блокируют удаление. При удалении ObjectType ссылки таких объектов обнуляются, а сведения о прежнем типе сохраняются отдельно для отображения.
- `objects.progress` допускает только `NULL` или число в диапазоне от 0 до 100 включительно; это ограничение должно быть закреплено SQL-ограничением `CHECK`.
- `uuid` обеих таблиц обязателен и уникален. Приложение создаёт UUID v4 через `QUuid::createUuid()`; в SQLite он хранится как `TEXT` в стандартном строковом представлении из 36 символов без фигурных скобок. UUID после создания записи не изменяется.
- `description` обеих таблиц допускает отсутствие значения и в таком случае хранится как `NULL`, а не как пустая строка.
- `objects.deadline_at` допускает `NULL`; заданная дата хранится как ISO `YYYY-MM-DD`, без времени.

**Общие правила идентификаторов**

- Во всех таблицах приложения, содержащих целочисленное поле `id` в качестве первичного ключа, обязательно используется `INTEGER PRIMARY KEY AUTOINCREMENT`.
- Внутренние ID используются SQLite и для связей между таблицами. После окончательного удаления записи её внутренний ID не должен выдаваться повторно. Это правило распространяется на `objects`, `object_types`, все остальные таблицы новой схемы и будущие таблицы с таким первичным ключом.
- Дополнительно каждой записи `objects` и `object_types` назначается глобальный UUID версии 4. Он генерируется приложением через `QUuid::createUuid()`, хранится в SQLite как `TEXT` в стандартном формате из 36 символов без фигурных скобок и защищён ограничением `NOT NULL UNIQUE`.
- UUID неизменяем после создания записи. Внутренний ID и UUID решают разные задачи: первый предназначен для локальных связей и SQLite, второй — для будущей синхронизации и обмена данными между установками приложения.
- На будущее предусматривается возможность синхронизации между несколькими пользователями/установками, но полноценная система пользователей, прав доступа и совместной работы сейчас не реализуется.

**Общие правила временных меток**

- `created_at` и `updated_at` формируются приложением, а не значениями по умолчанию SQLite.
- Все временные метки хранятся в UTC в формате ISO 8601 с точностью до миллисекунд, например `2026-11-17T12:34:56.789Z`.
- `created_at` устанавливается при создании записи и далее не изменяется.
- `updated_at` обновляется при обычном успешном изменении собственных данных записи.
- Для Object пересчёт прогресса сам по себе не меняет `updated_at`. Остальные правила изменения `updated_at` при работе с отношениями и восстановлении из корзины определены в подразделе Object выше.

**Правила хранения описания и прогресса**

- Необязательное описание в обеих таблицах хранится как SQL `NULL`, если пользователь его не задал; пустая строка не используется как эквивалент отсутствующего значения.
- `objects.progress` имеет тип `REAL` и ограничение уровня БД: значение должно быть `NULL` либо находиться в диапазоне от 0 до 100 включительно.
- `NULL` в `progress` означает, что у Object пока нет учитываемых составляющих для расчёта; `0` означает, что составляющие есть, но их прогресс равен нулю. Значение хранится с полной точностью, а округление до целого процента выполняется только при отображении.
- `deadline_at` хранит календарную дату без времени в формате ISO `YYYY-MM-DD`; поле допускает `NULL`, если дедлайн не задан.

**Удаление и восстановление Object**

- `deleted_at IS NULL` означает активный Object; непустое значение означает, что Object находится в корзине.
- Помещение Object в корзину выполняется установкой `deleted_at`, а восстановление — возвратом `deleted_at` к `NULL`. При восстановлении сохраняются прежние `id`, `uuid` и `created_at`.
- Окончательное удаление записи из таблицы освобождает её название, но не её внутренний ID: AUTOINCREMENT запрещает повторную выдачу ранее использованного идентификатора.

#### Дополнительные свойства ObjectType

ObjectType хранит определения дополнительных свойств, доступных объектам этого типа. Конкретные значения этих свойств хранятся у соответствующих Object. При создании или редактировании Object приложение определяет доступные дополнительные свойства на основании его ObjectType.

Для повторного использования определений свойств предусматриваются шаблоны. Шаблоны могут содержать отдельные свойства или наборы свойств и применяются при настройке ObjectType. Пользователь может использовать предустановленные шаблоны и сохранять собственные определения или наборы свойств в шаблоны.

При применении шаблона к ObjectType создаются независимые определения свойств, принадлежащие этому ObjectType. После применения они не зависят от шаблона: изменение или удаление шаблона не изменяет ранее созданные определения и значения Object. Аналогично, изменение определения свойства в ObjectType не изменяет шаблон или определения в других ObjectType. Пользователь может повторно применять один шаблон к разным ObjectType и редактировать полученные определения независимо.

Если при добавлении шаблона в ObjectType возникают совпадения названий, приложение предлагает свободные названия с числовым суффиксом в скобках: «Название (1)», «Название (2)» и так далее. Выбирается наименьший свободный положительный номер; если исходное название свободно, оно используется без суффикса. Пользователь может изменить предложенное название. Переименование или удаление свойства не меняет названия других свойств и не перенумеровывает их.

ObjectType может включать функциональную возможность публикации. Если эта возможность включена для типа, у объектов этого типа становятся доступны связанные с публикацией настройки, включая выбор Platform, а также свойство Object «Планируемая дата выпуска». Если возможность отключена, эти элементы не должны навязываться объектам данного типа. Дополнительные свойства и настройки, относящиеся к функциональной возможности, доступны объектам только при включённой для их ObjectType соответствующей возможности. Таким образом, конфигурация ObjectType определяет не только набор возможностей, но и то, какие связанные с ними свойства и настройки применяются к объектам. Планируемая дата выпуска относится к Object, а не к отдельной Publication. Конкретный состав публикационных данных и правила Publication будут определены отдельно.

ObjectType может задавать список Platform — ссылок на соответствующие сущности справочника платформ — как исходный список площадок для объектов этого типа. При создании Object этот список используется как начальное значение; один Object может быть предназначен для нескольких Platform одновременно, а пользователь может изменить список у конкретного Object, удалив или добавив Platform. Таким образом, список у ObjectType задаёт значение по умолчанию, а не жёсткое ограничение доступных площадок. Конкретные списки Platform для каждого ObjectType и возможные ограничения совместимости (например, YouTube для Video и Shorts, LitRes для Book) будут рассмотрены отдельно при проектировании сущности Platform.

#### Пользовательские свойства Object

Пользовательские свойства позволяют дополнять данные Object без введения отдельного программного поля для каждого возможного сценария. Определение свойства и его значения разделены: определение задаёт характеристики свойства, а конкретные значения хранятся отдельно для каждого Object.

**Области применения свойств**

Предусматриваются только две области определения пользовательских свойств:

- **Общие свойства Object (common)** — определяются один раз и автоматически доступны всем Object независимо от ObjectType. Это относится как к уже существующим объектам, так и к объектам, которые будут созданы позднее.
- **Свойства ObjectType (object_type)** — определяются для конкретного ObjectType и автоматически доступны всем существующим и будущим Object этого типа.

Индивидуальных свойств отдельного Object в модели нет. Если свойство требуется только некоторым объектам, пользователь может определить его на уровне подходящего ObjectType. Если свойство должно быть доступно всем Object, оно создаётся в общей области.

Добавление нового определения не требует массового создания или заполнения значений у существующих Object. Значение свойства хранится отдельно у каждого объекта и может отсутствовать, если свойство не является обязательным. Обязательность проверяется при соответствующем создании или редактировании Object; само появление нового обязательного свойства не должно автоматически блокировать другие операции с объектом, пока пользователь не выполняет сценарий, в котором требуется заполнить это свойство.

Определения общих свойств и свойств ObjectType независимы. Изменение или удаление одного определения не изменяет другое определение с таким же или похожим названием.

**Характеристики определения свойства**

Определение пользовательского свойства включает:

- название;
- необязательное описание или пояснение;
- тип значения;
- настройку множественности: одно значение или несколько;
- признак обязательности;
- значение по умолчанию;
- признак включённости (is_enabled);
- автоматический порядок отображения; ручное управление порядком не предусматривается;
- признак отображения на карточке Object (show_on_card);
- настройки, относящиеся к выбранному типу значения.

description допускает отсутствие значения и в таком случае хранится как SQL NULL. Множественность является отдельной настройкой и не образует самостоятельный тип значения. Значение по умолчанию может отсутствовать; его формат и применение описаны ниже.

**Типы значений**

Поддерживаются следующие типы, хранимые в базе данных под внутренними кодами:

- text — текст, единый тип для короткого и многострочного текста;
- number — число, единый тип для целых и дробных чисел;
- boolean — логическое значение;
- date — дата;
- datetime — дата и время;
- entity_reference — ссылка на сущность.

Отдельные типы для URL, валюты, процентов, длительности, размера файла и других специальных форматов на текущем этапе не вводятся. URL хранится как текст; в интерфейсе для такого текста предусматривается распознавание ссылок.

Для текстовых значений предусматриваются ограничения минимальной и максимальной длины. Конкретные пределы будут определены позднее. Для числовых значений ограничения min/max на текущем этапе не предусматриваются.

**Значения по умолчанию**

Значение по умолчанию хранится в поле default_value в формате JSON. Формат зависит от настройки множественности:

- для свойства с одним значением хранится JSON scalar соответствующего типа;
- для свойства с несколькими значениями хранится JSON array значений соответствующего типа;
- SQL NULL означает, что значение по умолчанию не задано;
- пустой JSON-массив означает, что явно задано пустое множество значений.

Application-слой проверяет соответствие JSON-значения типу свойства и настройке множественности. Точные правила применения значения по умолчанию в формах создания и редактирования определяются при реализации.

**Списки допустимых значений**

Для свойства может быть задан список допустимых вариантов. Он поддерживает как одиночный, так и множественный выбор; возможность выбрать несколько вариантов определяется отдельной настройкой множественности свойства.

Пользователь может выбрать существующий вариант или ввести новый. Введённый вариант автоматически добавляется в список допустимых значений соответствующего определения свойства и становится доступен всем Object, использующим это определение. Для общего свойства это означает доступность варианта всем Object, для свойства ObjectType — всем объектам соответствующего типа.

Варианты принадлежат конкретному определению свойства и не синхронизируются автоматически между разными определениями, даже если те созданы на основе одного шаблона или имеют одинаковые названия. Пользователь может сохранять собственные варианты вместе со свойством в шаблон, а также копировать/вставлять свойство вместе с его вариантами при настройке другого ObjectType.

Список допустимых вариантов можно изменять и после того, как он уже использовался. Перед изменением приложение должно предупредить пользователя о том, что вариант может быть связан с существующими значениями Object.

**Множественные значения**

Множественность является отдельной настройкой свойства, а не самостоятельным типом значения. Пользователь самостоятельно выбирает, хранит ли конкретное свойство одно значение или несколько.

Если свойство поддерживает несколько значений:
- пользователь может задавать порядок значений;
- дубликаты внутри одного набора значений одного Object не допускаются.

**Ссылки на сущности**

Для типа значения entity_reference целевой тип сущности обязательно задаётся в определении свойства. Одно свойство ссылается на один конкретный тип сущности и не может произвольно смешивать разные типы целей.

В качестве целевых сущностей предварительно рассматриваются Object, Platform, Account, Task, Publication, документы базы знаний и другие сущности CreatorOS, для которых приложение будет поддерживать такой механизм. Если в приложении появятся новые сущности, необходимость добавления их в список допустимых целей будет рассматриваться отдельно.

**Уникальность названий**

Название общего свойства должно быть уникальным среди общих свойств. Название свойства ObjectType должно быть уникальным только среди свойств того же ObjectType. Общие свойства и свойства ObjectType проверяются независимо, поэтому одинаковые названия в этих двух областях допустимы, даже если оба свойства доступны одному Object.

Если при создании или добавлении свойства возникает совпадение, приложение предупреждает пользователя и предлагает свободное название с числовым суффиксом в скобках: «Название (1)», «Название (2)» и так далее. Выбирается наименьший свободный положительный номер; если исходное название свободно, оно предлагается без суффикса. Пользователь может изменить предложенное название.

Проверка выполняется в пределах области определения: для общих свойств — среди всех общих свойств; для свойств ObjectType — среди свойств соответствующего ObjectType. Названия свойств разных ObjectType могут совпадать. Название общего свойства может совпадать с названием свойства любого ObjectType.

**Изменение и удаление определений**

Пользователь может изменять название, описание, настройки и тип значения уже созданного свойства. Изменение типа значения должно учитывать ранее сохранённые значения Object:

- если преобразование однозначно и выполняется без потери данных, приложение может выполнить его автоматически;
- если преобразование неоднозначно или может привести к потере данных, приложение должно предупредить пользователя и предоставить выбор;
- если отдельное значение невозможно преобразовать в новый тип, выбранное правило — удалить несовместимое значение.

Точные правила преобразования для каждой пары типов будут определены при проектировании реализации.

Удаление свойства ObjectType удаляет его определение и связанные с ним значения Object этого типа. Удаление общего свойства удаляет определение и связанные с ним значения у всех Object. Перед удалением в обоих случаях обязательно показывается предупреждение о последствиях.

Свойство можно временно отключить без удаления. При отключении определение и все сохранённые значения остаются в системе, но свойство:
- не отображается в формах создания и редактирования Object;
- не отображается в подробностях Object (Details);
- не отображается на карточке Object.

Повторное включение возвращает свойство в доступное представление вместе с ранее сохранёнными значениями. Отключение означает временное скрытие и недоступность свойства, а не удаление определения или его данных.

**Отображение, порядок и поиск**

Пользовательские свойства отображаются в автоматическом порядке. Ручное управление порядком пользовательских свойств на текущем этапе не предусматривается. Используется единый порядок отображения без отдельных порядков для разных экранов. Также предусматривается настройка того, какие свойства отображаются на карточке Object.

Значения пользовательских свойств участвуют в общем поиске Object.

Сортировка и фильтрация списка Object по пользовательским свойствам рассматриваются как возможное расширение. До оценки сложности и определения подходящего механизма они не фиксируются как обязательное функциональное требование.

Пользовательские свойства не привязываются к функциональным возможностям ObjectType. Их доступность определяется областью определения свойства и его состоянием (is_enabled). Встроенные и системные свойства, которые зависят от функциональных возможностей ObjectType, например планируемая дата выпуска при включённой публикации, остаются отдельным механизмом и не относятся к пользовательским свойствам.

#### Таблицы пользовательских свойств

Для определений пользовательских свойств используется одна общая таблица property_definitions, которая хранит определения обеих областей — общие и относящиеся к ObjectType. Область применения задаётся полем scope; для определения области object_type дополнительно указывается object_type_id, а для области common это поле не задаётся.

**Таблица property_definitions**

| Поле | Тип SQLite | Ограничения и назначение |
|---|---|---|
| id | INTEGER | Первичный ключ: INTEGER PRIMARY KEY AUTOINCREMENT. |
| uuid | TEXT | Обязательный глобальный UUID: NOT NULL UNIQUE. |
| scope | TEXT | Область определения: common или object_type. |
| object_type_id | INTEGER | Внешний ключ на object_types.id для области object_type; для common не задаётся. |
| name | TEXT | Обязательное название свойства. |
| description | TEXT | Необязательное описание; при отсутствии хранится NULL. |
| value_type | TEXT | Код типа значения: text, number, boolean, date, datetime, entity_reference. |
| is_multiple | INTEGER | Признак хранения одного или нескольких значений. |
| is_required | INTEGER | Признак обязательности. |
| default_value | TEXT | Необязательное JSON-значение; SQL NULL означает, что значение по умолчанию не задано. |
| is_enabled | INTEGER | Признак включённости свойства. |
| show_on_card | INTEGER | Признак отображения свойства на карточке Object. |
| created_at | TEXT | Обязательная дата создания. |
| updated_at | TEXT | Обязательная дата последнего изменения. |

Для property_definitions применяются общие правила внутренних ID, UUID и временных меток, установленные для Object и ObjectType: id использует AUTOINCREMENT, UUID v4 генерируется приложением через QUuid::createUuid(), хранится как строка из 36 символов без фигурных скобок и не меняется после создания; временные метки формируются приложением в UTC в формате ISO 8601 с миллисекундной точностью.

Ограничения и правила property_definitions:
- scope допускает только common и object_type;
- для scope = common поле object_type_id должно быть NULL; для scope = object_type поле object_type_id обязательно;
- object_type_id ссылается на object_types.id с ON DELETE CASCADE;
- value_type допускает только text, number, boolean, date, datetime и entity_reference;
- is_multiple, is_required, is_enabled и show_on_card хранятся как 0 или 1;
- значения по умолчанию: is_multiple = 0, is_required = 0, default_value = NULL, is_enabled = 1, show_on_card = 0;
- название перед сохранением нормализуется удалением пробелов в начале и конце; проверка уникальности не учитывает регистр;
- названия общих свойств уникальны без учёта регистра среди общих свойств; названия свойств ObjectType уникальны без учёта регистра в пределах одного ObjectType. Между общей областью и областью ObjectType, а также между разными ObjectType совпадения допустимы.

Ограничения настроек типов значений:
- property_text_settings хранит min_length и max_length; каждое поле может быть NULL, а заданные значения должны быть неотрицательными целыми числами; если заданы оба значения, min_length не может превышать max_length. Запись существует только для определения с value_type = text и удаляется каскадно вместе с определением.
- property_entity_reference_settings хранит обязательный target_entity_type и существует только для определения с value_type = entity_reference; запись удаляется каскадно вместе с определением. При смене типа с entity_reference на другой соответствующая настройка удаляется; при смене на entity_reference целевой тип должен быть задан.

Для property_options поле normalized_value обязательно. Оно формируется Application-слоем как каноническое представление значения: текст — с регистронезависимой нормализацией; число — в каноническом числовом формате; date/datetime — в нормализованном формате; boolean — true/false; entity_reference — UUID сущности.

Для текстовых ограничений и ссылок на сущности используются отдельные таблицы настроек:

- property_text_settings: property_id — первичный ключ и внешний ключ на property_definitions.id; поля min_length и max_length задают ограничения длины текста.
- property_entity_reference_settings: property_id — первичный ключ и внешний ключ на property_definitions.id; поле target_entity_type обязательно задаёт целевой тип сущности.

Для типа number отдельная таблица настроек на текущем этапе не требуется.

Названия определений нормализуются удалением пробелов в начале и конце перед сохранением. Уникальность названий проверяется без учёта регистра и в пределах соответствующей области: общие свойства сравниваются только с общими свойствами, а свойства ObjectType — только со свойствами того же ObjectType. Совпадения между общей областью и ObjectType, а также между разными ObjectType допустимы.

**Таблица property_options**

| Поле | Тип SQLite | Ограничения и назначение |
|---|---|---|
| id | INTEGER | Первичный ключ: INTEGER PRIMARY KEY AUTOINCREMENT. |
| property_id | INTEGER | Обязательный внешний ключ на property_definitions.id. |
| value | TEXT | Обязательное JSON-представление варианта того же типа, что и значение свойства. |
| normalized_value | TEXT | Обязательное каноническое представление значения, сформированное Application-слоем и используемое для обеспечения уникальности внутри одного свойства. |

Для вариантов не используются UUID и временные метки. Каждый вариант представляет собой само значение, а не пару «код — название». Варианты принадлежат одному определению свойства. В таблице действует ограничение UNIQUE(property_id, normalized_value).

Уникальность вариантов обеспечивается в пределах одного свойства по полю normalized_value: текст сравнивается без учёта регистра, числа — численно, даты и дата-время — после нормализации, логические значения — как true/false, ссылки на сущности — по UUID целевой сущности. Application-слой формирует каноническое normalized_value в соответствии с типом свойства; SQLite обеспечивает уникальность ограничением UNIQUE(property_id, normalized_value). Изменение или удаление варианта после его использования допускается после предупреждения пользователя; сохранённые значения Object при этом не изменяются, даже если перестают соответствовать актуальному списку вариантов.

**Таблица property_values**

Для хранения значений используется одна запись на пару Object и определение свойства. Отдельные записи заранее не создаются: отсутствие строки означает, что у Object нет собственного сохранённого значения этого свойства.

| Поле | Тип SQLite | Ограничения и назначение |
|---|---|---|
| object_id | INTEGER | Часть составного первичного ключа; внешний ключ на objects.id с ON DELETE CASCADE. |
| property_id | INTEGER | Часть составного первичного ключа; внешний ключ на property_definitions.id с ON DELETE CASCADE. |
| value | TEXT | Обязательное JSON-представление сохранённого значения. |

Первичный ключ таблицы — составной: (object_id, property_id). Отдельные id, UUID, created_at и updated_at не используются: запись не является самостоятельной сущностью, а изменение значения учитывается через updated_at соответствующего Object.

Удаление Object или определения свойства приводит к каскадному удалению соответствующих строк property_values. Помещение Object в корзину не удаляет его значения: они сохраняются для возможного восстановления. Окончательное удаление Object удаляет их вместе с объектом.

**Представление значений**

Формат JSON соответствует типу и настройке множественности определения свойства:

- text — JSON string;
- number — JSON number;
- boolean — true или false;
- date — строка YYYY-MM-DD;
- datetime — строка ISO 8601 в UTC с миллисекундной точностью;
- entity_reference — UUID целевой сущности.

Для свойства с is_multiple = false поле value содержит JSON scalar. Для свойства с is_multiple = true — JSON array элементов соответствующего типа. Порядок элементов массива сохраняет заданный пользователем порядок. Дубликаты внутри одного набора значений одного Object не допускаются.

Для entity_reference сохраняется UUID целевой сущности, а не её внутренний ID. Если целевая сущность помещена в корзину или окончательно удалена, сохранённая ссылка не удаляется и не переписывается. При отображении приложение сообщает, что целевая сущность недоступна или удалена.

Пустая строка и строка, состоящая только из пробельных символов, после нормализации Application-слоем трактуются как отсутствие значения. Такая нормализация не означает автоматическое удаление пробелов по краям у всех непустых текстовых значений.

**Значения по умолчанию и отсутствие собственного значения**

Если для определения задан default_value, он используется при отображении и заполнении формы Object, у которого ещё нет собственной строки в property_values. Само добавление определения или установка значения по умолчанию не создаёт массово строки property_values.

При первом сохранении формы значение по умолчанию становится собственным сохранённым значением Object. Если пользователь изменил его до сохранения, сохраняется выбранное им значение.

**Изменение настройки множественности**

При переходе is_multiple от false к true ранее сохранённое одиночное значение автоматически преобразуется в JSON-массив из одного элемента.

При переходе от true к false существующие массивы не преобразуются массово и не приводят к немедленному требованию исправить все Object. При следующем открытии конкретного Object для редактирования приложение обнаруживает несколько сохранённых элементов и предлагает пользователю выбрать одно значение. До выбора и сохранения Object можно оставить без изменений; обычный просмотр не требует исправления.

**Влияние изменений на updated_at Object**

Изменение определения свойства — в том числе его названия, описания, обязательности, множественности, списка вариантов, значения по умолчанию, включённости или порядка — само по себе не изменяет updated_at объектов и не запускает массовую проверку или корректировку их значений.

Изменение названия определения сразу отражается во всех Object, использующих это определение: название не дублируется в строках property_values. Такое переименование не считается изменением самих Object и не обновляет их updated_at.

Изменение сохранённого значения свойства у конкретного Object считается изменением данных этого Object и обновляет его updated_at.

#### Предварительно согласованный состав основных ObjectType

Для текущего проектирования в качестве основных типов рассматриваются:
- Project;
- Video;
- Shorts;
- Article;
- Post;
- Game;
- Book.

**Project** на текущем этапе не имеет дополнительных специфических свойств и использует только общие свойства Object. Его особенности определяются назначением и отношениями с другими объектами, а не отдельными полями. Это решение не является окончательным ограничением: если в дальнейшем появится практическая необходимость, для Project можно будет определить дополнительные свойства.

**Video и Shorts** являются двумя самостоятельными ObjectType:
- **Video** — обычное видео;
- **Shorts** — короткое самостоятельное видео, например YouTube Shorts или Instagram Reels.

Один Video или Shorts может быть связан с одним или несколькими объектами другого формата, если материал перерабатывается из одного формата в другой. Такая возможность не должна искусственно ограничиваться типом объекта; конкретные виды отношений будут определены отдельно.

Для Video и Shorts согласованы следующие положения:
- отдельные свойства для подготовки видео (например, сценарий, план монтажа или исходники) на текущем этапе не вводятся: соответствующие данные могут быть представлены задачами, документами базы знаний, файлами, материалами или связанными Object;
- отдельные этапы подготовки и статусы Video/Shorts на текущем этапе не определяются;
- отдельное свойство для серий, рубрик или групп не вводится. Для организации Video и Shorts предполагается использовать будущий общий механизм организации и группировки Object.

**Article** — полноценная статья, например материал для блога, сайта или онлайн-журнала.

**Post** — самостоятельная публикация для социальной сети или другой площадки, обычно более компактная и ориентированная на формат соответствующей площадки.

Article и Post являются разными ObjectType, но на текущем этапе для них согласован одинаковый набор специфических свойств и правил:
- отдельное встроенное свойство «Язык» не вводится. При необходимости пользователь сможет добавить его как собственное общее свойство или свойство соответствующего ObjectType;
- отдельные этапы подготовки и свойства, связанные с подготовкой материала, не вводятся;
- отдельные свойства для серий, рубрик и групп не вводятся. Для организации Article и Post предполагается использовать будущий общий механизм организации и группировки Object.

Article и Post могут быть связаны друг с другом как самостоятельные Object; преобразование материала из одного формата в другой не ограничивается направлением. Конкретные виды отношений будут определены при проектировании общей модели отношений Object. Создание языковых версий одного материала на текущем этапе не предусматривается; такая возможность может быть рассмотрена в будущем.

Эти решения не определяют структуру Publication и не устанавливают правила связи Account с Platform; соответствующие вопросы рассматриваются отдельно.


**Game** — самостоятельный объект, представляющий создаваемую игру. Тип не ограничивается видеоиграми: он должен подходить и для настольных, карточных и других видов игр. Пользователь самостоятельно организует работу над игрой; CreatorOS предоставляет инструменты для этого, но не предписывает конкретный рабочий процесс.

Для Game согласованы следующие положения:
- необязательное свойство **«Версия»**, позволяющее указать версию игры, например 1.0 или 1.1;
- свойство **«Жанр»** может быть добавлено пользователем из общего каталога предустановленных свойств; оно не является обязательным или автоматически включённым свойством Game;
- необязательное свойство **«Формат первого публичного выпуска»** со значениями «Демоверсия», «Ранний доступ» и «Полноценный релиз». Оно определяет, с какого варианта игра начнёт публично выходить, а не текущий этап или статус разработки;
- отдельные встроенные этапы или статусы разработки не вводятся. Организацию процесса пользователь определяет самостоятельно с помощью задач и других возможностей CreatorOS;
- отдельные встроенные свойства для подготовки игры не вводятся. Для связанных материалов, документов и рабочих данных используются соответствующие вспомогательные сущности и инструменты приложения;
- DLC, продолжения, ремейки и другие самостоятельные продукты могут быть отдельными Object. Пользователь самостоятельно определяет, создавать ли их как отдельные объекты и как организовывать связи между ними; тип Game не должен навязывать единственную схему организации;
- языковые версии игры как отдельные связанные Object на текущем этапе не предусматриваются.


**Book** — самостоятельный объект, представляющий создаваемую книгу как конечный продукт. ObjectType Book охватывает книги разных видов и форматов, включая бумажные, электронные и аудиокниги. Тип описывает саму книгу независимо от того, как пользователь организует её создание и подготовку.

Для Book согласованы следующие положения:
- свойство **«Жанр»** может быть добавлено пользователем из общего каталога предустановленных свойств; оно не является обязательным или автоматически включённым свойством Book;
- отдельные встроенные свойства «Версия», «Издание», ISBN, количество страниц, количество слов и другие библиографические характеристики не вводятся. При необходимости пользователь сможет добавить их как собственные свойства;
- понятие публикации для Book на текущем этапе охватывает все способы публикации и распространения книги, включая цифровые площадки, издательства и распространение печатных изданий. Возможное разделение этих способов будет рассмотрено отдельно в будущем;
- отдельные встроенные этапы или статусы работы над книгой не вводятся. Пользователь самостоятельно организует процесс с помощью задач и других возможностей CreatorOS;
- отдельные встроенные свойства для хранения структуры книги, глав, персонажей, содержания, заметок и материалов не вводятся. Для организации этих данных используются соответствующие вспомогательные сущности и инструменты приложения;
- отдельные правила или свойства для серий, циклов, томов, сборников, переизданий и переработанных версий не вводятся. Пользователь самостоятельно определяет, как организовать такие материалы и нужны ли для них отдельные Object;
- языковые версии книги как отдельные связанные Object на текущем этапе не предусматриваются.


### 2.3. Связи между Object

На текущем этапе предусматривается один тип отношений между Object: **«родительский объект — дочерний объект»**. Отношение направленное: оно определяет родительский и дочерний Object. Дополнительные типы отношений на данном этапе не вводятся; необходимость в них может быть рассмотрена позднее на основании практических сценариев использования.

Связь универсальна: совместимость ObjectType не ограничивается. Любой Object может быть родительским или дочерним по отношению к Object любого типа.

Иерархия объектов обладает следующими свойствами:
- один Object может иметь несколько родительских объектов;
- один Object может иметь любое количество дочерних объектов;
- Object может одновременно быть родительским и дочерним;
- вложенность объектов не ограничивается одним уровнем;
- циклические отношения запрещены: объект не может быть своим собственным предком или потомком, в том числе через цепочку отношений.

Между одной и той же парой родительского и дочернего Object может существовать только одно отношение. Повторно добавить того же дочернего Object к тому же родителю нельзя: для изменения роли используется уже существующее отношение. После удаления отношения эту пару объектов можно связать повторно; при этом создаётся новое отношение.


У каждого отношения есть роль дочернего Object в контексте конкретного родительского Object. Роль является характеристикой отношения и не является отдельной настраиваемой сущностью. На текущем этапе предусматриваются следующие роли:
- **основной** — основной продукт, создаваемый в рамках родительского Object;
- **дополнительный** — побочный или сопутствующий продукт, создаваемый в рамках родительского Object;
- **вспомогательный** — самостоятельный Object, создаваемый для поддержки работы над родительским Object, например отдельный результат исследования или анализа.

Роль показывает значимость и назначение дочернего Object относительно конкретного родителя, но не определяет порядок создания или выполнения, степень готовности либо самостоятельную ценность дочернего Object. Дополнительный и вспомогательный Object также могут быть крупными и самостоятельными продуктами.

Роль является характеристикой отношения, а не самого Object. Один и тот же дочерний Object может иметь разные роли по отношению к разным родителям. У одного родительского Object может быть несколько дочерних объектов с каждой из ролей. Роль Object в отношении со своим родителем не влияет на роли его собственных дочерних объектов.

Роль учитывается при определении прогресса родительского Object. Вес основного дочернего Object составляет 1, дополнительного — 0,5, вспомогательного — 0,2. Остальные правила расчёта прогресса описаны в разделе общих свойств Object. На текущем этапе роль также используется для визуального различения дочерних объектов. Иные последствия роли пока не устанавливаются.

Роль может изменяться после создания отношения. Способ её первоначального назначения, значение по умолчанию и защита от случайного изменения будут определены при проектировании интерфейса. При создании связей с несколькими родителями роль относится к каждому отношению отдельно и может различаться. Удобство массового назначения одинаковой роли и последующей индивидуальной настройки будет рассмотрено при проектировании интерфейса.

На текущем этапе предполагается, что дочерние Object являются частью жизненного цикла родительского Object. Родительский Object не может быть завершён, пока не завершены все его дочерние Object. Если дочерний Object имеет несколько родителей, его завершение учитывается каждым из них. Возможность иных правил участия связанных объектов в жизненном цикле может быть рассмотрена позднее вместе с возможными дополнительными типами отношений.

Дополнительное название или описание отношения не предусматривается.

**Структура таблицы отношений Object**

Для хранения отношений используется отдельная таблица `object_relations` со следующими полями:

| Поле | Ограничения и назначение |
|---|---|
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT`; внутренний идентификатор отношения |
| `uuid` | `TEXT NOT NULL UNIQUE`; UUID v4, генерируется приложением и не изменяется |
| `parent_object_id` | `INTEGER NOT NULL`; внешний ключ на `objects.id`, `ON DELETE CASCADE` |
| `child_object_id` | `INTEGER NOT NULL`; внешний ключ на `objects.id`, `ON DELETE CASCADE` |
| `role` | `TEXT NOT NULL`; допустимые коды: `main`, `addition`, `support` |
| `created_at` | `TEXT NOT NULL`; дата и время создания отношения |
| `updated_at` | `TEXT NOT NULL`; дата и время последнего изменения отношения |

Ограничения и правила:

- Пара `parent_object_id + child_object_id` уникальна: один и тот же ребёнок не может быть дважды связан с одним родителем.
- Непосредственная самоссылка запрещается ограничением SQLite: `parent_object_id <> child_object_id`.
- Циклические цепочки отношений запрещаются на уровне Application.
- Для отношения применяются общие правила внутренних ID, UUID и временных меток: внутренний ID не переиспользуется после окончательного удаления; UUID v4 создаётся приложением через `QUuid::createUuid()`, хранится строкой стандартного формата из 36 символов без фигурных скобок и остаётся неизменным; временные метки формируются приложением в UTC в формате ISO 8601 с миллисекундной точностью.
- `created_at` не изменяется. `updated_at` обновляется при изменении роли отношения.
- Отдельного `deleted_at` у отношения нет. Его активность определяется состоянием обоих связанных Object: отношение действует, только если оба Object активны; если хотя бы один находится в корзине, отношение сохраняется, но временно не действует; окончательное удаление любого из связанных Object удаляет отношение через `ON DELETE CASCADE`.
- Восстановление Object автоматически возвращает отношение в активное состояние, когда оба связанных Object снова активны.
- Ручное управление порядком дочерних Object не предусматривается: они отображаются в своей группе роли согласно автоматическому критерию сортировки.

#### Представление и управление иерархией Object

Дочерние Object отображаются на странице родительского Object в отдельном блоке. Внутри блока дочерние объекты разделяются по роли: основные, дополнительные и вспомогательные. Конкретное визуальное оформление различий между ролями будет определено при проектировании интерфейса.

Для дочернего Object предусматривается переход на его страницу. На странице Object также отображается список его родительских объектов в виде ссылок, позволяющих перейти к каждому из них. Если у объекта несколько родителей, отображаются все соответствующие ссылки. Во всех таких представлениях используется один и тот же Object, а не отдельные копии.

Предварительный вариант представления дочерних объектов — карточки. При этом интерфейс должен предусматривать возможность выбора пользователем другого способа отображения. Карточка или другой элемент списка должен показывать название и ObjectType, роль в контексте текущего родителя, прогресс, дедлайн и планируемую дату выпуска, если она задана. Статус также предполагается отображать после того, как система статусов Object будет спроектирована и реализована.

Вложенные уровни иерархии должны поддерживать раскрытие и сворачивание. Не требуется показывать всю вложенную структуру одновременно: пользователь должен иметь возможность управлять видимостью уровней. Конкретный способ визуализации вложенности будет определён при проектировании интерфейса. Если Object имеет нескольких родителей, он отображается как дочерний в контексте каждого из них, но остаётся одной сущностью.

Помимо страницы отдельного Object, предусматривается общая страница со списком всех Object независимо от наличия и характера отношений. Пользователь сможет сортировать и фильтровать объекты. На этой же странице должна быть предусмотрена возможность включать и отключать представление иерархии, чтобы использовать её как общий список или как визуализацию связей между объектами. Таким образом, отдельная страница иерархии пока не фиксируется как обязательная: её назначение может выполнять общая страница Object с переключаемым режимом представления.

В блоке дочерних объектов предусматриваются:
- поддерживается только автоматическая сортировка; ручной порядок и перетаскивание дочерних Object на текущем этапе не предусматриваются;
- доступны критерии сортировки: название, ObjectType, прогресс, дедлайн и дата создания;
- пользователь может менять направление автоматической сортировки;
- автоматическая сортировка применяется отдельно внутри каждой группы роли. Состав и порядок групп (основные, дополнительные, вспомогательные) при этом не меняются;
- добавление дочернего Object, восстановление отношения и изменение роли не задают отдельную позицию: объект отображается в своей группе согласно выбранному критерию автоматической сортировки;
- возможность менять роль дочернего Object непосредственно в списке. Способ защиты от случайного изменения будет определён при проектировании интерфейса.

Добавление дочерних объектов должно поддерживать оба сценария: создание нового Object непосредственно из контекста родителя и добавление уже существующего Object. При создании Object в целом также предусматривается возможность сразу установить отношения с одним или несколькими существующими объектами, выбирая для каждого отношения направление: создаваемый Object будет родительским или дочерним по отношению к выбранному объекту. Роль задаётся для каждого отношения отдельно.

Удаление дочернего Object из блока означает удаление только соответствующего отношения. Перед удалением связи приложение должно запросить подтверждение; сам Object при этом сохраняется.

Удаление отношения удаляет только связь между объектами и не удаляет сами Object. При удалении Object все его отношения удаляются, но остальные связанные с ним Object сохраняются, если пользователь отдельно не выбрал их удаление.


#### Удаление Object и корзина

Удаление Object не приводит к его немедленному безвозвратному уничтожению. Удалённый Object помещается в корзину, где пользователь может просматривать его подробности (только просмотр), восстановить его или окончательно удалить.

**Помещение в корзину и доступность**

- При помещении Object в корзину фиксируются точные дата и время удаления.
- Удалённый Object исчезает из обычной работы приложения: не отображается в общих списках Object, списках родителей и дочерних объектов, результатах поиска; не участвует в расчёте прогресса и не доступен для создания новых отношений.
- Данные Object сохраняются в корзине до восстановления или окончательного удаления.
- Удалённые объекты доступны для просмотра в корзине, но редактирование их данных там не предусматривается.

**Срок хранения и автоматическая очистка**

- Срок хранения в корзине составляет 30 календарных дней. Настройка этого срока пользователем на текущем этапе не предусматривается.
- Срок рассчитывается по календарной дате в часовом поясе пользователя, действовавшем в момент помещения Object в корзину. Этот часовой пояс сохраняется вместе с данными удаления, чтобы последующее изменение часового пояса не меняло срок хранения.
- Автоматическая очистка выполняется при запуске приложения. Периодическая проверка во время работы приложения и очистка перед закрытием не предусматриваются. Если приложение не запускалось длительное время, при следующем запуске окончательно удаляются все записи, срок хранения которых истёк.
- Помимо автоматической очистки пользователь может окончательно удалить отдельный Object из корзины до истечения срока хранения или очистить всю корзину одной операцией.
- Перед окончательным удалением и очисткой корзины обязательно показывается предупреждение о необратимости действия. При очистке всей корзины дополнительно указывается количество удаляемых Object.

**Отношения между Object**

- При помещении Object в корзину его отношения с другими Object временно перестают действовать и не отображаются в активной иерархии. Записи отношений сохраняются для возможного восстановления.
- Если удалённый Object был ребёнком другого Object, он исчезает из активного списка детей. Остальные дети продолжают отображаться и учитываться независимо.
- Отношение восстанавливается только тогда, когда оба участвовавших в нём Object находятся в активном состоянии. Если один из них всё ещё находится в корзине, отношение остаётся сохранённым, но неактивным.
- Если один из связанных Object окончательно удалён, отношения с ним также окончательно удаляются.
- При восстановлении отношений сохраняются их характеристики, включая роль дочернего Object в контексте родителя. Восстановленный дочерний Object отображается в своей группе согласно выбранному критерию автоматической сортировки.

**Задачи, публикации и другие вспомогательные данные**

- Задачи и публикации, принадлежащие Object, при его помещении в корзину также помещаются в корзину. При восстановлении Object восстанавливаются только те задачи и публикации, которые были помещены в корзину одновременно с ним. Если задача или публикация уже находилась в корзине до удаления Object, автоматически она не восстанавливается.
- Предполагается, что каждая задача и каждая публикация принадлежат только одному Object; совместное владение одной задачей или публикацией несколькими Object не предусматривается. Для задач и публикаций используются собственные поля `deleted_at`; их помещение в корзину обновляет `updated_at`.
- Документы базы знаний и другие самостоятельные вспомогательные материалы не удаляются только из-за помещения связанного Object в корзину. Их собственное существование не зависит от этого Object.
- Если материал используется несколькими объектами или контекстами, удаление одного Object не должно уничтожать этот материал или нарушать его использование в остальных контекстах. Связи с такими материалами восстанавливаются вместе с Object, если сами материалы и соответствующие связи по-прежнему существуют.

**Файлы**

- Вместе с Object в корзину помещаются принадлежащие ему файлы — собственные материалы Object, а не любые файлы, на которые он ссылается или которые использует.
- Файлы, используемые несколькими Object, не удаляются при помещении одного из них в корзину.
- Внешние файлы, на которые Object только ссылается, не перемещаются и не удаляются.
- При восстановлении Object его собственные файлы восстанавливаются в исходное расположение с прежними именами. Если имя уже занято, приложение предлагает выбрать новое имя.
- Недоступность или повреждение файла не должна блокировать восстановление Object.
- При окончательном удалении Object удаляются его принадлежащие ему файлы. Общие и внешние файлы сохраняются.

**Восстановление Object**

- Восстановление возвращает Object с прежним ID и всеми сохранёнными собственными данными: названием, описанием, ObjectType, значениями пользовательских свойств, дедлайном, прогрессом и другими характеристиками.
- Первоначальная дата создания сохраняется. Само восстановление не считается редактированием Object и не изменяет `updated_at`; если пользователь исправляет данные Object в процессе восстановления, `updated_at` обновляется.
- При восстановлении очищаются `deleted_at` и сохранённый часовой пояс удаления `deleted_timezone`.
- Если прежнее название уже занято другим активным Object, приложение предупреждает о конфликте и предлагает свободное название с числовым суффиксом в скобках: «Название (1)», «Название (2)» и так далее. Выбирается наименьший свободный положительный номер. Пользователь может изменить предложенное название; восстановление завершается только после разрешения конфликта.
- Если некоторые связанные данные уже недоступны (например, связанный Object был окончательно удалён), это не препятствует восстановлению самого Object. Недоступные отношения не восстанавливаются.
- Если связанный Object ещё находится в корзине, отношение остаётся сохранённым, но неактивным. Оно снова становится действующим после восстановления обоих Object; дополнительных действий пользователя не требуется.
- При восстановлении Object проверяется актуальность его пользовательских свойств относительно существующих ObjectType и определений свойств: доступность и включённость определения, соответствие сохранённого значения текущему типу и настройке множественности, обязательность значения. Если требуются исправления, пользователь выполняет их в процессе восстановления; до успешного завершения Object остаётся в корзине.
- Если восстановление не требует изменения данных Object, `updated_at` сохраняет прежнее значение. Если данные Object исправлены в процессе восстановления, `updated_at` обновляется.
- При восстановлении пересчитывается прогресс затронутых активных родительских Object.

Окончательное удаление Object также окончательно удаляет находящиеся в его корзине задачи и публикации, принадлежащие ему файлы и его отношения. Самостоятельные документы базы знаний, общие материалы, другие Object и файлы, используемые в нескольких контекстах, сохраняются.





**Удаление ObjectType, связанного с Object в корзине**

- Наличие в корзине Object, ссылающегося на ObjectType, не блокирует удаление этого ObjectType. Удаление блокируется, если на ObjectType ссылается хотя бы один активный Object.
- Перед удалением ObjectType Application в одной транзакции сохраняет UUID и название прежнего типа у находящихся в корзине Object. После этого удаление ObjectType выполняется; ссылки таких Object обнуляются.
- Для Object, у которого прежний ObjectType удалён, при восстановлении пользователь обязан выбрать существующий ObjectType. После выбора нового типа выполняется проверка актуальных пользовательских свойств по правилам выше.
- Определения пользовательских свойств удалённого ObjectType и связанные с ними варианты, настройки и значения удаляются. Сохранённые значения, определения которых были удалены вместе с ObjectType, не сохраняются и не восстанавливаются; после выбора нового типа пользователь заполняет актуальные свойства заново.

**Сортировка корзины**

Список корзины сортируется автоматически по выбранным пользователем параметрам. Ручное перетаскивание и хранение `sort_order` не используются.


### 2.4. Вспомогательные сущности и данные

Задачи, публикации, аналитика, документы базы знаний, файлы, материалы и другие данные рабочего процесса не являются Object. Это отдельные сущности со своими моделями, жизненными циклами и правилами.

Object может быть связан со вспомогательными сущностями в соответствии с назначением этих сущностей. Такие связи концептуально отличаются от отношений Object–Object и не превращают вспомогательную сущность в Object. Например, Object может быть связан со своими задачами, публикациями, документами базы знаний и файлами. Один и тот же вспомогательный материал может использоваться в нескольких контекстах.

Все типы Object поддерживают возможность иметь дочерние Object, задачи и завершение. Наличие этих возможностей не означает, что у каждого объекта обязательно должны быть дочерние объекты или задачи.

### 2.5. База знаний и Markdown-документы

База знаний — полноценная часть CreatorOS, а её документы являются самостоятельными вспомогательными сущностями, а не Object.

Документы базы знаний:
- хранятся как обычные файлы Markdown (.md) в папках выбранного пользователем рабочего пространства;
- доступны для открытия и редактирования сторонними редакторами без экспорта из CreatorOS;
- поддерживают стандартные возможности Markdown, включая заголовки, списки, таблицы, кодовые блоки и изображения;
- могут содержать внутренние ссылки на другие документы и ссылки на сущности CreatorOS;
- поддерживают теги, обратные ссылки (backlinks), поиск и граф связей;
- могут создаваться из шаблонов и организовываться в папки;
- могут существовать независимо от задач и публикаций и связываться с одним или несколькими Object и другими документами;
- не обязаны физически находиться в папке какого-либо объекта.

Используется гибридная модель хранения с разделением ответственности:
- **Markdown-файлы** — основное и переносимое хранилище текста документов; пользователь может читать и редактировать их вне CreatorOS.
- **SQLite** — основное хранилище структурированных сущностей CreatorOS, а также метаданных документов, поискового индекса, результатов разбора Markdown и связей между документами и рабочими сущностями.
- **Файловая система** — хранилище вложений и других пользовательских материалов; документы базы знаний могут ссылаться на эти файлы.

Индекс SQLite является производным от файлов и может быть восстановлен повторным сканированием рабочего пространства. SQLite не должна становиться единственной копией текста Markdown-документов. При конфликте источников содержимое Markdown-файла считается авторитетным для текста документа, а SQLite — для структурированных сущностей и служебных связей CreatorOS.

Приложение должно учитывать внешние изменения файлов. При перемещении, переименовании или удалении документа необходимо обновлять индекс и корректно обрабатывать неразрешённые ссылки. Если файл недоступен, запись индекса не должна приводить к потере самого документа или создавать впечатление, что файл существует.

Путь к документу не является единственной устойчивой идентичностью. Внутренние ссылки должны разрешаться с учётом переименования и перемещения файлов настолько, насколько это возможно на основе идентификаторов и актуального индекса.

## 3. Task

Task — отдельная вспомогательная сущность, используемая для организации работы над Object. Задача не является Object и не представляет конечный продукт. Задачи могут быть связаны с объектами любого типа.

Task поддерживает собственную иерархию задач. Связь задачи с Object и связь с родительской Task являются разными отношениями. Модель связей задачи с объектами должна учитывать предметные сценарии CreatorOS и не должна ограничиваться только Project или Content. Конкретная структура этих связей будет определена при проектировании задач в рамках целевой модели Object.

Статусы Task:

~~~text
todo
in_progress
done
cancelled
~~~

Статус изменяется через предусмотренный workflow, а не произвольным вводом в редакторе.

Приоритет является системным производным значением. Система рассчитывает его по контексту задачи, срокам, зависимостям и влиянию задачи; пользователь не изменяет приоритет вручную.

Дедлайн задаётся для конкретной задачи и используется системой при последующем расчёте приоритета.

Создание/редактирование Task не должно позволять пользователю изменять системный контекст, статус или приоритет через обычную форму редактора.

## 4. Publication

Publication — отдельная вспомогательная сущность, представляющая публикацию объекта на внешней площадке. Publication связывается с конкретным Object, который поддерживает возможность публикации, и конкретным Account. Не каждый Object обязан поддерживать публикации; доступность этой возможности определяется ObjectType.

Основные направления данных:

```text
object_id
platform_id
account_id
status
scheduled_at
published_at
external_id
external_url
title
description
publication_data
error_message
```

## 5. Platform и Account

Platform описывает площадку публикации.

Account представляет конкретный аккаунт/канал пользователя на этой площадке.

Связь:

```text
Platform
    ↓
Account
    ↓
Publication
    ↓
Object
```

В форме создания и редактирования Account пользователь выбирает существующую Platform из выпадающего списка. Если список Platform пуст, форма создания Account не открывается; пользователю показывается сообщение с указанием сначала добавить Platform. Выпадающий список Platform раскрывается вниз при обычных условиях отображения.

## 6. EntityCard

EntityCard — базовый C++/Qt-класс для целостного UI-представления карточки сущности.

База знает общие механизмы карточки: поверхность, заголовок, описание, статус, прогресс, метаданные, области дополнительного содержимого и действия. Эти механизмы могут существовать в базе заранее, даже если конкретному наследнику часть из них не нужна.

База не знает конкретный ObjectType или тип вспомогательной сущности. В ней не должно быть ветвлений по конкретным типам сущностей.

Если сущности достаточно стандартных механизмов карточки, страница создаёт экземпляр `EntityCard` напрямую и передаёт ему данные, метаданные и обработчики. Для Object применяется именно этот подход: отдельный класс `ObjectCard` не создаётся, а `ObjectsPage` настраивает `EntityCard` для каждого Object.

Специализированный наследник нужен только тогда, когда у сущности есть самостоятельное поведение или UI-контракт, которые нельзя разумно выразить настройкой общего компонента. Общий визуальный каркас при этом не копируется.

## 7. EntityDetails

EntityDetails — базовый C++/Qt-класс для целостных подробных представлений сущностей.

База знает UI-механизмы details-представления: прокрутку, общую структуру страницы, навигационную область, header, стандартные состояния, summary/info-области, действия, дополнительные content-регионы и управление их видимостью.

EntityDetails предоставляет общий каркас подробного представления. Конкретная страница определяет содержание, условия показа данных и доступные действия.

~~~text
EntityDetails
   ├── ObjectDetailsPage
   └── TaskDetails
~~~

Например, `ObjectDetailsPage` может отображать общие свойства Object и специфические свойства его ObjectType, а `TaskDetails` — только те механизмы, которые подходят Task. База предоставляет механизм, наследник принимает решение.

База не проверяет тип конкретной сущности и не содержит entity-specific ветвления.

Если в details появляется действительно независимый сложный объект с собственным контрактом и поведением, он подключается через composition. Простая разметка, QLabel, QPushButton и layout остаются внутри details-класса.

Бизнес-операции, доменные правила и инварианты выполняются через application/domain слои.

### Целевая UI-архитектура Object (этап 3.5.1)

**Единый список Object**

Для всех Object используется одна страница `ObjectsPage`; отдельные списки Project и Content постепенно заменяются единым представлением. Страница отвечает за получение и обновление списка активных Object, создание элементов списка, открытие подробностей и отображение состояний загрузки, пустого результата и ошибки.

Страница использует `ObjectService` для получения и изменения Object, `ObjectTypeService` для получения сведений о типах и `LocalizationService` для локализуемых текстов. Общий каркас списка и его состояний переиспользуется через существующие `EntityList` и `PageHeader`.

**Карточка Object**

Отдельный класс `ObjectCard` не создаётся. `ObjectsPage` непосредственно создаёт экземпляры существующего `EntityCard` и настраивает их данными конкретных Object. Это соответствует подходу, уже применённому в `AccountsPage` и `PlatformsPage`.

Карточка показывает общие краткие сведения Object, в том числе название, ObjectType, прогресс и дедлайн. Описание, дата создания и дата последнего изменения на карточке не отображаются — для них сохраняются ранее установленные правила подробного представления.

Дополнительно карточка динамически показывает значения пользовательских свойств, если одновременно выполняются условия:
- определение свойства включено (`is_enabled = true`);
- для определения включено отображение на карточке (`show_on_card = true`);
- свойство относится к общей области (`common`) либо к ObjectType отображаемого Object.

Для каждого такого определения показывается значение, сохранённое у конкретного Object. Общие свойства и свойства ObjectType используют единый механизм отображения; ветвления по конкретным ObjectType внутри `EntityCard` не допускаются.

**Подробная страница Object**

Для всех Object используется единая `ObjectDetailsPage`, построенная на существующих `EntityDetails` и `EntityHeader`. Страница отображает общие сведения Object, доступные пользовательские свойства, дочерние Object, родительские Object и предусмотренные отношения. Переходы по ссылкам на связанные Object открывают ту же единую страницу соответствующего Object.

Страница использует:
- `ObjectService` — получение и изменение Object;
- `ObjectTypeService` — сведения об ObjectType;
- `ObjectRelationService` — получение и изменение отношений Object;
- `PropertyDefinitionService` — определения и настройки пользовательских свойств;
- `PropertyValueService` — значения свойств конкретного Object;
- `LocalizationService` — локализуемые тексты.

**Редактор Object**

Создание и редактирование выполняются общей формой Object. При её реализации используются `ObjectService`, `ObjectTypeService`, `PropertyDefinitionService`, `PropertyValueService` и `LocalizationService`. `ObjectRelationService` не относится к редактированию обычных полей и значений свойств Object: управление отношениями выполняется отдельными действиями на подробной странице или в соответствующем интерфейсе отношений.

**Навигация и переход от старой модели**

В целевой навигации используется единый раздел Objects. Управление ObjectType является отдельным разделом и реализуется на этапе 3.5.2. Существующие страницы и маршруты Project/Content сохраняются, пока их пользовательские сценарии не перенесены на новую модель Object; их удаление не входит в этап 3.5.1.

Сервисы Object и связанные сервисы принадлежат MainWindow. UI получает необходимые зависимости через конструкторы от точки сборки приложения; страницы не создают Repository или Service самостоятельно.

## 8. ConfirmModal

ConfirmModal является единым механизмом подтверждения действий в native UI.

Концептуальный поток:

~~~text
Qt UI
↓
ConfirmModal
↓
решение пользователя
↓
callback
↓
Application Service / Use Case
↓
C++ действие
~~~

Отображение, состояние диалога и пользовательский выбор принадлежат UI-компоненту. Само удаление или изменение сущности выполняется C++ service после проверки правил.

## 8.1 Правило самодостаточности UI-компонента

Компонент отвечает за собственное:
- визуальное состояние;
- дочерние widgets;
- сигналы/слоты;
- локальные UI-правила;
- передачу пользовательского намерения наружу.

Компонент не выполняет SQL и не содержит бизнес-правила.

## 13. ООП-архитектура CreatorOS

C++ является основной ООП-моделью CreatorOS. Общий принцип организации кода действует во всех слоях приложения, а не только в UI: связанные данные и поведение одной ответственности остаются вместе, а повторяющиеся механизмы объединяются по смыслу и контракту. Предпочтительны передача данных/параметров и типобезопасная конфигурация вместо копирования одинаковой реализации. Уникальные правила остаются специализированными; похожие фрагменты с разными контрактами не объединяются искусственно. Наследование используется при совместимом контракте и отношении «является», composition — для частей с самостоятельной ответственностью. Абстракции создаются только при подтверждённой пользе для повторного использования, тестируемости, заменяемости или ясности границ.

~~~text
«является» + общий контракт + общее поведение
        → наследование

«содержит» / «использует» + независимый контракт
        → композиция

только совпадают поля
        → не повод для наследования
~~~

UI-класс не обязан разделять визуал и UI-поведение на разные архитектурные классы. Пара .h/.cpp является техническим устройством C++ для объявления и реализации одного класса, а не архитектурным разделением UI и logic. Неиспользуемые файлы удаляются только после проверки ссылок, CMake и зависимостей; само наличие пары .h/.cpp не является причиной для удаления.

### Общие UI-сущности и специализация

Каждый повторно используемый тип UI-сущности — карточка, список, страница подробностей, редактор, модальное окно и т. п. — централизует свой визуальный каркас, стандартное поведение, локальное UI-состояние и общие действия в одном компоненте. Общий компонент определяет, какие элементы существуют, как они размещены и что происходит при стандартном взаимодействии.

Специализированные UI-классы конкретных доменных сущностей (например, TaskCard) по возможности передают в общий компонент данные и конфигурацию: заголовок, описание, метаданные, статус, прогресс, подписи действий и идентификатор/маршрут перехода. Если самостоятельное поведение карточки не требуется, отдельный класс не создаётся: конкретная страница использует EntityCard напрямую. Для Object карточки формируются непосредственно в ObjectsPage; класс ObjectCard не вводится.

Если конкретная сущность требует дополнительной надписи, метаданных или действия, расширение должно подключаться через предусмотренный общий механизм (например, дополнительный metadata/action widget или типобезопасную конфигурацию). Не создавать новый архитектурный класс или отдельную копию UI только ради единичного отличия. При этом общий компонент не должен содержать ветвлений по конкретным ObjectType или по типам вспомогательных сущностей: специализированные данные передаются извне, а уникальное поведение выражается небольшим явным расширением.

Эти правила относятся ко всем повторно используемым UI-сущностям, а не только к карточкам. При рефакторинге нужно переиспользовать существующие EntityCard, EntityDetails, EntityHeader, EntityList, EditorDialog, FormField, ConfirmModal и StateWidget там, где их контракт подходит, расширяя его при необходимости вместо создания параллельных реализаций.

### Типизированные страницы и расширяемые метаданные

Страницы списков должны строиться на общем механизме, который централизует стандартный каркас и поведение: загрузку и обновление данных, loading/empty/error состояния, список, общие поля и типовые действия. Конкретная страница передаёт тип сущности, источник данных/адаптер, фабрику представления элемента и конфигурацию. Общая часть не должна проверять конкретный тип сущности через ветвления.

Общие поля страницы задаются единым контрактом, а метаданные описываются типизированными элементами/представлениями: у разных сущностей может быть разное число полей и разные значения. Уникальные действия и дополнительные секции подключаются через явные расширения или callbacks, а не через копирование страницы. Типизация должна сохраняться на границе конкретной страницы и адаптера; не следует сводить все данные к неструктурированным строкам или универсальным словарям без необходимости. При выборе реализации учитывать ограничения Qt MOC: шаблонный механизм не должен требовать Q_OBJECT там, где Qt signals/slots необходимы; конкретные QObject-страницы могут оставаться небольшими адаптерами.

### Типизированные репозитории

Репозитории могут использовать общий типизированный инфраструктурный механизм для повторяющихся операций с запросами: выполнение SQL, привязка параметров, обработка ошибок, чтение одной/нескольких строк и общие шаблоны результата. Конкретные репозитории сохраняют собственные контракты, SQL и преобразование строки результата в соответствующую доменную модель. Специфические транзакции и бизнес-ограничения не прячутся в универсальном CRUD-классе. Общий механизм должен сокращать дублирование, не ослабляя типизацию и не стирая различия предметных сущностей.

Повторяющийся прикладной механизм также не должен копироваться по сущностям только из-за разных типов данных. Если разные ObjectType или вспомогательные сущности используют одинаковую часть алгоритма, повторяемая часть должна находиться в общем типобезопасном механизме; специализированный класс добавляет уникальные проверки и правила.

При этом domain и application остаются независимыми от конкретной визуальной реализации. Бизнес-правила не переносятся в QWidget только ради уменьшения числа файлов. UI-компоненты и страницы не обращаются к SQLite и не выполняют файловые операции напрямую.

Интерфейсы репозиториев и интеграций вводятся там, где они дают реальную заменяемость и тестируемость. Искусственные абстракции не создаются. Файловая структура должна отражать ответственность компонентов; перемещение каталогов и удаление файлов выполняются только после проверки фактических зависимостей и сборки.

## 15. База данных и файловое хранилище

SQLite является локальной базой структурированных данных приложения. Содержимое Markdown-документов хранится в обычных файлах в выбранном пользователем рабочем пространстве.

Доступ к структурированным данным строится только через C++ infrastructure/repository layer:

~~~text
Native UI
↓
Application Service / Use Case
├── Repository → Qt SQL / QSQLITE → SQLite
└── File Service → File System → Markdown documents and attachments
~~~

UI-компоненты и страницы не работают с БД напрямую и не выполняют файловые операции напрямую.

### DatabaseManager

Отдельный инфраструктурный объект отвечает за открытие подключения, первоначальное создание схемы новой БД по единому SQL-файлу, проверку версии схемы, управление транзакциями и закрытие подключения. SQLite-файл хранится в пользовательском каталоге данных приложения, а не рядом с исполняемым файлом.

Репозитории отвечают за операции структурированных сущностей и индекса документов, например `IProjectRepository`, `IContentRepository`, `ITaskRepository` и `IDocumentIndexRepository`.

### Markdown и файловый сервис

Отдельный файловый сервис отвечает за чтение, создание, запись, переименование, перемещение и удаление Markdown-файлов, проверку доступности и синхронизацию индекса. Содержимое документа не дублируется в SQLite как единственная или основная копия. SQLite хранит индексируемые метаданные, теги, разобранные внутренние ссылки и связи с сущностями приложения. Индекс должен поддерживать полное перестроение из рабочего пространства, а операции с файлами и индексом должны обрабатывать частичные ошибки без автоматического удаления пользовательских данных.

CreatorOS должен обнаруживать изменения, сделанные внешними редакторами, и обновлять индекс. При недоступности файла, повреждённой ссылке или конфликте изменения приложение показывает понятное состояние и не удаляет данные автоматически.

### Схема структурированных данных

#### Границы схемы

В итоговую схему текущего этапа входят:

- `object_types`;
- `objects`;
- `object_relations`;
- `property_definitions`;
- `property_text_settings`;
- `property_entity_reference_settings`;
- `property_options`;
- `property_values`.

Таблицы `Platform`/`Account`, файловой подсистемы, настроек приложения, задач и публикаций в рамках этого этапа не проектируются. Их структура будет определена отдельно. Требования к корзине задач и публикаций, определённые в разделе 2.3, сохраняются как предметные требования для будущего проектирования.

#### Идентификаторы и временные метки

- Во всех таблицах, где предусмотрено целочисленное поле `id` в качестве первичного ключа, используется `INTEGER PRIMARY KEY AUTOINCREMENT`.
- Для таблиц с UUID поле имеет ограничение `TEXT NOT NULL UNIQUE`. UUID v4 создаёт Application через `QUuid::createUuid()`; формат UUID проверяется Application, дополнительная SQL-проверка формата не требуется.
- UUID неизменяем после создания записи.
- Обязательные временные метки имеют `TEXT NOT NULL`; необязательные временные метки допускают `NULL` до соответствующего события.
- Временные метки формирует Application в UTC в формате ISO 8601 с миллисекундной точностью. Проверка формата выполняется Application; отдельные SQL-проверки формата не добавляются.
- `created_at` неизменяем. `updated_at` изменяется по правилам соответствующей сущности. Пересчёт прогресса сам по себе не меняет `updated_at`.

#### Таблица objects: удалённый ObjectType и срок хранения

В дополнение к полям, описанным выше, таблица `objects` содержит:

- `former_object_type_uuid TEXT NULL`;
- `former_object_type_name TEXT NULL`;
- `deleted_timezone TEXT NULL`.

Внешний ключ `objects.object_type_id` ссылается на `object_types.id` с действием `ON DELETE SET NULL`. Дополнительные SQL-ограничения обеспечивают согласованность полей:

- `object_type_id IS NULL` допускается только при `deleted_at IS NOT NULL`, одновременно `former_object_type_uuid` и `former_object_type_name` должны быть заполнены;
- если `object_type_id IS NOT NULL`, оба поля прежнего ObjectType должны быть `NULL`;
- вне корзины `deleted_timezone` должен быть `NULL`; при помещении в корзину он заполняется идентификатором часового пояса, действовавшего в момент удаления.

Перед удалением ObjectType Application в одной транзакции проверяет отсутствие активных Object этого типа и сохраняет UUID и название типа у объектов в корзине. После этого удаление ObjectType выполняется с `ON DELETE SET NULL`. Наличие ссылок из корзины не блокирует удаление. При восстановлении Object пользователь выбирает существующий ObjectType, после чего поля прежнего типа очищаются.

`deleted_timezone` сохраняет идентификатор часового пояса (например, `Europe/Belgrade`), а не только числовое смещение UTC. Это позволяет корректно рассчитывать 30 календарных дней с учётом правил часового пояса, включая переходы на летнее и зимнее время. При восстановлении `deleted_at` и `deleted_timezone` очищаются.

#### Внешние ключи и каскадные действия

| Таблица и поле | Ссылка | Действие при окончательном удалении |
|---|---|---|
| `objects.object_type_id` | `object_types.id` | `ON DELETE SET NULL`; Application предварительно запрещает удаление типа при наличии активных Object. |
| `object_relations.parent_object_id` | `objects.id` | `ON DELETE CASCADE`. |
| `object_relations.child_object_id` | `objects.id` | `ON DELETE CASCADE`. |
| `property_definitions.object_type_id` | `object_types.id` | `ON DELETE CASCADE`; общие определения с `scope = common` не имеют ссылки на ObjectType. |
| `property_text_settings.property_id` | `property_definitions.id` | `ON DELETE CASCADE`. |
| `property_entity_reference_settings.property_id` | `property_definitions.id` | `ON DELETE CASCADE`. |
| `property_options.property_id` | `property_definitions.id` | `ON DELETE CASCADE`. |
| `property_values.object_id` | `objects.id` | `ON DELETE CASCADE`. |
| `property_values.property_id` | `property_definitions.id` | `ON DELETE CASCADE`. |

Мягкое удаление Object не активирует каскадное удаление: отношения и значения свойств сохраняются. Отношение временно не действует, пока хотя бы один из его Object находится в корзине. Окончательное удаление Object удаляет его отношения и значения свойств через внешние ключи.

Удаление ObjectType каскадно удаляет его определения свойств, настройки, варианты и значения этих определений. Это соответствует принятому правилу, что значения свойств удалённого ObjectType не переносятся и не восстанавливаются.

#### Ограничения целостности

SQLite обеспечивает ограничения, которые можно выразить непосредственно в схеме:

- допустимые значения `object_relations.role`: `main`, `addition`, `support`;
- непосредственная самоссылка в `object_relations` запрещена (`parent_object_id <> child_object_id`);
- циклические цепочки отношений проверяются Application;
- `objects.progress` допускает `NULL` либо значение от 0 до 100 включительно;
- `property_definitions.scope` допускает только `common` и `object_type`;
- для `scope = common` поле `object_type_id` должно быть `NULL`, для `scope = object_type` — не `NULL`;
- `property_definitions.value_type` допускает только `text`, `number`, `boolean`, `date`, `datetime`, `entity_reference`;
- булевы настройки определений свойств хранятся как `0` или `1`;
- ограничения длины текста неотрицательны, а если заданы обе границы, `min_length <= max_length`;
- `target_entity_type` обязателен для настройки `entity_reference`;
- обязательные поля и согласованность данных, непосредственно выражаемые через `NOT NULL`, `CHECK`, `UNIQUE` и внешние ключи, закрепляются в SQLite.

Application дополнительно проверяет:
- формат UUID и временных меток;
- соответствие JSON-значений типу и множественности определения;
- синтаксическую корректность JSON в `property_values.value`, `property_definitions.default_value` и `property_options.value`;
- соответствие настроек дочерних таблиц фактическому `value_type` определения (например, наличие `property_text_settings` только для `text`);
- применимость определения свойства к конкретному Object;
- обязательность и допустимость значений при создании, редактировании и восстановлении Object;
- циклические отношения и остальные предметные правила, которые нельзя надёжно выразить простыми ограничениями таблиц.

Дополнительные JSON SQL-функции и триггеры для этих проверок не вводятся. Значение свойства остаётся JSON в одном поле; семантическая проверка выполняется Application.

#### Уникальность и индексы

SQLite обеспечивает следующие ограничения уникальности:

- `object_types.name` — уникально без учёта регистра;
- `objects.name` — уникально без учёта регистра только среди активных Object (`deleted_at IS NULL`);
- `object_relations(parent_object_id, child_object_id)` — уникальная пара;
- `property_options(property_id, normalized_value)` — уникальная пара;
- UUID — уникальны во всех таблицах, где они предусмотрены;
- имена `property_definitions` уникальны без учёта регистра отдельно для каждой области: среди `scope = 'common'` и среди `scope = 'object_type'` в пределах одного `object_type_id`.

Для имён определений свойств используются отдельные частичные уникальные индексы: один для `scope = common`, второй для `scope = object_type` с учётом `object_type_id`. Это позволяет обеспечить требуемую уникальность без искусственного запрета совпадающих названий в независимых областях.

Дополнительно создаются индексы для часто используемых внешних ключей и выборок:

- `objects.object_type_id`;
- `objects.deleted_at` для корзины и поиска истёкших записей;
- `object_relations.child_object_id`;
- `property_definitions.object_type_id`;
- `property_values.property_id`.

Первичные и уникальные индексы, у которых нужный внешний ключ является первым столбцом, повторно не создаются. Индексы добавляются для реальных сценариев выборки, проверки внешних ключей и каскадных операций, без дублирования одинаковых индексных префиксов.

#### Транзакции и внешние ключи

- Любая операция, изменяющая несколько связанных таблиц, выполняется в одной транзакции. Это включает создание Object с отношениями и значениями свойств, помещение Object в корзину, восстановление, удаление ObjectType, удаление определения свойства и окончательное удаление Object.
- При ошибке любого шага вся операция откатывается.
- Для каждого соединения SQLite при открытии выполняется `PRAGMA foreign_keys = ON`. После включения приложение проверяет фактическое значение `PRAGMA foreign_keys`; если внешние ключи не включены, соединение не используется для работы приложения.
- Нарушение внешнего ключа приводит к ошибке операции. Автоматическое исправление или скрытое изменение связанных данных не выполняется.

#### Отложенные части схемы

Таблица настроек приложения не создаётся в рамках текущего проектирования. Также не создаются таблицы задач и публикаций новой модели. Полная схема этих сущностей, их связи с Object, собственные поля удаления и сохранение часового пояса будут спроектированы отдельными этапами до их реализации. Требования к их поведению, уже согласованные в этапе 3.3.7, остаются обязательными для последующего проектирования.

### Создание и версия схемы

#### Единый файл начальной схемы

- Для новой модели Object используется один SQL-файл начальной схемы: `database/migrations/001_initial_schema.sql`.
- Файл содержит полное создание всех восьми таблиц, согласованных на этапах 3.3.1–3.3.8, а также необходимые ограничения, внешние ключи и индексы.
- Начальная схема не содержит seed-записей: пользовательские ObjectType и другие пользовательские данные не создаются автоматически.
- Во время текущей разработки изменения структуры БД вносятся непосредственно в этот файл. Отдельные последовательные SQL-файлы миграций для каждого изменения не создаются.
- Автоматический механизм переноса уже существующей БД со старой схемы на новую или между изменениями схемы в рамках текущего этапа не реализуется. Если схема меняется в ходе разработки, локальная БД пересоздаётся вручную.

#### Версия схемы и применение

- Для новой БД с `PRAGMA user_version = 0` приложение применяет единый файл начальной схемы и устанавливает `PRAGMA user_version = 1`.
- Значение `user_version = 1` служит отметкой версии созданной схемы, а не основой для последовательного механизма обновления БД.
- Повторное применение начальной схемы к уже созданной БД не предусматривается.
- В SQL используются обычные `CREATE TABLE` и `CREATE INDEX`, без `IF NOT EXISTS`. Неожиданное наличие объектов схемы должно приводить к явной ошибке, а не маскироваться.

#### Переход со старой схемы в период разработки

- Перед первым запуском версии CreatorOS с новой схемой пользователь вручную удаляет старый файл БД `creatoros.sqlite`.
- Существующие SQL-файлы старой схемы `001_initial.sql`–`005_platforms_and_accounts.sql` больше не используются. Они удаляются из проекта, а их ресурсы исключаются из `resources/database.qrc`.
- В ресурсах приложения остаётся единый файл `001_initial_schema.sql`.

#### Проверка корректности

В рамках реализации схемы выполняются необходимые проверки её создания и целостности, включая проверку внешних ключей, ограничений и предусмотренных каскадных действий. Эти проверки являются частью проверки реализации этапа; отдельная сложная система полной диагностики БД при каждом запуске приложения не вводится.## 16. Основные пользовательские возможности

- планирование работы и выпуска контента;
- хранение и повторное использование материалов и вложений;
- ведение публикаций и связь публикаций с аккаунтами платформ;
- доступные интеграции с платформами, автоматизация и сбор аналитики;
- возможность совместной работы с ролями и правами доступа;
- локализация интерфейса и AI-функции, в которых пользователь контролирует предложенные результаты.

SQLite хранит структурированные данные, метаданные и поисковый индекс базы знаний. Содержимое документов хранится в обычных Markdown-файлах, а вложения — в файловой системе. CreatorOS должен сохранять возможность работы с Markdown-файлами вне приложения и не должен делать SQLite единственным хранилищем текста документов.

## 17. Кроссплатформенность

Целевые desktop-платформы:

~~~text
Windows
macOS
Linux
~~~

Qt используется как основной кроссплатформенный framework.

Platform-specific код допускается только через явно выделенные adapters.

Для каждой ОС отдельно проверяются:

~~~text
window management
native dialogs
secure storage
browser/OAuth callback
font rendering
Qt Widgets rendering
application data directory
packaging
~~~

Общая предметная модель, application services, repositories и native UI-компоненты должны оставаться максимально платформонезависимыми.

## 18. Лицензирование

CreatorOS распространяется как proprietary/closed-source приложение; лицензии сторонних компонентов должны допускать такое распространение.

### Qt

Основной open-source вариант — использование LGPL v3 компонентов Qt при полном соблюдении LGPL.

Qt не является однородно лицензированным пакетом: в актуальном Qt 6.12 часть модулей доступна open-source пользователям только под GPL v3. Эти GPL-only модули не включаются в базовую proprietary-сборку без отдельного лицензионного решения.

Для CreatorOS принимаются следующие практические меры:

~~~text
Qt DLLs
↓
динамическая поставка
↓
license notices
↓
информация об исходниках LGPL-компонентов
↓
возможность замены/relinking согласно LGPL
~~~

Особое внимание:
~~~text
модульный состав Qt
лицензирование дополнительных Qt-модулей
Qt Network Authorization
изменения исходного кода Qt
~~~

### SQLite

SQLite используется через Qt SQL/QSQLITE. В документации Qt 6.12 SQLite указан как third-party компонент под SQLite Blessing.

### Прочие зависимости

Каждая дополнительная библиотека проверяется до включения в основной target:

~~~text
license
commercial redistribution
source/notice obligations
static/dynamic linking requirements
platform compatibility
~~~

В релизе CreatorOS должен существовать раздел О программе → Лицензии.

Этот раздел фиксирует технические требования к распространению, но не является индивидуальным юридическим заключением. Состав компонентов каждого распространяемого пакета и их лицензии должны соответствовать актуальным лицензионным текстам.
