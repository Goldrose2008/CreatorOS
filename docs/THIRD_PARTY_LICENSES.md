# Лицензии и сторонние компоненты

**Статус:** рабочий реестр лицензирования проекта  
**Дата актуализации:** 08.10.2026

## 1. Назначение

Этот документ ведётся отдельно от архитектурной документации и используется как рабочий реестр лицензионных обязательств CreatorOS.

Задача документа:

- фиксировать конкретные библиотеки и модули текущего стека;
- указывать выбранную open-source лицензионную модель;
- фиксировать обязательства при распространении приложения;
- отслеживать сторонние компоненты, которые реально попадают в дистрибутив;
- служить частью release checklist перед первой публичной поставкой и последующими обновлениями зависимостей.

Документ не заменяет юридическую проверку конкретного релиза. При изменении Qt, способа линковки, состава runtime или условий распространения реестр должен быть пересмотрен.

## 2. Выбранная модель Qt

CreatorOS планируется как приложение с закрытым исходным кодом, использующее Qt Open Source по условиям LGPLv3.

Qt официально указывает LGPLv3 как подходящий вариант для Qt-приложений при соблюдении условий LGPLv3. Для open-source сборок отдельные модули Qt могут быть доступны только под GPL, поэтому состав Qt необходимо проверять до добавления нового модуля.

Текущий целевой набор:

| Компонент | Текущий статус | Open-source лицензирование | Решение CreatorOS |
|---|---|---|---|
| Qt Core | используется | LGPLv3 или GPLv2 | LGPLv3 |
| Qt Gui | используется | LGPLv3 или GPLv2 | LGPLv3 |
| Qt Widgets | используется | LGPLv3 или GPLv2 | LGPLv3 |
| Qt Sql | используется | LGPLv3 или GPLv2 | LGPLv3 |
| Qt Network | используется | LGPLv3 или GPLv2 | LGPLv3 |

Источники Qt 6.12:

- Qt Licensing: https://doc.qt.io/qt-6.12/licensing.html
- Qt GUI: https://doc.qt.io/qt-6.12/qtgui-index.html
- Qt Widgets: https://doc.qt.io/qt-6.12/qtwidgets-index.html
- Qt SQL: https://doc.qt.io/qt-6.12/qtsql-index.html
- Qt Network: https://doc.qt.io/qt-6.12/qtnetwork-index.html

## 3. Что означает использование Qt под LGPLv3 для CreatorOS

Для текущей модели распространения критичны следующие требования.

### 3.1. Приложение может оставаться закрытым

Использование LGPL-библиотеки не требует автоматически открывать исходный код самого приложения. Qt прямо указывает, что LGPL позволяет сохранять исходный код приложения закрытым, если приложение является произведением, использующим библиотеку, и соблюдаются условия LGPL.

### 3.2. Пользователь должен иметь возможность заменить Qt-библиотеки

Для LGPLv3 необходимо обеспечить возможность использовать приложение с другой, в том числе модифицированной, совместимой версией LGPL-библиотек.

Для CreatorOS выбранная техническая стратегия — динамическое подключение Qt-библиотек отдельными DLL/runtime-библиотеками, а не статическая линковка Qt непосредственно в исполняемый файл.

Это упрощает выполнение требования о relinking/replacement, но перед каждым релизом необходимо проверять фактический дистрибутив. Одна только динамическая линковка не должна считаться автоматическим доказательством полного соблюдения LGPL.

### 3.3. Нужно предоставить лицензионную информацию

Распространяемый продукт должен содержать:

- копию текста применимой лицензии;
- явное уведомление об использовании Qt;
- информацию о соответствующих исходных кодах Qt-компонентов.

Qt отдельно указывает, что при LGPL-использовании нельзя просто полагаться на ссылку на исходный код Qt на сайте Qt Company/Qt Project как на единственный способ выполнения требования по исходному коду. Доступ к исходному коду должен быть организован со стороны распространителя продукта.

### 3.4. Изменения в Qt нельзя превращать в закрытый проприетарный код

Если CreatorOS когда-либо изменит исходный код LGPL-компонента Qt, такие изменения должны распространяться с соблюдением условий соответствующей лицензии.

Пока проект не модифицирует исходный код Qt.

## 4. Третьесторонний код внутри Qt

Qt содержит код сторонних проектов с собственными лицензиями. Qt рекомендует приложениям указывать такие лицензии и отмечает, что учитывать необходимо те сторонние компоненты, которые фактически поставляются вместе с приложением.

Для Qt 6.12 опубликованы отдельные списки third-party-компонентов и SPDX SBOM.

Источники:

- Third-Party Code Used in Qt 6.12: https://doc.qt.io/qt-6.12/licenses-used-in-qt.html
- Qt 6.12 SBOM: https://doc.qt.io/qt-6.12/sbom.html

Поэтому реестр CreatorOS ведётся по фактическому runtime-дистрибутиву, а не просто по названию подключённого CMake-модуля.

## 5. Известные компоненты для текущего Qt 6.12

### Qt SQL / SQLite

Qt SQL в Qt 6.12 документирует SQLite как сторонний компонент. В документации Qt 6.12 указан SQLite 3.53.4 с SQLite Blessing.

Требование для проекта: при выпуске конкретной версии CreatorOS необходимо подтвердить фактическую версию и источник SQLite, который попал в дистрибутив через используемый QSQLITE plugin/runtime.

Источник: https://doc.qt.io/qt-6.12/qtsql-index.html

### Qt Network

Qt Network в Qt 6.12 документирует, среди прочего, Public Suffix List и libpsl как сторонние компоненты.

Это не означает, что каждый возможный компонент Qt Network автоматически является отдельным распространяемым артефактом CreatorOS. Перед релизом необходимо сверять фактический набор DLL/plugins с соответствующим SBOM и third-party notices.

Источник: https://doc.qt.io/qt-6.12/qtnetwork-index.html

### Qt GUI

Qt GUI в Qt 6.12 содержит ряд сторонних компонентов, среди которых документируются FreeType, HarfBuzz, D3D12 Memory Allocator и другие зависимости.

Фактически применимый список определяется тем, какие части runtime действительно используются и поставляются с приложением.

Источник: https://doc.qt.io/qt-6.12/qtgui-index.html

## 6. Что проверять перед релизом

Перед первым публичным релизом и после любого обновления Qt:

1. Зафиксировать точную версию Qt.
2. Зафиксировать список модулей Qt6::* и plugins, реально попавших в дистрибутив.
3. Проверить соответствующий Qt SBOM.
4. Проверить third-party licenses только для реально поставляемых компонентов.
5. Подготовить пользовательский раздел «Лицензии и исходный код» в дистрибутиве CreatorOS.
6. Включить необходимые тексты лицензий и notices.
7. Проверить, что Qt runtime поставляется таким образом, чтобы пользователь мог заменить совместимые LGPL-библиотеки.
8. Проверить, не был ли добавлен модуль Qt, доступный для open-source использования только под GPL.
9. Зафиксировать результат проверки в DEVELOPMENT_LOG.md.

## 7. Что пока не считается закрытым вопросом

Следующие вопросы должны быть закрыты перед первым публичным релизом:

- точный состав файлов Qt runtime, которые поставляются в release;
- точный состав third-party компонентов в этом runtime;
- способ предоставления исходного кода Qt и собственных изменений Qt, если они когда-либо появятся;
- пользовательский экран/раздел с лицензиями и notices;
- проверка финального installer/package на соответствие выбранной LGPL-модели.

До закрытия этих пунктов нельзя считать лицензионную проверку первого релиза завершённой.

## 8. Правило для будущих зависимостей

Новая библиотека, Qt-модуль, plugin, SDK или иной внешний компонент не добавляется в основной стек без предварительной проверки:

1. лицензии;
2. совместимости лицензии с моделью распространения CreatorOS;
3. обязательств при распространении;
4. third-party зависимостей;
5. способа включения компонента в конечный дистрибутив.

Результат проверки заносится в этот документ до завершения соответствующего этапа разработки.
